## 4. Decisions & record
- **The one-ulp item (the only numerics decision) — pinned the correctly-rounded double, kept exact equality.**
  Both failures were `expectEqual(0.03292575831602317, …)` vs `0.03292575831602318`. Those tests wrote their
  expectation as a **comptime** `@exp(-2.621 - 0.0317 * 25)`, while the code under test calls the **runtime** `@exp`.
  On 0.17 the two disagree by 1 ulp at this argument. Arbitration by exact arithmetic on the binary64 argument
  (`-2.621 - 0.0317*25` = `-3.41349999999999997868371792719699442386627197265625`):
  `exp(x) = 0.0329257583160231760330427409719954748271276658891916301919123`, so the nearest double is
  `0.03292575831602318` (`0x3fa0dba51e539ea0`) — **the runtime value is correctly rounded; the comptime literal is the
  one ulp low**. Same check for O2: `exp(-6.702499999999999680255768907955)` → `0x3f541ded83af797d` =
  `0.0012278384663129964`, also correctly rounded. Decision: replace the comptime re-derivation with the
  correctly-rounded literal + the proof in the comment, **keeping `expectEqual`** — a tolerance would have hidden the
  very comptime/runtime difference that was found, and the correctly-rounded value is toolchain-independent.
  Not a DEV: no production value changed and no bound moved.
- **`selectionBaseName` (production edit)**: the output-name check must treat an editor-supplied path the same way
  regardless of the host running the model; splitting on both separators is the host-independent rule the test asserts.
  POSIX-only behaviour is identical to `std.fs.path.basename`; the other `path.basename` use
  (`src/ecosys_ng.zig:13750`) is a real filesystem path in a message and was left alone.
- **Reaction fixture**: fixed the fixture, not the guard. DEV-021's `fraction >= 1e-12` skip stays; the test now
  exercises a present zone and still asserts the same error identity plus byte-exact rollback.
- **issue-106 crash: measured, not touched.** The 0.17 `build.zig` fix made the **executable-root test step compile
  and run for what is believed to be the first time** (120 tests: 119 pass, 1 crash). The crash is
  `index out of bounds: index 4, len 4` at `hourly_heat_water_solute.zig:10686` — the fixture's `schedules: [4]u8` is
  smaller than the 8-rung `recovery_substep_counts` ladder (`heat_step.zig:515`, already 8 rungs at `HEAD`). Recorded
  in `audit/issues/issue-106-…md` with the fix shape (size the fixture from the ladder + the stronger "whole ladder in
  ladder order" expectation) **gated on the `wthr.f` NFH verdict**, which this migration cycle deliberately did not
  decide. No test was relaxed to pass.
- **Playbook lesson**: on a toolchain bump, a 1-ulp test failure is answered by exact arithmetic against the binary64
  argument — decide *which* double is correct before touching the assertion, and beware tests whose expectation is a
  comptime evaluation of the very builtin the code calls at runtime.
