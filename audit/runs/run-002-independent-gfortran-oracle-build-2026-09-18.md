**New finding, not previously documented**: `f77src` contains a **stray, uncompiled duplicate** -- `redist_utf8.f` -- which is not part of `f77src\makefile`'s `SRCS` list (the makefile lists exactly 40 `.f` modules; the directory has 41). This is a source-tree hygiene issue, not a science gap -- `redist_utf8.f`'s relationship to `redist.f` (byte-for-byte duplicate vs. a divergent variant) has not been diffed and is out of scope for this run record; flagging for a future dedicated check.

Flags (identical to OneDrive's documented `PROVENANCE.md` recipe): `-O2 -std=legacy -cpp -ffixed-form -ffixed-line-length-72 -fdefault-real-8 -fdefault-double-8 -falign-commons -fautomatic -fmax-stack-var-size=0 -fprotect-parens -fno-associative-math -fno-reciprocal-math -ffp-contract=off -fno-frontend-optimize -fallow-argument-mismatch`, plus the same `EXTERNAL SPLIT` compatibility declaration inserted into a scratch **copy** of `soil.f` (gfortran 16 otherwise treats `SPLIT` as an intrinsic and rejects the legacy 10-argument call to the user-defined `SPLIT` subroutine). `splits.c`/`splitp.c` compiled separately via `gcc -O2 -c`.

**Result: build succeeded.** Two harmless warnings only (`watsub.f:5774,5780` -- unary-minus-following-arithmetic-operator extension warnings, purely a parser-leniency note, not a correctness concern). ## Execution attempt

`ecosys_oracle.exe` (renamed to `ecosys_x.exe` for PowerShell invocation -- PowerShell refuses to run a bare `.x`-extension file mid-pipeline, treating it as a document rather than an executable) launched against the isolated, decontaminated deck via the exact stdin sequence extracted from `runottawa`'s heredoc.

**Correction/clarification (this is NOT a plain 6-year run)**: `runottawa`'s stdin line `6,5` (read by `main.f:64,72` as `NAX,NDX` then `NAY,NDY`) configures **6 weather/option scenes (the 1998-2003 file blocks) executed as one scenario, repeated 5 times** (`main.f:113-119`'s `DO 120 NTX=1,NDX / NEX=1,NAX / NT=1,ND(NEX) / NE=1,NA(NEX)` calls `SOIL` `1*1*5*6=30` times total) -- i.e. this is a **30-simulated-year rotation replay**, reusing the same 6 years of weather/option files 5 times over, with the internal calendar year counter continuing to increment across repeats (e.g. the 2nd repeat of the "1998" scene logs as calendar year 2004, not 1998, explaining log lines like `NOW EXECUTING DAY 120 OF YEAR 2005` seen well after the nominal 1998-2003 file range). **This exactly matches the Zig production run's own declared horizon** -- `audit/runs/run-001-ottawa-diagnostic-2026-09-18.md` independently documents `expected_hours=262920`, "30 passes (5 repeats x 6 scenes: years 1998-2003)" for the ecosys-ng side of the same deck. This means the Fortran oracle, if it runs to completion, is directly comparable in scope to the Zig production example, not a shorter proxy of it.

**Observed behavior**: the binary runs and is genuinely making progress (confirmed via direct log-file byte-growth checks over multiple short intervals -- not a hang), but is extremely slow and extremely verbose during `starte.f`'s soil-chemistry initialization phase (the two ~1000-iteration Newton-style convergence loops already documented in `audit/features/feature-008-starte-soil-chemistry-initialization.md`). The legacy code prints a full diagnostic dump (`RPALPX1`,`RPFEPXI`,`APATI`,`RXH2PI`,`RYH2PI` state vectors) every 100th Newton iteration, for every grid cell, for every K-branch (rainfall/irrigation/soil) -- this print is unconditional in the Fortran source (not gated behind a debug flag), so it fires on every run of this binary, not just this attempt. This independently corroborates why the OneDrive reference project's own gfortran run was "externally terminated" rather than run to natural completion -- the same verbose-and-slow initialization behavior would affect any gfortran build of this codebase, not something specific to this checkout.

**Update**: the initial attempt crashed deterministically at day 286/year 1 with a genuine Fortran runtime I/O error -- see `audit/issues/issue-023-grosub-8821-format-write-argument-mismatch-oracle-build-crash.md`. After patching the scratch-only oracle build (restoring a missing `IYRC` argument to a debug `WRITE` statement, matching its own commented-out sibling), the run was relaunched and **completed the entire 30-simulated-year rotation without any further error**, monitored continuously to completion (~2h40m wall-clock: heavy STARTE-initialization cost concentrated in the first simulated year, then a steady ~9-11 simulated days/minute pace thereafter). The only anomaly at exit was gfortran's standard informational note (`Note: The following floating-point exceptions are signalling: IEEE_INVALID_FLAG IEEE_DIVIDE_BY_ZERO IEEE_UNDERFLOW_FLAG IEEE_DENORMAL`) -- this is a non-fatal end-of-program FPE-flag summary gfortran prints whenever any of those flags were raised at any point during the run (common and expected for a 30-year biogeochemical model with many near-zero-denominator ratios); it does not indicate a crash, and the process exited 0.
