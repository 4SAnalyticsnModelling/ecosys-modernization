# Run 011 -- matched-state kernel harness (`kernelgen.py`) validated end to end on STOMATE

Date: 2026-09-21. Executed by the adversarial Claude/Pi session; the harness was written by the peer Pi session, the build and run recorded here were performed by this session (Pi had explicitly not built or run anything, and said so plainly when asked).

**Why this matters beyond the tooling**: `issue-024`, `issue-079` and `issue-080` each name a "matched-state kernel comparison" as their required next experiment, and all three have been blocked on the same missing capability -- no way to drive a single legacy Fortran routine in isolation with a chosen input state. `issue-078`'s sixth pass hit a related wall from the Zig side. This run establishes that the capability now exists and works.

## What was validated, and what was not

**VALIDATED (mechanism)**: generation, compilation, linking, stream I/O against a byte-exact COMMON layout, and that the legacy routine actually executes and mutates state.

**NOT VALIDATED (physics)**: the input used was all zeros. That is not a physical soil/plant state, so nothing here says anything about STOMATE's science or about oracle-versus-Zig agreement. This run answers "does the harness work", not "do the two sides agree".

## Exact commands and results

Artifacts generated by `ecosys-audit/scripts/kernelgen.py` (peer-written): `audit/tests/kernels/kernel_stomate.f` (driver, 4,964 bytes), `kernel_stomate.layout.json` (51,167 bytes, 74 variables), `kernel_stomate.build.ps1` (1,444 bytes).

1. **Build** -- `.\audit\tests\kernels\kernel_stomate.build.ps1 <scratch_dir>` from the project root, output directed into this session's scratchpad so nothing was written into the tracked tree. **exit 0.** The script compiles the generated driver with `-ffixed-form -ffixed-line-length-72 -fdefault-real-8 -fdefault-double-8 -I f77src`, compiles `f77src/stomate.f` separately with the additional `-std=legacy -fallow-argument-mismatch`, then links. The split is deliberate and documented in the script: the driver needs `ACCESS='STREAM'` (Fortran 2003) while the legacy unit needs `-std=legacy`. The `-fdefault-real-8`/`-fdefault-double-8` precision contract matches the documented oracle recipe in `run-002`/`issue-023`, so this harness and the full oracle build agree on real-kind by construction.
2. **Input** -- created `kernel_stomate.in` as exactly `36,994,008` zero bytes, the size the layout declares.
3. **Run** -- `.\kernel_stomate.exe` in that directory. **exit 0, 0.88 s wall clock.** Printed `kernelgen: ok`. Wrote `kernel_stomate.out`, also exactly `36,994,008` bytes.
4. **Proof the routine actually ran, not just the I/O**: `SHA-256` of input `E35F9545823C5C6C0CC74B82CF8B2F73750898BA56947249DACDCCAC583C06E6` versus output `9562904C1865D93F030948FD8F053F2CC689C60D1D865B887EE98F52E70E6BC0` -- **not identical**, with exactly **2 nonzero bytes** in the output. A byte-identical output would have meant the driver was a no-op; it is not. Two nonzero bytes is the expected order of magnitude for an all-zero input, where nearly every term evaluates to zero.

Wall-clock note worth keeping: 0.88 s per invocation, against roughly 19 minutes for a fresh-from-hour-1 production run. A kernel comparison is three orders of magnitude cheaper than the runs this project has been spending its diagnosis budgets on.

## What is still required before this answers a single open science question

1. **An input writer.** The layout JSON gives names, types, ranks, bounds and byte offsets, but nothing yet constructs a *physical* state from it. Until that exists, the harness can only be smoke-tested. This is the single blocking item.
2. **A Zig-side counterpart driver** that loads the same `.in`, runs the Zig kernel, and emits a comparable `.out` -- otherwise there is an oracle with nothing to compare against.
3. **The internal-block extraction** for the three issues that actually need it: `issue-024`/`issue-079` need the WATSUB freeze-thaw blocks (`watsub.f:2802-2823` snow-free surface, `:6399-6415` deep-layer micropore), and `issue-080` needs the REDIST tillage mixing blend (`redist.f:12137-12203`). None of the three is a standalone subroutine, so each needs the wrapper or slicer path.

Recommended order: input writer first (it is the one item every downstream use needs), then the WATSUB freeze-thaw wrapper, since `issue-024` is the top-priority science gap and its disposition question is currently unanswerable without exactly this measurement.
