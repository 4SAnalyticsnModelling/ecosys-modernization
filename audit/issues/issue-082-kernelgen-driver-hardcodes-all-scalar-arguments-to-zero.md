# Issue 082 -- `kernelgen.py`'s generated driver hardcodes every scalar argument to 0, so the routine is called out of bounds and computes nothing

Status: **FIXED AND VALIDATED, same day (2026-09-21)** -- see `audit/runs/run-012-kernelgen-harness-validated-against-hand-arithmetic-2026-09-21.md`. The peer author rewrote the generator to take `I/J/NFZ/NZ/NY/NX` from `COMMAND_ARGUMENT_COUNT`/`GET_COMMAND_ARGUMENT` with a `<kernel>.args` sidecar fallback, to emit in-Fortran bounds checks that `STOP 2` before opening the snapshot, and to add `-fcheck=bounds` to both the driver and legacy-unit compiles. Rebuilt and re-run here on the run lane, with all three guard cases tested explicitly: out-of-bounds `NZ=0` refused (`argument NZ out of bounds [1,JP]`, exit 2), no-arguments refused (exit 2), valid subscripts accepted (exit 0, 0.068 s). The decisive proof is that the two quantities this issue used to expose the defect now come out right: `FMOL(1,1,1) = 40.89887640449439` against a hand-computed `1.2194e4/298.15`, matching to full f64 precision, and `CO2I(1,1,1) = 280` against `0.7*400`, exactly. ## The defect

`audit/tests/kernels/kernel_stomate.f`, the driver generated by `ecosys-audit/scripts/kernelgen.py`, contains:

```fortran
      INTEGER I,J,NFZ,NZ,NY,NX
      INTEGER IOS
      I=0
      J=0
      NFZ=0
      NZ=0
      NY=0
      NX=0
      ...
      CALL STOMATE(I,J,NFZ,NZ,NY,NX)
```

Those six values are `STOMATE`'s entire argument list (`f77src/stomate.f:2`: `SUBROUTINE stomate(I,J,NFZ,NZ,NY,NX)`), and there is **no mechanism anywhere in the driver to supply them** -- not from the snapshot, not from argv, not from an environment variable. Every kernel this tool generates will call its routine with all-zero scalar arguments.

For `STOMATE` that is out of bounds. `NZ`, `NY`, `NX` are the plant/latitude/longitude subscripts, and the arrays they index are declared with lower bound **1** (per the layout manifest this same tool emits: `FMOL` bounds `1:JP, 1:JY, 1:JX`). So `stomate.f:55`'s `FMOL(NZ,NY,NX)=1.2194E+04/TKC(NZ,NY,NX)` reads and writes `FMOL(0,0,0)` and `TKC(0,0,0)` -- outside the declared arrays. gfortran was not given `-fcheck=bounds`, so this is silent undefined behavior writing into whatever precedes those arrays in the COMMON image.

## How it was found, and why the earlier "validation" did not catch it

A physical input state was written with `kernel_writer.py` (`TKC(1,1,1)=298.15`, `CO2Q(1,1)=400.0`, `FCO2(1,1,1)=0.7`, `SSIN(1,1)=0.866`, `ARLFP(1,1,1)=3.0`, and others), the kernel was run, and the outputs were checked against hand-computed expectations:

| quantity | expected | observed |
|---|---|---|
| `FMOL(1,1,1)` = `1.2194e4 / 298.15` | `40.90` | **0** |
| `CO2I(1,1,1)` = `FCO2 * CO2Q` = `0.7 * 400` | `280` | **0** |
| `TKC(1,1,1)` (invariant) | `298.15` | `298.15` OK |
| `CO2Q(1,1)` (invariant) | `400` | `400` OK |
| `SSIN(1,1)` (invariant) | `0.866` | `0.866` OK |

Both computed quantities are assigned at `stomate.f:55-56`, **before** the `SSIN`/`ARLFP` gate at `:57-58`, so they must be written unconditionally for any in-bounds subscript. They were not, which pointed straight at the subscripts. The invariants round-tripping perfectly proves the snapshot I/O and `kernel_writer.py` are sound; only the argument handling is broken.

**Correction to `run-011`, which this issue supersedes on one point.** `run-011` reported that the output differed from a zeros input by exactly 2 nonzero bytes and concluded this was "proof the routine actually ran, not just the I/O". The first half stands -- something executed. The conclusion was too generous: with all-zero subscripts the only observable effect available to the routine is an out-of-bounds write, so **those 2 nonzero bytes are most likely the signature of the out-of-bounds store, not of legitimate computation.** `run-011` has been annotated accordingly. This is exactly the failure mode the harness has to be proof against, because an out-of-bounds write that happens to land somewhere harmless produces a plausible-looking nonzero diff and a confident but meaningless "the oracle works".

## Required fix

The driver must take its scalar arguments from outside itself. Either:
1. read them from a small header prepended to (or a sidecar beside) the snapshot, which keeps one file as the complete description of a case; or
2. accept them on the command line via `COMMAND_ARGUMENT_COUNT`/`GET_COMMAND_ARGUMENT`, which is simpler and adequate.

Whichever is chosen, the generated driver must **refuse to run on a subscript that is out of the declared bounds** rather than proceeding. The bounds are already in the layout manifest, so the generator can emit the check. Compiling the kernel with `-fcheck=bounds` would be a cheap additional backstop for the legacy unit and is worth doing for a diagnostic harness even though it is wrong for production.

Recommend also adding a generated self-test to `kernelgen.py`'s output: write a known value to an input-only member, run, and assert a hand-computable output. For `STOMATE` that is exactly the `FMOL = 1.2194e4/TKC` check above -- one line of arithmetic that would have caught this immediately.

## What is NOT affected

- `kernel_writer.py` is **verified correct** and is not implicated. Nine of eleven offsets matched a hand calculation on the first attempt, and the two that did not were my hand calculation being wrong, not the writer's: `WGLF` and `ARLF` have first bound `0:25`, so index `[1,...]` correctly lands at byte offset 8 rather than 0. The writer handled the zero-lower-bound case that the project's own dialect notes warn "silently produces wrong science"; the hand check did not. See `run-011`'s addendum for the full offset table.
- The build and stream I/O path is sound: `36,994,008` bytes in and out, exit 0, 0.068 s with the physical state.
- The `-fdefault-real-8`/`-fdefault-double-8` precision contract matches `run-002`'s oracle recipe, and the layout manifest independently confirms `effective_type: f64` for these members, corroborating the dialect note that every implicitly-typed real in this tree is f64.
