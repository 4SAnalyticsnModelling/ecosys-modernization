## Root-cause investigation (2026-09-19)

Diagnosis-only, follow-up pass per the task's three-experiment budget and the contract's "inputs/bindings before physics" investigation order. Method: pure source reading (no build, no rerun, no source changes) of `f77src/watsub.f:6907-6913`, `f77src/redist.f:9645-9666`, `f77src/starts.f:640-661`, `ecosys-ng/src/soil/water/heat_step.zig:3280-3420`, `ecosys-ng/src/soil/water/heat_layer_remap.zig` (full file, `calculate` at lines 107-302), `ecosys-ng/src/soil/profile/relayering.zig:380-609`, `ecosys-ng/src/soil/profile/relayering_activity.zig:1-243`, and a structural comparison against `ecosys-ng/src/validation/layer_local_conservation.zig` and `ecosys-ng/src/redistribution/tillage/activity.zig`. Cross-references `issue-060` and `issue-006` (`SURFACE-HEAT-BRACKET-RUNAWAY-001`/`DRY-LAYER-UNPHYSICAL-HEAT-SINK-HOUR-2726-001`).

### Finding 1 -- the discard is faithfully-preserved legacy behavior, confirmed in TWO legacy sites, not a Zig translation defect

`watsub.f:6907-6913`, read directly: `IF(VHCP1(L,NY,NX).GT.VHCPRX(NY,NX).AND.VOLX(L,NY,NX).GT.ZEROS2(NY,NX))THEN TK1=(ENGY1+THFLWL+THFLFL+THFLVL+HWFLU1+HFLXF)/VHCP1 ELSE TK1=TKS(L,NY,NX)`. When a layer's heat capacity is at/below the floor, legacy does not divide; it holds the layer at its prior temperature and the forcing terms (`THFLWL` etc., already booked as leaving/entering neighboring layers elsewhere) are never applied to this layer's state. This is exactly what `heat_step.zig:3332-3370`'s WATSUB-6907 discard path does, and its own comment (lines 3313-3319) already says so ("WATSUB 6907--6913 does not solve a layer whose heat capacity is at or below VHCPRX; it holds TKS and the energy the layer cannot absorb is discarded... The oracle can afford that silently because it has no conservation census; this census exists, so the discard is booked and reported"). Disposition for the discard decision itself: `preserved`.

Second, independently: `redist.f:9645-9666` (the REDIST layer-remap/relayering code, `STARTS 655`/`redist.f:9655-9659` cited by `flux.zig:47-62`) computes `FXENGY` (moved material's energy at the donor's own temperature), forms exact energy splits `ENGY1=VHCP(L1)*TKS(L1)+FXENGY` / `ENGY0=VHCP(L0)*TKS(L0)-FXENGY` (these sum to the pre-transfer total exactly), then at lines 9655/9661 tests each side's POST-transfer `VHCP` against `VHCPRX`: above floor, divide (`TKS=ENGY/VHCP`); at/below, discard the computed `ENGY` and hold `TKS(L)` (the loop's reference temperature) instead. `ecosys-ng/src/soil/water/heat_layer_remap.zig`'s `calculate` (lines 231-275) is a deliberate, heavily-commented line-for-line translation of this exact logic, including its own VHCPRX-equivalent floor fallback (lines 270-275, comment explicitly cites `redist.f` 9660-9665), and carries five dedicated regression tests (lines 315-836) that pin this fallback's behavior against the legacy citations (e.g. "an emptied source with no retained storage inherits the destination temperature", "`redist.f` 9660--9665 handles this with an explicit fallback ... rather than a division by a vanishing capacity"). This is a carefully-audited, intentional fidelity match, not an overlooked gap.

### Finding 2 -- the concrete mechanism tripping `RelayeringActivityConservationFailure` is more direct than this issue's own original hypothesis, and is now confirmed by source reading (not yet by an instrumented rerun)

This issue originally hypothesized the failure comes from the WATSUB-6907 solve-time discard's compensating offset (`negligible_capacity_unabsorbed_megajoules_by_layer`, `heat_step.zig:3364-3369`) not being visible to `relayering_activity.zig`'s snapshot. That offset is confirmed real and confirmed NOT threaded anywhere else (a repo-wide search shows it referenced only inside `heat_step.zig`) -- but a second, more direct mechanism, found this pass, is independently sufficient to explain the same symptom:

`relayering.zig:380-609` calls `water_heat_remap.transferLayerFractions` (line 423 -- the redist.f 9645-9665 remap, including its own VHCPRX-floor fallback) and only afterward captures the donor/recipient "after" snapshot via `binding.sidecar.captureLayer`/`stageBoundary` (lines 587-607). `SnapshotSource.capture` reads the grid/thermal state directly, i.e. whatever `transferLayerFractions` actually wrote. Whenever the transfer leaves either side's resulting heat capacity at/below the floor (cell 0/layer 0 already was there this hour: `2.03e-5 MJ/K` vs the `8.38e-5` floor, per `issue-060`'s own cited evidence), `heat_layer_remap.zig`'s fallback (lines 274-275) assigns that side's temperature from the OTHER side's temperature rather than from `energy_after / capacity`, so the actual captured `heat_megajoules` diverges from the amount `stageBoundary`'s donor/recipient bookkeeping expects to have moved. `stageBoundary` (lines 210-222) allows only a tiny representation-level tolerance for `heat_megajoules` and raises `error.RelayeringActivityConservationFailure` for anything larger. This reproduces this issue's exact symptom through a distinct, more direct path than the original hypothesis (both mechanisms -- the WATSUB-6907 solve-time discard and the redist.f-remap-time fallback -- can fire for the same degenerate layer in the same hour; they are not mutually exclusive). **Not yet confirmed by an instrumented rerun or a targeted unit test** -- recommended as the first thing a follow-up (fix-implementation) pass should verify, e.g. a cheap synthetic `transferLayerFractions` + `stageBoundary` reproduction that drives a donor or recipient layer's resulting capacity at/below the floor and checks whether `RelayeringActivityConservationFailure` fires (mirrors this issue's own "Recommended next steps" item 3).

### Finding 3 -- magnitude: 14.7 MJ is not negligible against any ledger's own tolerance, but it is not an ordinary discarded flux either

Against the actual gates: `issue-060`'s own cited `tolerance_mj=1.49e-10` for this cell -- 14.7 MJ is roughly 14 orders of magnitude over that. `relayering_activity`'s own absolute tolerance is built the same way (`mass_balance_absolute_tolerance.heat_megajoules_m2 * cell_area_m2`, `hourly_geometry_disturbance.zig:49-69`), i.e. similarly minute for a 1 m2 Ottawa cell. No plausible tolerance change makes either ledger accept this "for the right reason" -- both are calibrated for floating-point/representation noise, not for a legacy-inherited physical discard.

But 14.7 MJ is also not "14.7 MJ of ordinary heat quietly vanishing from a healthy layer." It is the size of the ALREADY badly-diverged candidate state the Newton-Raphson/Anderson solver produced before giving up on this layer (`final_scaled_residual=2.24e14`, ~105 K candidate temperature spread, `defect_mj=-8.5` even in the "best-state" audit) on a layer whose total heat capacity is `2.03e-5 MJ/K`: dividing 14.7 MJ into that capacity would imply roughly a 724,000 K temperature swing, which is exactly why both legacy and Zig refuse to do it and hold the prior temperature instead. The deeper, still-open root cause is upstream of the discard entirely: *why* the solver stagnates this badly on this specific thin/dry cell-0/layer-0 state at hour 2,894 (and non-fatally at hours 2,705-2,726 under a different configuration) remains `issue-006`'s open, `NOT_ASSESSED` `SURFACE-HEAT-BRACKET-RUNAWAY-001`/`DRY-LAYER-UNPHYSICAL-HEAT-SINK-HOUR-2726-001` question -- unresolved by this pass, and out of scope for a "make conservation consumers robust" fix.

### Finding 4 -- structurally, at least a third (and plausibly a fourth) independent consumer of the same degenerate-layer state exists

Beyond `landscape_mass_inventory_phosphorus_ions.zig` (fixed, `issue-060`/`061`) and `relayering_activity.zig` (this issue, open): `ecosys-ng/src/validation/layer_local_conservation.zig` is a large, independent heat-conservation ledger (thousands of lines; dozens of `heat_megajoules`-typed before/after transfer accumulations across snow, litter, canopy, boundary and internal soil-heat paths) that is structurally capable of reading the same discarded/fallback-assigned layer state. `ecosys-ng/src/redistribution/tillage/activity.zig` independently implements the same donor/recipient predicted-vs-actual boundary-mismatch pattern as `relayering_activity.zig` (near-identical `Tolerance`/`Record`/`Sidecar` shapes, its own `error.TillageActivityPredictedPostMismatch`) for tillage-driven layer transfers -- i.e. the identical failure mode is structurally possible there too, if tillage ever operates on a layer in this degenerate state. Neither was proven to fail this pass (no reproduction attempted for either) -- this is flagged as supporting evidence for the "whack-a-mole" pattern this issue already named, not as a confirmed third failure.

### Recommendation (diagnosis only -- not implemented this pass)

Do not patch `relayering_activity.zig`'s tolerance, and do not extend `layer_local_conservation.zig`/`tillage/activity.zig` one at a time as each is (hypothetically) discovered to trip. Do not modify the discard/fallback itself in `heat_step.zig` or `heat_layer_remap.zig` -- Finding 1 shows it is a faithful, deliberately-tested legacy translation; changing it would be an unapproved physics deviation and would risk `heat_layer_remap.zig`'s own five existing regression tests.

The well-scoped candidate fix is architectural, not physical: generalize the pattern `heat_step.zig` already uses for `negligible_capacity_unabsorbed_megajoules_by_layer` into a single, shared, per-cell/per-layer "known legacy-floor discard this hour" ledger, populated by BOTH `heat_step.zig`'s solve-time WATSUB-6907 path AND `heat_layer_remap.zig`'s remap-time VHCPRX-floor fallback path (Finding 2), and have every downstream conservation consumer (`layer_local_conservation`, `relayering_activity.stageBoundary`, and `tillage/activity`'s equivalent check) subtract this shared offset from its own raw before/after delta before applying tolerance -- instead of each consumer needing its own bespoke floor/guard. This is the same family of fix as `issue-060`/`061`'s `aqueousCarrierM3` floor correction, generalized to a shared mechanism rather than repeated per file; it is explicitly NOT a "make every consumer independently tolerant of an unlabeled anomaly" pattern, because the anomaly is already fully characterized and bounded (Findings 1-3) and does not need rediscovering by each consumer.

Recommended next bounded actions, not performed here: (1) a cheap synthetic `transferLayerFractions` + `stageBoundary` unit reproduction confirming Finding 2's mechanism directly; (2) scoping the shared discard ledger's storage/threading (likely alongside `landscape_mass_balance_runtime.Inputs`, following the same threading pattern `issue-060`'s fix already used for `cell_area_m2`); (3) only after both, implement and validate with targeted tests before any further full-length run.
