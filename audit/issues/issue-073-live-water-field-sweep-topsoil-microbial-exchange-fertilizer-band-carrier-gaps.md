## Finding A (HIGH PRIORITY -- production-state-mutating, same severity class as issue-061 Finding 1 and issue-069 Finding A): `ecosys-ng/src/surface/metabolism_state_update.zig` -- the TOPSOIL aqueous carrier in five functions, distinct from the file's own already-fixed LITTER carrier

## Finding C (high blast radius, no guard at all): `ecosys-ng/src/stages/soil_chemistry_convergence.zig`'s `updateFertilizerBandGeometry` builds roughly twenty nitrate/phosphate/precipitate mol pools from the raw live water field with zero floor protection, unlike its own sibling function three calls earlier in the same file

`convergeHourlySoilChemistry` (the file's public entry point, line 102) calls, in order: `applyFertilizerDissolution` &rarr; `solveHourlyReactionCells` (which calls `solveHourlyReactionLayer`, confirmed to have the correct floor-skip at line 384/398, complete with its own `ISSUE-065 DRY_CARRIER_TRACE` diagnostic comment) &rarr; `updateFertilizerBandGeometry` (line 178).

`updateFertilizerBandGeometry` itself has **no such floor-skip anywhere**. Its second per-layer loop (lines 778-844) reads:

```zig
const water_volume_m3 = context.grid.matrix_liquid_water_m3[global_layer];
...
const nitrate_nonband_g_n = layer.nitrate_non_band * water_volume_m3 * 14.0;
const nitrate_band_g_n = layer.nitrate_band * water_volume_m3 * 14.0;
...

... [16 more phosphate/precipitate species pairs, all `concentration * water_volume_m3`] ...
```

with only a finiteness/non-negativity check (lines 705-706) -- **not** a magnitude/floor check of any kind -- before any of these multiplications. These become `nitrate_nonband_pools`/`hydrogen_phosphate_nonband_pools`/etc. (lines 845-878+), which feed the fertilizer-band nitrate/phosphate diffusion-redistribution geometry model (`ecosys.fertilizer_band_nitrate_phosphate`) alongside the tortuosity/diffusivity `layer_properties` computed in the first loop (lines 698-730, also unguarded against a near-zero `water_volume_m3` in the `water_fraction` calculation at line 707-713, though that branch is physically bounded by the `pore_capacity_m3 > 0` check and clamped to `[0,1]`, so it is lower-severity than the mass pools).

**Reachability.** `updateFertilizerBandGeometry` runs unconditionally, every hour, for every cell with `active_layer_count > 0` (line 674's only guard), regardless of whether any fertilizer band is actually configured for that cell (`nitrate_application`/`phosphate_application` only select `.banded` vs `.unbanded`, they do not skip the geometry/pool computation). This is the highest-blast-radius of the findings in this issue: roughly twenty species pools, every layer, every hour, with **no** floor protection at all (worse than an exact-zero guard -- there is no guard).

**Recommended fix pattern (not applied here):** mirror `solveHourlyReactionLayer`'s own already-correct pattern in the same file: compute `context.config.physical_tolerance.waterVolume(bulk_volume_m3)` and either (a) skip/zero-fill a layer's pools when `water_volume_m3` is at or below that floor (matching the `continue`-based skip this file already uses twice elsewhere, lines 218 and 661), or (b) substitute `context.soil_chemistry.dry_reference_water_m3[global_layer]` if the redistribution model requires a nonzero carrier to remain internally consistent with the reaction solver's own dry-reference bookkeeping. Given this function runs immediately after `solveHourlyReactionCells` in the same hourly pass, prefer whichever of (a)/(b) keeps its own pools consistent with what the reaction solver (and the concentration state it just wrote) assumed for the same layer in the same hour.
