### Step 3: is it a layer-index/relayering misattribution (hypothesis c)? Ruled out by an existing internal self-check

`hourly_cell_storage_before`/`after` (the exact arrays the gate compares, `ecosys_ng.zig:5849-5850`) are each populated once per hour by `diagnostics.reconstructLayerMassBalanceScopes` (`ecosys_ng.zig:5831-5835` for "after"; `:6643-6648` for "before"), which forwards to `layer_mass_inventory.reconstructScopes` (`layer_mass_inventory.zig:21-239`). That function computes the per-cell canonical total via a **wholly independent path** (`runtime.reconstructCells`, line 42) from the per-layer/scope totals it also builds in the loop below (lines 45+), and it **internally** calls `requireExactCellPartition` (line 239) before returning, every time it runs -- for both the "before" and "after" snapshot, every hour, not only when the external, additional partition check (`ecosys_ng.zig:6672`, needed because of the charcoal exchange-capacity adjustment at lines 6653-6671) happens to run. `requireExactCellPartition` (`layer_mass_inventory.zig:259-284`) enforces, to a tight `128*eps*addend_count*scale` roundoff bound, that the per-layer sum equals the independently-computed canonical cell total, and returns `error.LayerInventoryPartitionMismatch` on any drift.

No `LayerInventoryPartitionMismatch` (or any panic) appears anywhere in the log; the run reaches the terminal `HourlyCellConservationFailure` cleanly. This means: for hour 2,894's "after" snapshot, the per-layer sum and the independently-computed canonical per-cell total **agree**. Two different code paths reading the same underlying state at the same instant produce the same (collapsed) answer. That rules out a same-cell layer-to-layer misattribution (mass really moved from layer 0 to layer 1, still present in the cell total) as the shape of this defect -- both reconstruction paths agree the mass is gone from the cell, not merely relocated within it. (This run is single-cell, `cell_count=1`, so a *cross-cell* relayering misattribution is not applicable either.) **Hypothesis (c) as stated is refuted** for this specific failure; the mass is genuinely absent from (or uninterpretable from) the underlying chemistry state at the moment of capture, on both independent reads.

### Refined hypothesis (not confirmed by execution this pass): the shared carrier is `dry_reference_water_m3[layer]`, and the defect is in its captured VALUE, not the guard's threshold

`ecosys-ng/src/soil/chemistry/water_carrier_rebase.zig`'s own doc comment (line 184-189) states plainly that aqueous, phosphate, *and* geochemistry-solid coordinates all share one water-normalized representation and require "the same carrier translation." `state.dry_reference_water_m3[layer]` is the one stored value that stands in for a collapsed layer's water carrier across every one of those pools -- exactly the shared state the task asked to look for. Its lifecycle (`rebaseLayer`/`rebaseLayerWithRoundoff`, lines 190-266):
- On re-wet (`new_water_m3 > negligible_water_volume_m3`): reset to `0` (lines 210, 250, 264).
- On going/staying dry (`new_water_m3 <= negligible_water_volume_m3`): `rememberDryCarrier` (line 389-391) sets it **only if currently `0`**, to `sourceWaterM3(old_water_m3, ...)` -- which is `old_water_m3` itself if `old_water_m3` was above the floor, else whatever the (possibly-already-stale) reference already held.

Five call sites write through this mechanism, all in `ecosys-ng/src/stages/hourly_heat_water_solute.zig`: lines 731 and 755 (topsoil-only, vapor/soil-ingress carriers), 4563 (the main per-layer WATSUB commit, using `self.transport_replay.pendingSnapshot()` as `old_water_m3`), 7776 and 8190 (not yet read this pass). None of the four already-applied fixes (issues 060/061/063/064) touch this file or this mechanism at all -- they only widened the *threshold* used by `aqueousCarrierM3`-style guards elsewhere (the census/ledger side) to select between live water and whatever `dry_reference_water_m3` already holds. If the *value* being remembered at hour 2,894's degenerate layer-0 transition is itself wrong or stale (e.g. captured during the same substep-escalation episode from an already-degraded intermediate carrier, or reset-then-re-captured within the same hour), every fix that only widens the *selection threshold* would correctly make no difference at all -- which is exactly what was observed (bit-for-bit identical residuals across all four fixes). This is a materially different, more specific claim than the prior pass's hypothesis 1 ("carrier convergence" over many hours): it points at a specific value-capture/reset lifecycle bug tied to *this hour's* pathological heat-stagnation/substep-recovery episode, not a slow multi-hour drift.

**This is not confirmed.** Confirming it requires reading `state.dry_reference_water_m3[layer=0]` and `context.grid.matrix_liquid_water_m3[layer=0]` at the moment of the L186 heat-discard event and again at the L206 second-block capture -- values not present in the existing log and not recoverable from the hour-2,880 checkpoint (which predates the hour-2,894 episode by 14 hours of normal operation). The two remaining call sites (lines 7776, 8190) were not read this pass either.
