## Working hypothesis (not confirmed by a targeted experiment this pass)

The failing-element list -- aluminum, iron, calcium, magnesium, sodium, potassium (plus carbon/silicon) -- matches, field-for-field, `chemistry.aqueous[...]`'s `isBasePondedAqueousField` list (`ecosys-ng/src/soil/chemistry/layer_remap.zig:625`: `hydrogen`, `hydroxide`, `aluminum`, `iron`, `calcium`, `magnesium`, `sodium`, `potassium`) -- the free aqueous-ion pools moved by `transferAqueousLayerFraction`, **not** the geochemistry-solid/phosphate-precipitate pools issue-063 fixed. `relayering.zig`'s call to `transferAqueousLayerFraction` (item "4a. Aqueous chemistry", lines ~490-506) builds its `ZoneWaterVolumes` via `waterZones(src_water_before, ...)`/`waterZones(dst_water_before, ...)`/`waterZones(src_water_after, ...)`/`waterZones(dst_water_after, ...)` from the same **raw**, unfloored `src_water_before`/`dst_water_before`/`src_water_after`/`dst_water_after` values -- this call site was explicitly named, but deliberately not touched, in issue-063's own diagnosis ("`transferAqueousLayerFraction`'s own raw `ZoneWaterVolumes` ... not yet checked against the same floor").

This strongly suggests the **same carrier-basis mismatch mechanism** (mutator divides by a raw near-zero carrier; some census/whole-hour-balance reader elsewhere uses a floored carrier for the same field) recurs one call site over, on the aqueous free-ion pools instead of the solid/precipitate pools. Silicon and carbon's continued appearance could be residual attribution from the same cell's other pools (e.g. silicon from geochemistry silicates already fixed by issue-063, now showing a smaller residual than before but not zero; or from a different, not-yet-identified contributor) -- **not yet traced**, and should not be assumed without checking.

**Not confirmed to be `transferAqueousLayerFraction` specifically** -- this is a plausible, well-evidenced hypothesis from field-name overlap and this issue's own prior art, not a targeted reproduction. Per the project's three-experiment discipline, this is Experiment 0 (an observation from the validation run performed for issue-063, not a dedicated experiment for this issue); a real Experiment 1 should be a targeted read of `hourly_cell_conservation.zig`'s actual census wiring (does it call the same `aqueousCarrierM3`-floored path, or a different one?) before any fix is attempted.

## Fix applied and validated (2026-09-19, follow-up session)

### The specifically-diagnosed mechanism: fixed

Confirmed this issue's own leading hypothesis (`transferAqueousLayerFraction`'s `ZoneWaterVolumes` built from raw, unfloored water) is a real, genuine instance of the same defect class issue-060/061/063 fixed: `chemistry_layer_remap.transferAqueousLayerFraction`'s `concentration()` helper divides by `carrier` guarded only by a bare `carrier > 0` check (`ecosys-ng/src/soil/chemistry/layer_remap.zig:599-606`), and `relayering.zig`'s call site (item "4a. Aqueous chemistry") built the four `ZoneWaterVolumes` arguments (`src_zones_before`/`dst_zones_before`/`src_zones_after`/`dst_zones_after`) via `waterZones(...)` directly from the raw `ctx.grid.matrix_liquid_water_m3[...]` values, never routed through the floored substitution issue-063 already threaded into the sibling `transferSolidLayerFraction` call immediately below it.

**Fix** (`ecosys-ng/src/soil/profile/relayering.zig`): hoisted the `cell_area_m2`/`negligible_water_volume_m3`/`dry_reference_water_m3` computation that issue-063's fix had scoped to the solid-chemistry block (item "4b") up above item "4a", floors all four water values (`src_water_before`/`dst_water_before`/`src_water_after`/`dst_water_after`) through the existing `solidTransferWaterCarrierM3` helper (unchanged, reused as-is), and passes the floored carriers into `waterZones(...)` instead of the raw values. Item "4b"'s solid-chemistry block now reuses these same already-computed carriers instead of re-deriving them, so both call sites agree bit-for-bit on one basis. No new parameters or public API changes were needed -- this is a strictly internal reordering plus threading through the already-fixed helper.

**Regression test** (`ecosys-ng/src/soil/chemistry/layer_remap.zig`, `"issue-064: transferAqueousLayerFraction manufactures fake mass with a raw near-zero carrier but conserves mass when the caller floors it first"`): mirrors issue-063's own before/after test exactly, for `calcium` (a base-ponded aqueous field using the plain `shared_m3` carrier). Raw near-zero recipient carrier (`1e-9 m3`, below a `1e-6 m3` floor) manufactures fake mass `> 1000x` the real `0.5 mol` transferred amount; the same carrier floored first conserves exactly `0.5 mol`.

2. **`ecosys-ng/src/soil/chemistry/phosphate_inventory.zig`** (`solublePhosphorus_g_p`, REDIST UPO4 daily soluble-phosphorus output ledger) -- `litter_aqueous_carrier = if (litter_water > 0) litter_water else dry_reference_water` was an undiscovered sibling of issue-061 Finding 2's already-fixed `landscape_mass_inventory_surface.zig`, reading the same collapsible `litter_water_m3` array through its own private exact-zero-only guard. Fixed by adding a required `RuntimeContext.cell_area_m2: []const f64` field (wired from `ecosys_ng.zig`'s existing `driver_context.canopy_cell_area_m2.*`) and widening the guard the same way.
