# Issue 037 -- SOLUTE.F's restricted-domain (ISALTG=0 / static-salt) soil-layer NH4-NH3 and phosphate band-zone formulas are translated and unit-tested in Zig but have zero production callers

Status: **OPEN, LOW PRIORITY (corrected 2026-09-19) -- NOT an active gap for the validated Ottawa deck.** Not a numerical-correctness defect in the translated formulas themselves (those were verified faithful, including a deliberately-preserved legacy quirk); the gap is in production wiring/reachability. A definitive re-check (see "## Correction (2026-09-19)" below) found that the Ottawa deck is `ISALTG=1` (dynamic-salt), not `ISALTG=0` (static-salt) as a later pass (`issue-053`) had assumed without checking the deck's own input file. Because Ottawa is `ISALTG=1` on the legacy side too, the legacy oracle itself runs the full dynamic-salt formula set for this deck -- meaning Zig's current "always run the dynamic formulas" production behavior is the *correct* match for Ottawa, not a divergence from it. This issue's restricted-formulas-unwired finding is still real (the code exists, is dead in production, and would matter for a genuinely `ISALTG=0` deck), but it does not affect the project's one currently-validated production deck today. Downgraded from "affects the validated deck today" framing; see `audit/handoff-issue-triage.md`'s corrected Tier 3 ranking.

Owner: found by this session's audit fork, 2026-09-19, while auditing FEAT-017's "restricted band-zone mirrors" assignment (`f77src/solute.f`, ISALTG=0 branch, soil layers).

## What was found

`f77src/solute.f` branches on `ISALTG` (`:589,2880,4203,4630`; comment at `:2880-2882`: "IF NO SALT IS SELECTED IN SITE FILE THEN A SUBSET OF SOIL EQUILIBRIA REACTIONS ARE SOLVED: MOSTLY THOSE FOR PHOSPHORUS AND CO-REACTANTS"). The `ISALTG.EQ.0` ("restricted"/static-salt) branch does **not** mirror the full-salt branch's carboxyl dissociation (`:1407-1423`) or Al(OH)/Fe(OH)/carbonate ion-pairing (`:1432-1568`, `RALO1..4`/`RHCO3`/`RCO2Q`) at all -- confirmed absent by a full-file grep; this is a real, by-design omission on the Fortran side, not a translation gap. It **does**, however, mirror cation exchange (`:3348-3520`, restricted counterpart of `:1210-1387`), phosphate anion exchange (`:3075-3139` non-band, `:3268-3307` band; restricted counterparts of `:957-1174`), and NH4-NH3 dissociation (`:3547-3588`, restricted counterpart of `:1461-1494`) -- each with formula differences from the full-salt branch (documented in `FEAT-017` Findings 4 and 6).

Zig has direct, unit-tested translations of these restricted-domain formulas:
- `ecosys-ng/src/soil/solute/aqueous_reaction_rates.zig` (sha256 `BC6E1581D8F1CC4EBC012919BF92BAA490CEA9ECCFCE13E5DAF13DD9E8811418`), `calculateRestrictedAmmoniumSourceOrder` (`:82-142`), explicit doc comment citing `SOLUTE.F lines 3557--3588`, with a dedicated test (`:441-472`, `"SOLUTE 3557-3588 restricted ammonium retains band XMIN dependency"`) that specifically exercises the retained-`XMIN` legacy quirk at line `:3578`.
- `ecosys-ng/src/soil/solute/phosphate_exchange.zig` (sha256 `02C87C082842D30211620F9A7FA74ADB46040D80A72F600B7A3A51555DE09504`), `calculateRestrictedSourceOrder` (`:61-134`, citing `SOLUTE.F :3075-3139`) and `calculateRestrictedBandSourceOrder` (`:139-`, citing `SOLUTE.F :3268-3307`, explicitly documenting the source's `FIONX`/`FIONN` mixing), each with its own test.

A whole-codebase grep (`grep -r "calculateRestrictedAmmoniumSourceOrder\|calculateRestrictedSourceOrder\|calculateRestrictedBandSourceOrder" ecosys-ng/src`) finds **no callers outside the two defining files and their own in-file tests.** Separately, the per-cell static/dynamic-salt configuration flag (`dynamic_salts` / `salinity_enabled_by_cell` / `SalinityChemistry`) is genuinely wired through many other subsystems -- snow-solute transport (`snow_solute_transport.zig`), tillage salt incorporation (`salt_incorporation.zig`, `surface_chemical_transfer.zig`), root salt uptake (`root_processes_uptake.zig`), fire/combustion salt release (`organic_matter_fire_exchange.zig`, `disturbance_management_dispatch.zig`), fertilizer-band amalgamation (`fertilizer_band_nitrate_phosphate.zig`), and litter's own carboxyl gate (`litter_reaction_rates.zig:770`, `if (context.dynamic_salts) try carboxylRate(...) else 0`) -- but **not** by the core soil reaction-chemistry production path (`reaction_solve.zig`, `reaction_try_network.zig`, `reaction_solver_*.zig`, `cation_exchange.zig`'s main `calculate`/`calculateSourceOrder`, `aqueous_reaction_rates.zig`'s main `calculate`, `phosphate_exchange.zig`'s main `calculateForZone`), none of which branch on the flag at all for soil layers.

The practical implication: a soil cell configured for static-salt chemistry (`ISALTG=0`) still receives the full-salt/dynamic cation-exchange, NH4-NH3, and phosphate-exchange formulas in production ecosys-ng today. The restricted-domain formulas exist and are individually correct (including a deliberately preserved legacy defect) but are dead code from the production model's perspective.

## Why this needs a record

This is adjacent to, but distinct from, the "unified-kernel deviation" pattern in `issue-018`/`issue-020`/`issue-021`/`issue-036`: those are cases where Zig runs a *different, unified* formula in place of a legacy variant. Here, Zig has the *matching* variant written and tested but **never invokes it** -- a reachability/wiring gap rather than a formula deviation. It was not caught by the existing FEAT-017 dossier because Finding 4's original pass verified formula fidelity (comparing Fortran text to Zig function bodies) without checking whether those Zig functions are called from any production stage.

## Disposition

`unresolved`, pending a coordinator decision: either (a) static-salt (`ISALTG=0`) soil-layer chemistry is out of the v1.0.0 production scope entirely (in which case these functions should be documented as intentionally-unwired reference translations, or removed/flagged dormant per contract's "dormant branches remain in the inventory" clause), or (b) it is in scope and the soil reaction-network stage needs to branch on the per-cell salinity flag the same way litter's `carboxylRate` already does. No production run this pass exercises `ISALTG=0` soil cells to observe actual impact; materiality is not evaluated.

**Update (2026-09-19):** the coordinator decision above should be made in light of the correction below -- the project's only currently-validated deck (Ottawa) is confirmed `ISALTG=1`, so it does not exercise this gap at all. Option (a) is the practically operative choice for v1.0.0 unless/until a genuinely `ISALTG=0` deck enters scope; these functions should be documented as intentionally-unwired reference translations for a future static-salt deck, not treated as a defect blocking the current validated deck.

## Correction (2026-09-19, definitive re-check, read-only)

A later pass (investigating `issue-053`) asserted "this is a non-saline `ISALTG=0` deck" when discussing Ottawa, and `audit/handoff-issue-triage.md` built on that assertion to rank this issue as its #3 top Tier-3 priority specifically because it supposedly "affects the validated deck *today*, not conditionally." That assertion was independently re-checked and found to be **incorrect, unverified against either deck's own input file**:

- `f77src/readi.f:154` (`READ(1,*)IETYPG,ISALTG,IERSNG,NCNG,DTBLIG,XXXX,DTBLGG`) maps site record 3's second field to `ISALTG`. `f77example/Cool Temperate Maize-Soybean ON/f25si98` line 3 is `33 1 3 1 1.0 2.5 0.0` -- second field `=1`, i.e. **`ISALTG=1`** ("salt equilibrium concentrations and pH are solved dynamically," per `readi.f:99-100`'s own comment), not `0`.
- The modern production deck's equivalent input (`ecosys-ng-prod-examples/Cool Temperate Maize-Soybean ON/runottawa_input_files/landscape/f25si98`, line 3: `33 1 3 1 1.0 0.0`) confirms the same field `=1`.
- On the Zig side, `ecosys-ng/src/state/site.zig:239-249` (`SITE-SALT-001`/`SITE-SALT-002` banner) confirms this exact field is parsed into `site.salinity_enabled`, which `ecosys_ng.zig`'s domain initialization copies per cell into `salinity_enabled_by_cell` -- the flag that gates salt chemistry throughout the tree. For Ottawa's own input, this resolves to `true` (dynamic-salt), matching the legacy oracle's own `ISALTG=1` configuration for the same deck.

Root cause of the discrepancy: `issue-053` paraphrased `readi.f`'s comment describing what `ISALTG=0` *means* ("salt concentrations entered in soil file generate equilibrium concentrations that remain static") and then asserted, without checking `f25si98` or any site-record parse, that this applied "for a deck like Ottawa" -- an unverified assumption, not a checked fact. `issue-024`'s Round 5 addendum then repeated and amplified this claim (as "this non-saline, `ISALTG=0` deck") in a sensitivity argument, and `audit/handoff-issue-triage.md` treated `issue-053`'s assertion as already-confirmed evidence ("the project's own `issue-053` confirms the Ottawa deck **is** an `ISALTG=0` deck") when ranking this issue. No pass before this correction had actually opened `f25si98`/`readi.f:154` together to check the claim.

**Consequence for this issue specifically:** because Ottawa is `ISALTG=1` on the legacy side, the legacy oracle's own Fortran solver runs the full dynamic-salt formula set (`solute.f`'s `ISALTG.NE.0` branch) for this deck -- it does *not* run the restricted/static formulas this issue is about. Zig's current behavior (always running the dynamic/full-salt formulas in production, per this issue's own "What was found" section) is therefore the **correct** behavior for Ottawa, not a divergence from the legacy design. The restricted-formula-unwired gap this issue documents is real and would matter for a genuinely `ISALTG=0` deck, but it is **not** an active gap for the deck this project currently validates against. See `audit/issues/issue-053-hour1-cion-osmotic-potential-dual-formulation-unverified-equivalence.md` and `audit/issues/issue-024-top-layer-water-content-divergence-oracle-vs-zig.md` for the corresponding corrections, and `audit/handoff-issue-triage.md` Section 4 for the corrected Tier 3 ranking.
