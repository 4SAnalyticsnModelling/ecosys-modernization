`inventory.Storage`'s fields are checked by `stageBoundary` in **declaration order** via `inline for (std.meta.fields(inventory.Storage))`, and the loop returns immediately on the first field that fails. `heat_megajoules` is declared second (`landscape_mass_inventory_support.zig:36-37`, right after `water_m3`); `carbon_dioxide_carbon_g` is declared much later (`:52`), after eight `diagnostic_*` fields plus `oxygen_g`, `hydrogen_g`, `residue_carbon_g`, `organic_carbon_g`. This is a clean, deterministic, field-order-based proof that the heat-floor-discard netting fixed the mechanism it was built for.

## The new defect: `carbon_dioxide_carbon_g` is being manufactured at the recipient, not conserved

Donor (layer 1) loses essentially nothing (`1.87e-4` g C, consistent with a small REDIST boundary-displacement fraction `fx` for this hour). Recipient (layer 0 -- the SAME degenerate thin/dry cell-0/layer-0 state issue-060/062 already characterize as being at/below the VHCPRX heat-capacity floor this same hour) gains `10.6` g C -- roughly 100x the donor's loss and roughly 100x the recipient's OWN pre-transfer inventory (`0.108` g C). `allowed` (the acceptance tolerance for this field/scale) is `1.1e-8`, twelve orders of magnitude smaller than the actual mismatch. This is not a rounding/representation issue.

**Working hypothesis (NOT confirmed by a targeted experiment this pass -- diagnosis-only, per the project's three-experiment discipline):** `gas_remap.transferLayerFractions` (`ecosys-ng/src/soil/gas/layer_remap.zig`), the actual mutator called for this boundary's gas transfer (relayering.zig item "2. Gas"), is a pure `moved = fraction * source; source -= moved; destination += moved` transfer with no floor/fallback logic anywhere in it (read in full this pass) -- it cannot manufacture mass by construction, and its own regression tests pin exact conservation. The 10.6 g discrepancy must therefore come from something else that changes layer 0's `carbon_dioxide_carbon_g`-contributing state between `donor_before_activity`'s capture and the post-transfer `stageBoundary` capture, for this same boundary's processing window -- either:
1. A genuine local CO2-producing process (e.g. microbial respiration/decomposition, a mineralization reaction) that legitimately runs on layer 0 during this same hour and is being incorrectly attributed to (or double-counted with) this specific relayering boundary's before/after diff, when `stageBoundary`'s donor/recipient model assumes the diff is due to the transfer alone; or
2. A carrier-collapse defect analogous to issue-060/061's `aqueousCarrierM3` fix (`landscape_mass_inventory_phosphorus_ions.zig`) -- i.e. whatever computes the `carbon_dioxide_carbon_g` value for `relayering_activity`'s `SnapshotSource.capture_fn` at layer 0 may divide by (or otherwise depend on) the same near-zero water/aqueous carrier that collapsed this hour, in a module that was never updated with issue-060/061's floor fix because it is a different call site.

**This is explicitly NOT the same mechanism as issue-062** (that issue is about `heat_megajoules` and a heat-capacity floor; this is about `carbon_dioxide_carbon_g` and, if hypothesis 2 holds, a water/aqueous-carrier floor -- a mass-domain concern, not a heat-domain one). Per the task's own standing instruction not to conflate independent fixes, this is filed as a new, separate issue rather than folded into issue-062 or issue-060/061.

### Hypothesis 1 (local production / double-count) -- RULED OUT

Traced every mutation that runs between `donor_before_activity`/`recipient_before_activity`'s capture and `donor_after_activity`/`recipient_after_activity`'s capture for this exact boundary (`relayering.zig` lines ~359-625): fertilizer band remap, `water_heat_remap.transferLayerFractions`, `gas_remap.transferLayerFractions`, `organic_remap.transferLayerFraction`, transport-owner transfers, `chemistry_remap.transferAqueousLayerFraction`/`transferSolidLayerFraction`, `mineral_remap.transferLayerFraction`, `nitrite_remap.transferLayerFraction`, `fertilizer_remap.transferCellLayerFraction`, `root_remap.transferPondedCellLayerFraction`. No microbial respiration, decomposition, or mineralization step runs inside this window -- only the enumerated pool *transfers* do, and no gas-transport/diffusion stage runs concurrently with REDIST relayering for this cell.

- `gas_remap.transferLayerFractions` (`ecosys-ng/src/soil/gas/layer_remap.zig`), the mover of `gaseous_mass_g`/`dissolved_mass_g`/`macropore_dissolved_mass_g`/`band_dissolved_mass_g` for CO2/CH4 (the two species `landscape_mass_inventory_gas.zig:276-279`'s `fourPhaseGas` sums into `carbon_dioxide_carbon_g`), is confirmed a pure `moved = fraction * source; source -= moved; destination += moved` transfer (`transferPair`, line 118-122) with no floor, fallback, or production term anywhere in the file. `fourPhaseGas` itself (`landscape_mass_inventory_support.zig:427-436`) is a plain four-term sum, no division. Both read in full; neither can manufacture mass.
- `organic_remap.transferLayerFraction` (`ecosys-ng/src/soil/organic/layer_remap.zig`) never touches `gas.State` at all -- it moves organic-matter pools only, via the same pure-fraction `transferElementLayer`/`transferScalarLayer` pattern. Not a contributor.
- Root gas (`gaseous_carbon_dioxide_g_c`/`aqueous_carbon_dioxide_g_c`/`gaseous_methane_g_c`/`aqueous_methane_g_c`, aggregated into the same `carbon_dioxide_carbon_g` field by `aggregateRootGasLayer`, `landscape_mass_inventory_gas.zig:318-330,381-385`, when `relayering_layer_snapshot.zig`'s `capture` includes root gas) is **not moved by this boundary's root transfer at all**: `plant_root_layer_remap.zig`'s `soil_root_domain_layer_extensive_fields` list (lines 60-84, used by `transferSoilRootLayerFraction`, the function `root_remap.transferPondedCellLayerFraction` actually calls) explicitly excludes every root-gas field, with an explicit comment citing that `redist.f` 10415-10450's adjacent root-gas statements are commented out in the legacy reference and therefore intentionally excluded. Root gas at layer 0 and layer 1 is therefore bit-identical before and after this boundary's root transfer -- it contributes zero delta, not manufactured mass.

No other mutation in the window writes `gas.State`'s CO2/CH4 fields or the root-gas fields. Hypothesis 1 is ruled out for this specific boundary/hour: nothing resembling a double-counted local production process runs inside the before/after capture window.

### Hypothesis 2 (carrier-collapse) -- CONFIRMED, mechanism identified

`relayering_layer_snapshot.zig`'s `capture` (the actual `SnapshotSource.capture_fn` wired to production) calls **eight** group aggregators and sums their contributions into one `inventory.Storage`. `carbon_dioxide_carbon_g` is populated not only by `aggregateSoilPhysicalAndGasLayer` (soil gas, ruled out above) and `aggregateRootGasLayer` (root gas, ruled out above), but **also** by `aggregateProfilePhosphorusAndIonsLayer` (`landscape_mass_inventory_phosphorus_ions.zig`), which was not part of either recorded hypothesis's original text but is a third, previously-unidentified contributor:

- Aqueous carbonate/bicarbonate species (`isCarbonateCarrier`, lines 792-804) add directly, with no water-carrier division (`amount_mol * carbon_g_per_mol`, lines 289-291) -- not implicated.
- **`calcite_solid_mol_per_m3` and `pending_solids.calcite_solid_mol_per_m3`/`pending.calcite_mol` (lines 366-392) are implicated.** These are converted from concentration to extensive mass via `extensiveGeochemistrySolids(solids, water_m3)` (line 368), where `water_m3` is computed at line 263-267 via `aqueousCarrierM3(soil_water_m3[profile_cell], chemistry.dry_reference_water_m3[profile_cell], negligible_water_volume_m3)` -- **the already-fixed issue-060/061 floor**, which substitutes the much larger `dry_reference_water_m3` reference volume whenever the live water carrier is at or below the `ZEROS2`-derived `negligible_water_volume_m3` floor (`aqueousCarrierM3`, lines 621-631, using the shared `legacyNegligibleWaterVolumeM3` from `core/legacy_water_negligible_floor.zig`).

The actual **mutator** for these same fields at this exact boundary is `relayering.zig`'s call (lines ~508-545) to `chemistry_remap.transferSolidLayerFraction` (`ecosys-ng/src/soil/chemistry/layer_remap.zig:135-258`), which for every `geochemistry.SolidState` field (including `calcite_solid_mol_per_m3`, line 230-236) and every water-scaled phosphate-precipitate field (`aluminum_phosphate_solid_mol_per_m3`/`iron_phosphate_solid_mol_per_m3`/`dicalcium_phosphate_solid_mol_per_m3`/`hydroxyapatite_solid_mol_per_m3`/`monocalcium_phosphate_solid_mol_per_m3`, lines 208-224) calls `transferOwnedAmount` (lines 576-597) with `source_water_m3`/`destination_water_m3`/`source_water_after_m3`/`destination_water_after_m3` passed straight through from `relayering.zig`'s **raw, unfloored** `src_water_before`/`dst_water_before`/`src_water_after`/`dst_water_after` (`ctx.grid.matrix_liquid_water_m3[src_global]`/`[dst_global]`, captured directly at lines 341-342 and 490-491, never routed through `aqueousCarrierM3`). `transferOwnedAmount` derives the new concentration as `next_amount / scale_after` guarded only by `scale_after > 0` (line 587-588) -- **not** by any floor: a tiny-but-nonzero raw water carrier at the recipient (the same degenerate cell-0/layer-0 state issue-060/061/062 already characterize this hour) inflates the resulting `calcite_solid_mol_per_m3` concentration arbitrarily, because a modest transferred amount is divided by an almost-zero volume.

**The mutator and the census therefore use two different carrier bases for the same field, on the same layer, at the same instant**: the mutator (`transferSolidLayerFraction`) divides by the raw, near-zero carrier (inflating concentration); the census (`aggregateProfilePhosphorusAndIonsLayer`) then re-multiplies that inflated concentration by the much larger *floored* reference carrier (`dry_reference_water_m3`). The product is the appearance of manufactured mass at exactly this boundary's before/after diff, with no physical process or double-counted transfer involved -- a pure carrier-basis bookkeeping defect, structurally analogous to (but mechanically distinct from) issue-062's heat-floor-discard finding.

### Cross-check against `f77src/redist.f`: this is a translation-introduced indirection, not merely a missing floor

`redist.f`'s own relayering statements for these exact pools move them as **pure extensive mol**, with no water-carrier conversion anywhere:
- `PCACO` (precipitated CaCO3 -- legacy's `calcite_solid_mol_per_m3` analog): `redist.f:8935-8936` `PCACO(L1,NY,NX)=PCACO(L1,NY,NX)+FX*PCACO(L0,NY,NX)`; `redist.f:9987-9988` `FXPCACO=FPO*PCACO(L0,NY,NX); PCACO(L1,NY,NX)=PCACO(L1,NY,NX)+FXPCACO`.
- `PALPO`/`PFEPO`/`PCAPD`/`PCAPH`/`PCAPM` (the five phosphate-precipitate pools -- legacy analogs of the five `*_solid_mol_per_m3` phosphate fields): `redist.f:513-527`, the same pattern, `FALP=FSINK*PALPO(L,NY,NX)`, moved and subtracted/added directly.

Neither block references `VOLW` (soil water) at all. `ecosys-ng`'s Zig translation instead represents these pools as water-volume-normalized concentrations (`_solid_mol_per_m3`) and must round-trip through a water carrier to perform the same conservative transfer legacy performs directly on the extensive quantity. That round-trip is self-consistent (and legacy-equivalent) **only if every reader of the resulting concentration uses the same carrier the writer used** -- which is exactly what breaks down between `transferSolidLayerFraction` (raw carrier) and the census (floored carrier). Per the contract's investigation order ("...translation/units/indexing/precision defects... before approved physical changes"), this is classified as a translation/indexing defect in carrier consistency, not a physics-level question.

### Plausibility and bound (task step 3)

Recipient's own pre-transfer `carbon_dioxide_carbon_g` is `0.108` g; donor's whole-layer pool is `11.07` g; the manufactured `10.6` g is ~98x the recipient's own pool and comparable in scale to an *entire neighboring layer's* pool -- a large fraction of a small pool, not noise. The real, physically-bounded transfer this boundary performs is the donor's own observed loss, `1.87e-4` g (consistent with the boundary's tiny geometric fraction, ~1.7e-5 of the donor's pool). The manufactured amount is bounded only by the ratio `dry_reference_water_m3 / raw_water_m3` for the affected layer -- a ratio with no physical ceiling as the raw carrier shrinks toward (but never reaches) zero. This should be treated as a **systemic, potentially-unbounded-magnitude risk at any sufficiently degenerate near-zero-water layer**, not a one-off bounded to this hour/cell, and it recurs at the same cell-0/layer-0 state already flagged this hour by issues 060/061/062.

### Masking risk: this is a per-call-site defect, not a per-field one

`inventory.Storage`'s field declaration order (`landscape_mass_inventory_support.zig:35-93`) checks `carbon_dioxide_carbon_g` (line 52) well before `phosphate_phosphorus_g` (line 66), `ion_inventory_mol` (line 83), and the element-resolved `aluminum_mol`/`iron_mol`/`calcium_mol`/`magnesium_mol`/`sodium_mol`/`potassium_mol` (lines 71-76, populated from the same `geochemistry_solids`/phosphate-precipitate fields via `element_moles`, `landscape_mass_inventory_phosphorus_ions.zig:280-372`). Because `stageBoundary` returns on the first failing field, a netting-only fix scoped to `carbon_dioxide_carbon_g` (mirroring issue-062's pattern) would very likely just unmask the identical carrier-basis defect on `phosphate_phosphorus_g`/`ion_inventory_mol`/`aluminum_mol`/`calcium_mol`/`iron_mol` next, exactly as issue-062's own fix unmasked this issue. The correct fix scope is the call site (`transferSolidLayerFraction`'s carrier consistency), not the one field currently failing.

### Recommendation (diagnosis only -- not implemented this pass)

Do not net out `carbon_dioxide_carbon_g` with an issue-062-style discard ledger -- that pattern fits a *known, bounded, legacy-faithful* discard; this is an *unbounded* bookkeeping artifact with no legacy analog (per the `redist.f` cross-check above), so netting would hide a real translation defect rather than correctly account for preserved legacy behavior.

The well-scoped candidate fix is carrier consistency: thread the same floored carrier (`aqueousCarrierM3`/`legacyNegligibleWaterVolumeM3`, already centralized in `core/legacy_water_negligible_floor.zig`) into `relayering.zig`'s `chemistry_remap.transferSolidLayerFraction` call site, replacing its four raw `matrix_liquid_water_m3`-derived arguments, so the mutator and the census agree on the same basis -- a sibling application of issue-060/061's already-validated pattern to a call site that fix did not reach, rather than issue-062's netting-ledger pattern.
