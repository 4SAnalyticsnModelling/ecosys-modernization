## Round 8 (2026-09-21): the `ICHKV` proactive-subdivision mechanism, implemented and validated -- genuinely new, distinct from round 7's declined experiment and from issue-068's declined Newton/Anderson acceptance-logic changes

**Scope note, stated explicitly per this round's own instructions**: prior rounds (round 7 above; issue-068's tenth/eleventh rounds) explicitly declined to (a) extend `recovery_substep_counts` past its current `[1,2,4,8,16,20,32,64]`, or (b) touch any acceptance/damping/Newton-Anderson logic inside `phase_solver.zig`/`solver_solve.zig`, deferring both to a human reviewer. This round does neither: it does not add a rung to the ladder and does not touch any acceptance/damping/Newton logic. It implements a different, narrower mechanism -- choosing a DIFFERENT STARTING POINT already inside the existing, already-tested ladder, based on a proactive (before-the-attempt) check, mirroring exactly what `wthr.f:568-571`'s `ICHKV` does in the oracle.

### Mechanism

`wthr.f:568-571`: `IF(VHCP(NU(NY,NX),NY,NX).LT.4.19E-03*AREA(3,NU(NY,NX),NY,NX))ICHKV=1`, and `wthr.f:589-601`: when `ICHKV=1`, `NFH=4`/`NPH=MAX(20,NPX)` for the WHOLE hour, decided before `soil.f` ever calls `HOUR1`/`WATSUB` for that hour -- proactive, not a retry-after-failure. This differs from `heat_flux.minimum_layer_heat_capacity_megajoules_per_m2_k` (`starts.f:655`'s `VHCPRX=8.380E-05*AREA`, already used reactively by `validatePerLayerSpatialHeatClosure`/`residualAtImpl`/`temperatureForCellEnthalpy`) -- a different, ~50x larger constant, confirmed by direct source read; the two are not interchangeable.

Implemented as `ichkvTopLayerHeatCapacityBelowThreshold` (`ecosys-ng/src/soil/water/heat_step.zig`), a pure, allocation-free query computing each top soil layer's current heat capacity (`dry_solid_heat_capacity_megajoules_per_m3_k*layer_volume_m3 + liquid_water_heat_capacity_megajoules_per_m3_k*(matrix+macropore+vapor) + ice_heat_capacity_megajoules_per_m3_k*(matrix+macropore ice)`, the same formula shape as the existing `refreshExtensiveHeatCapacity`/`temperatureForCellEnthalpy` negligible-capacity check) against the new `ichkv_top_layer_heat_capacity_threshold_megajoules_per_m2_k = 4.19e-3` constant, scaled by that layer's plan area. `dry_solid_heat_capacity_megajoules_per_m3_k`/`layer_volume_m3` are read from `context.soil_thermal`/`context.soil_solver_properties` (slow-changing, erosion/relayering-only material/geometry properties `runtime_material_refresh.refreshAcceptedHour` keeps current as of the end of the previous accepted hour); the water/ice terms are read directly from `context.grid`, which is always current -- so the check is exact for the hour's TRUE starting state, not a one-hour-stale approximation from a cached workspace array.

`hourly_heat_water_solute.zig`'s `boundedInitialRecoverySubstepCount` (the exact point identified by this round's own instructions as "where a new hour's WATSUB stage begins and currently defaults to `substep_count=1`") now takes a third parameter, `ichkv_proactive_floor_active: bool`, computed once per hour in `solveSoilHeatWaterAndSoluteTransport` and threaded through `recoverFixedExternalHourAdaptively` to the FIRST attempt's substep-count selection only (subsequent escalation attempts within the same hour are unaffected, since they already go through the separate, untouched `boundedRecoveryFallback` chain). When active, it floors the requested count to `stiff_heat_direct_recovery_substeps` (=20, exactly `NFH x` Fortran's `NPH>=20` baseline for this condition, and already a member of the existing ladder). When inactive -- the overwhelming majority of hours -- `requested` is untouched, so the returned substep count is bit-for-bit whatever it would have been before this change.
