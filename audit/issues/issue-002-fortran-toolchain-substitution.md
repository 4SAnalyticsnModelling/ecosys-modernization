Scientific/output impact: `-r8` promotes every `REAL` declaration to 8-byte (double) precision at compile time, and `-i4` fixes default `INTEGER` to 4 bytes; `-align dcommons` affects COMMON block memory layout/padding. gfortran's nearest equivalents are `-fdefault-real-8 -fdefault-double-8` (real/double promotion) and `-fno-align-commons`/default alignment behavior, which are not guaranteed bit-identical to ifort's `-align dcommons`. Any precision or common-block-layout-sensitive legacy behavior (e.g. EQUIVALENCE tricks, uninitialized COMMON reads) could differ between an ifort-built oracle and a gfortran-built substitute. The existing `f77example` run deck already contains prior legacy reference outputs (`*.bin` state files, `f25ch1`/`f25eh1`/`f25nh1`/`f25wh1`/`f25wd1` hourly outputs, `restart.manifest`, `runottawa_resume_validation`) -- these are almost certainly the original ifort-produced reference, not something regenerated with gfortran, and per contract they must be preserved as-is and not overwritten.

## CORRECTION (2026-09-18, same session): the original hypothesis above is FALSE -- `f77example` contains NO Fortran reference output at all

A dedicated read-only investigation (fresh fork, no prior context) checked the actual bytes and provenance of every file this issue's original hypothesis relied on:

1. **`ecosys.x` (the compiled legacy binary `runottawa` pipes stdin into) does not exist anywhere in this checkout.** Recursive search across all of `D:\ecosys-modernization` returned zero hits. Combined with ifort/icc being absent (confirmed above), **no legacy Fortran run has ever been executed from this folder on this machine** -- there is no toolchain and no binary to run it with, so it is not possible for this checkout's `f77example` folder to contain a genuine ifort-produced run.
2. **The `NNN.*.bin` checkpoint files (`239.grid_and_plants.bin`, etc.) are confirmed Zig artifacts, not Fortran output.** Byte-level inspection: the first 8 bytes of `239.grid_and_plants.bin` are the ASCII magic string `ECOSCPST`, an exact match to `ecosys-ng/src/io/checkpoint/checkpoint.zig:10`'s `const coupled_magic = "ECOSCPST"`. File sizes are byte-identical across every checkpoint hour for a given category (typical of a fixed-layout Zig struct dump, not evolving legacy output). All `.bin` files are dated 2026-07-26, six days after the rest of the folder's input decks (2026-07-20) -- they were generated by an ecosys-ng (Zig) run and later placed into this legacy example folder, not shipped as part of any original Fortran example package.
3. **`f25ch1`/`f25wh1`/`f25nh1`/`f25eh1`/`f25cd1`/`f25wd1`/`f25nd1`/`f25pd1`/`f25ed1` are confirmed static input control-card templates, never overwritten with output.** `runottawa`'s stdin deck references each of these same nine filenames identically across all six simulated years (1998-2003) -- a real run would overwrite these as output after each year and feed the previous year's output back in; instead the exact same filename appears unchanged six times. Direct content check: each file is only ~102 lines / 330-480 bytes of `YES`/`NO` flags and short numeric control codes -- not the many-thousands-of-lines multi-year hourly/daily time series a real run would produce.
4. **`runottawa_resume_validation`/`f25y98_resume_validation` are input-side resume-testing scaffolding**, not comparison/validation output artifacts, and (per point 1) could never have been exercised by a legacy binary that doesn't exist here.

**Verdict: no genuine frozen legacy-Fortran reference output exists anywhere in this checkout.** `f77example` contains only unfilled legacy input templates/control cards, legitimate legacy input forcing/parameter data (`gbf*h` weather files, crop parameter files), and misplaced Zig checkpoint bundles. **This means output comparison against a Fortran oracle (`PROJECT_CONTRACT.md`'s G3/G4 requirement, and the user's own "outputs comparable to oracle" success criterion) is not currently possible from this checkout's shipped files at all** -- this is a more fundamental blocker for that specific criterion than even `issue-015`'s stiff-solver frontier, since even a fully-converging production run would have nothing genuine to compare against yet.
