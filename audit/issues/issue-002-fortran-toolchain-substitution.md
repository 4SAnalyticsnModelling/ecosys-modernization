Any precision or common-block-layout-sensitive legacy behavior (e.g. EQUIVALENCE tricks, uninitialized COMMON reads) could differ between an ifort-built oracle and a gfortran-built substitute. ## CORRECTION (2026-09-18, same session): the original hypothesis above is FALSE -- `f77example` contains NO Fortran reference output at all

A dedicated read-only investigation (fresh fork, no prior context) checked the actual bytes and provenance of every file this issue's original hypothesis relied on:

1. **`ecosys.x` (the compiled legacy binary `runottawa` pipes stdin into) does not exist anywhere in this checkout.** Recursive search across all of `D:\ecosys-modernization` returned zero hits. Combined with ifort/icc being absent (confirmed above), **no legacy Fortran run has ever been executed from this folder on this machine** -- there is no toolchain and no binary to run it with, so it is not possible for this checkout's `f77example` folder to contain a genuine ifort-produced run.
2. **The `NNN.*.bin` checkpoint files (`239.grid_and_plants.bin`, etc.) are confirmed Zig artifacts, not Fortran output.** Byte-level inspection: the first 8 bytes of `239.grid_and_plants.bin` are the ASCII magic string `ECOSCPST`, an exact match to `ecosys-ng/src/io/checkpoint/checkpoint.zig:10`'s `const coupled_magic = "ECOSCPST"`. File sizes are byte-identical across every checkpoint hour for a given category (typical of a fixed-layout Zig struct dump, not evolving legacy output). All `.bin` files are dated 2026-07-26, six days after the rest of the folder's input decks (2026-07-20) -- they were generated by an ecosys-ng (Zig) run and later placed into this legacy example folder, not shipped as part of any original Fortran example package.
3. **`f25ch1`/`f25wh1`/`f25nh1`/`f25eh1`/`f25cd1`/`f25wd1`/`f25nd1`/`f25pd1`/`f25ed1` are confirmed static input control-card templates, never overwritten with output.** `runottawa`'s stdin deck references each of these same nine filenames identically across all six simulated years (1998-2003) -- a real run would overwrite these as output after each year and feed the previous year's output back in; instead the exact same filename appears unchanged six times. Direct content check: each file is only ~102 lines / 330-480 bytes of `YES`/`NO` flags and short numeric control codes -- not the many-thousands-of-lines multi-year hourly/daily time series a real run would produce.
4. **`runottawa_resume_validation`/`f25y98_resume_validation` are input-side resume-testing scaffolding**, not comparison/validation output artifacts, and (per point 1) could never have been exercised by a legacy binary that doesn't exist here.

**Verdict: no genuine frozen legacy-Fortran reference output exists anywhere in this checkout.** `f77example` contains only unfilled legacy input templates/control cards, legitimate legacy input forcing/parameter data (`gbf*h` weather files, crop parameter files), and misplaced Zig checkpoint bundles. **This means output comparison against a Fortran oracle (`PROJECT_CONTRACT.md`'s G3/G4 requirement, and the user's own "outputs comparable to oracle" success criterion) is not currently possible from this checkout's shipped files at all** -- this is a more fundamental blocker for that specific criterion than even `issue-015`'s stiff-solver frontier, since even a fully-converging production run would have nothing genuine to compare against yet.

**This also corrects a stale claim carried in this session's own auto-memory** (`project_ecosys_ng_audit.md`, "treat f77example's shipped hourly/daily/.bin outputs as the frozen ifort-built reference; do not regenerate them casually") -- that memory entry should be corrected or removed; do not act on it further without re-verifying.

## Follow-up (2026-09-18, same session, user-directed check): the OneDrive reference project proves gfortran CAN produce a usable oracle run

Per the user's direct instruction, checked (read-only) whether the OneDrive mature reference project has a genuine legacy Fortran run. **It does.** `C:\Users\...\OneDrive...\ecosys_modernization\validation\legacy_ottawa_gfortran_16_1\ottawa_run\ecosys.x` (38,971,210 bytes, SHA-256 `C17182F95CFD442AEF5FB4F3A5F48B0F3D6CAB1AF577ECD2D577E0ECE534EB90`) is a real compiled binary -- built with gfortran 16.1.0 (MinGW-W64), the same substitute compiler available on this machine, explicitly because "GNU compilation cannot establish bitwise equivalence to the historical Intel toolchain" (per that folder's own `PROVENANCE.md`). It produced genuine multi-thousand-row hourly text output -- `01998f25ch1` (2,296,568 bytes, verified: plain ASCII fixed-width text starting `DOY DATE HOUR SOIL_CO2_FLUX...`, no Zig-checkpoint magic, 6,876 lines) and similar-sized siblings for water/nitrogen/energy streams.

**This proves the technical path is viable on this exact machine/toolchain** -- a gfortran build of this codebase can run and produce real output, contradicting nothing in this issue's original toolchain-precision concern (still open, still needs documented flag-equivalence) but confirming it is not a blocking obstacle to getting *some* usable oracle.

**Important caveats, directly from their own documentation** (`golden_comparison_ottawa.md`): their reference run is explicitly "a partial derived comparison artifact; not a trusted historical baseline" -- inputs were partially reconstructed (not a pristine legacy snapshot), the run terminated externally partway through day 286 with no Fortran error recorded, and it cannot prove bitwise state equivalence to the historical Intel build. Their own comparison against the Zig side covers only ~24 hours of day 1 (their Zig side also dies early, on an unrelated heat-closure bug) -- **no full-year comparison exists or is claimed anywhere in their docs.** Daily-cadence output streams were never compared (`modern_missing`), and the `visual` output family has no legacy counterpart at all (all 9 `WRITE` statements are commented out in the legacy `visual.f` itself) -- tagged `DISC-OUTPUT-VISUAL-NOT-EMITTED` in their register.

**Implication for this `D:` checkout**: do not copy OneDrive's specific reference run wholesale (it's their artifact, tied to their exact reconstructed inputs and commit state) -- instead, attempt the same gfortran-build approach independently against **this checkout's own** `f77src`/`f77example`, following their documented methodology as a lesson (not a source to copy), producing a properly-provenanced reference run of our own. Given even the mature project's oracle is admittedly partial/degraded, expectations for what this unlocks should be calibrated accordingly -- this gets us *a* usable comparison baseline, not a gold-standard one.
