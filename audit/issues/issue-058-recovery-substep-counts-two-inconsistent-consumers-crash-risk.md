## Failure signature and first bad time/location/process

During issue-024 round 7's experiment (temporarily adding `80` to `recovery_substep_counts` at `ecosys-ng/src/soil/water/heat_step.zig:483` and raising `minimum_freeze_flow_coupling_substeps` from `4` to `80` at `ecosys-ng/src/soil/water/heat_step.zig:954`, both reverted before that pass finished), the rebuilt production binary (`zig build -Doptimize=ReleaseFast`, Zig 0.16.0) crashed with `STATUS_ACCESS_VIOLATION` (exit code `-1073741819` / `0xC0000005`) partway through simulated hour 1 of the Ottawa deck, after emitting exactly 65 of an intended 80 `MATRIC_TRACE024 hour=1` substep-trace lines. No accepted hour-1 state was ever reached; no Zig panic message or stack trace was emitted -- the log simply stops. Reproduced twice (both runs exited on their own with the same code, well inside a 10-minute wall-clock budget). Full reproduction detail, log excerpts, and the before/after ice-conversion numbers are recorded in `issue-024`'s "## Round 7", Experiments 14-15; not duplicated verbatim here.

## Independent re-verification (this pass, current source, read-only)

Re-read both consumers side by side at their current line numbers (no drift found since round 7 -- the array and both files are exactly where round 7 left them, confirming the revert was clean):

**Consumer 1 -- `ecosys-ng/src/soil/water/heat_step.zig`, fully array-driven:**
- `:483` -- `pub const recovery_substep_counts = [_]u8{ 1, 2, 4, 8, 16, 20, 32, 64 };`
- `:621-625` -- when an exact substep count is requested (test-only hook), validates membership by a linear scan of `recovery_substep_counts` itself.
- `:649` -- `for (recovery_substep_counts) |substep_count| { ... }`, the actual escalation ladder that `advanceMappedDeferred` walks, restoring full state and retrying at each array member in ascending order until one schedule completes without a retryable failure.
- `:954` -- `pub const minimum_freeze_flow_coupling_substeps: u8 = 4;`, a separate floor constant (not itself part of the array) consumed both here (`:761-763`, forces a retry whenever an accepted substep count is below this floor and ice changed significantly) and by consumer 2 below.

This consumer reads `recovery_substep_counts` directly for its escalation sequence; extending the array alone changes consumer 1's behavior correctly and automatically.

**Consumer 2 -- `ecosys-ng/src/stages/hourly_heat_water_solute.zig`, partially hardcoded:**
- `:11320-11322` -- three independent named constants: `stiff_heat_direct_recovery_substeps: u8 = 20`, `secondary_bounded_recovery_substeps: u8 = 32`, `maximum_bounded_recovery_substeps: u8 = 64`.
- `:11326-11337` -- `boundedRecoveryFallback(attempted_substep_count: u8) ?u8`, the stage-level controller's error-aware escalation-on-failure chain. Its body is a plain `if`/`else if` chain over the three named constants above; it **never reads or references `recovery_substep_counts`** at all. It returns `null` once `attempted_substep_count >= maximum_bounded_recovery_substeps` (i.e. its ceiling is hardcoded at `64`, independent of whatever the array's actual current maximum is).
- By contrast, two *sibling* functions in the same file **do** correctly consult the array: `boundedInitialRecoverySubstepCount` (`:11339-11352`) validates its candidate against `recovery_substep_counts` via a linear scan, and `nextCoarserRecoverySubstepCount` (`:11354-11361`) scans the same array to step down one rung on a clean/cooldown hour. **Only `boundedRecoveryFallback`'s upward, error-driven escalation chain is hardcoded** -- this is a more precise characterization than round 7's summary ("a hardcoded three-tier chain entirely independent of the array"), which is correct about `boundedRecoveryFallback` specifically but could be read as describing the whole file.
- `:11415-11421` (`recordFreezeFlowRequirement`) and `:11490-11496` (the floor-clamp inside `recoverFixedExternalHourAdaptively`) are the mechanism that let round 7's experiment reach `80` at all: once a `HeatInducedPhaseChangeRequiresQuarterHourSubsteps` error sets `freeze_flow_coupling_floor_active`, the next requested substep count is `@max(boundedRecoveryFallback(substep_count) orelse ..., ecosys.soil_water_heat_step.minimum_freeze_flow_coupling_substeps)` -- this reads `minimum_freeze_flow_coupling_substeps` directly from `heat_step.zig` (a genuinely shared constant), so raising that floor to `80` overrides `boundedRecoveryFallback(1)=20` with `max(20, 80)=80` in a single step, bypassing `boundedRecoveryFallback`'s own chain and ceiling entirely. `boundedInitialRecoverySubstepCount`'s array-membership check (`:11349-11351`) then accepts `80` because round 7 had also added `80` to the array itself -- both edits were necessary, matching round 7's Experiment 14 finding exactly.

**Confirmed: no synchronization mechanism exists.** Searched for a shared constant, `comptime` assertion, or test that would fail if `recovery_substep_counts` were extended without a matching update to `hourly_heat_water_solute.zig`'s three named constants:
- No `comptime` assertion or shared constant ties `maximum_bounded_recovery_substeps`/`secondary_bounded_recovery_substeps`/`stiff_heat_direct_recovery_substeps` to `recovery_substep_counts`'s contents; grepping both files for these three constant names finds only their own declaration, `boundedRecoveryFallback`'s body, `boundedInitialRecoverySubstepCount`'s clamp, and their own unit tests (`hourly_heat_water_solute.zig:9690-9696,9986,10003,10006,10013`) -- all of which use the literal values `20`/`32`/`64`, not a derived reference to the array.
- The one existing test that iterates the array itself (`"accepted schedule duration uses bounded floating point accumulation"`, `:9700-9712`) only checks a generic duration invariant (`sum of 1/n over n substeps == 1 hour`) for every array member -- it would pass unchanged if `80` were added to the array, because it does not touch `boundedRecoveryFallback` at all.
- The tests that do exercise `boundedRecoveryFallback`'s escalation chain (`:9813-9851`, `:9853-9883`) hardcode their expected schedules as literal arrays (`&.{16, 20, 32}`, `&.{16, 20, 32, 64}`), not derived from `recovery_substep_counts.len` or its contents -- so none of them would fail if the production array were extended to `{..., 64, 80}` while `hourly_heat_water_solute.zig` was left untouched.

**Conclusion of independent verification: round 7's finding is confirmed, precisely.** The two consumers are genuinely independent for the escalation-on-failure path specifically (`boundedRecoveryFallback` vs. `heat_step.zig`'s array walk), are not kept in sync by any compile-time or test mechanism, and the specific combination that crashed (extending the array *and* raising the floor past the hardcoded chain's ceiling) is exactly what is needed to expose the inconsistency -- not refuted, not superficial.

## Reachability/severity assessment for current production Ottawa deck (new in this pass)

**Not reachable today under the presently committed source, for any input deck.** Under the code as currently committed (`recovery_substep_counts` capped at `64`; `minimum_freeze_flow_coupling_substeps = 4`):
- `heat_step.zig`'s array walk (consumer 1) never proposes a substep count above `64`, because `64` is the array's own last/largest member.
- `hourly_heat_water_solute.zig`'s floor-clamp can only push a request up to `minimum_freeze_flow_coupling_substeps = 4`, which is already below `boundedRecoveryFallback`'s first tier (`20`) and therefore never overrides it -- the clamp is a no-op for escalation purposes at its current value.
- `boundedRecoveryFallback`'s own hardcoded ceiling (`64`) coincides exactly with the array's actual current maximum (`64`), so no legitimate production escalation sequence can ever request a value the array doesn't have, or that `boundedRecoveryFallback` doesn't know how to escalate to.

This means the crash is **dormant, not latent-but-creeping** -- it cannot be triggered by any weather forcing, deck configuration, or organic solver escalation under today's committed constants; it requires a source edit that reintroduces the specific mismatch (extending `recovery_substep_counts` past `64`, or raising `minimum_freeze_flow_coupling_substeps` above `64`, without a corresponding update to the three named constants in `hourly_heat_water_solute.zig`). This is the "always-dormant unless someone else makes a similar forced-value mistake" case, not "reachable under normal production escalation, just not yet hit." However, this dormant state is fragile: it depends entirely on a human remembering to keep two files' hardcoded values in step by convention, with no compiler or test enforcement -- and the project's own history (below) shows that exact reminder has already failed twice.

## Relationship to `SOLUTE-HYDROGEN-ROW-RECURRING-NONCONVERGENCE-001`

Read the tag's context at `hourly_heat_water_solute.zig:9813-9822` and `:9853-9861` (test comments) and `audit/features/feature-003-newton-raphson-anderson-solute-reaction-solver.md:29`. Both are genuinely the **same class of defect** as this issue, not merely superficially similar, and both are specifically about `boundedRecoveryFallback`/the escalation chain lagging `recovery_substep_counts`'s true contents:
- **Hour 2,571** (real, unforced production run): the *previous* implementation of the fallback logic made "at most one error-aware fallback," so a preferred schedule that wasn't already `20` could reach `20` but never escalate further to the `32`-step rescue that the array already declared as available. - **Hour 2,604** (real, unforced production run, 33 hours later): the *fixed* chain's ceiling was itself hardcoded one rung short (`32`) of `recovery_substep_counts`'s actual declared maximum (`64`) at the time, so a genuinely harder hour that needed `64` substeps still failed. Fixed by adding the third named constant/tier (`maximum_bounded_recovery_substeps = 64`).

Both historical fixes **manually re-synchronized the hardcoded chain to match the array's contents at that moment** -- neither one changed `boundedRecoveryFallback` to read the array directly, so the underlying two-representations design gap was never closed, only re-aligned by hand. The regression tests added for both incidents (`:9813-9851`, `:9853-9883`) pin today's specific values (`20`/`32`/`64`) and would catch a *third* manual value-alignment slip only by coincidence, not by construction -- as demonstrated directly by this pass's confirmation (above) that extending the array alone triggers no test failure. **This issue's finding is therefore not covered or mitigated by the existing `SOLUTE-HYDROGEN-ROW-RECURRING-NONCONVERGENCE-001` tests; it is the same recurring design gap manifesting a third time**, this time discovered via a deliberate diagnostic experiment rather than an organic production failure, and this time producing a hard crash (access violation) rather than a suboptimal/failed recovery -- a more severe failure mode than either prior incident, because a future recurrence is not guaranteed to be caught by any existing test before it reaches a production run.

## Disposition

Cause: **confirmed, independently re-verified this pass.** `recovery_substep_counts` (`heat_step.zig:483`) has two consumers for the upward escalation-on-failure path: `heat_step.zig`'s own array-driven ladder (`:649`), which is correct and automatically stays in sync with the array; and `hourly_heat_water_solute.zig`'s `boundedRecoveryFallback` (`:11326-11337`), which is a hardcoded three-tier chain (`20`/`32`/`64` via named constants at `:11320-11322`) that never reads the array and has no mechanism (shared constant, compile-time assertion, or test) forcing it to stay in step with the array's actual contents. A separate shared floor constant, `minimum_freeze_flow_coupling_substeps` (`heat_step.zig:954`), can override `boundedRecoveryFallback`'s result via a `@max` clamp (`hourly_heat_water_solute.zig:11490-11496`), and it was exactly this combination -- array extended to include `80`, floor raised to `80` -- that let issue-024 round 7's experiment reach a substep count `boundedRecoveryFallback` itself would never have proposed, crashing the binary.

Reachability: **not reachable under the presently committed source for any current production deck or input** (see assessment above) -- the array's current maximum (`64`) and `boundedRecoveryFallback`'s hardcoded ceiling (`64`) coincide today, and the floor constant (`4`) is far below any tier where the mismatch would matter. This is a dormant, review-worthy design gap, not an active production risk as committed right now.

Prior coverage: **not already covered or mitigated** by `SOLUTE-HYDROGEN-ROW-RECURRING-NONCONVERGENCE-001`'s existing tests, which pin today's specific hardcoded values but do not guard against a future re-drift of the same shape -- this is the same recurring design gap (two independent, manually-synchronized representations of the same schedule) reproduced a third time, this time as a crash rather than a suboptimal/failed recovery.

Two design options exist, both requiring dedicated review and testing across many hours/layers before being adopted, and this issue does not decide between them:
1. Make `boundedRecoveryFallback` (and its floor-clamp interaction) read `recovery_substep_counts` directly -- e.g. via `nextCoarserRecoverySubstepCount`-style array lookups -- so extending the array automatically and correctly extends the escalation chain, eliminating the two-representations gap structurally. (This is the fix direction issue-024 round 7 itself suggested as a prerequisite for its own candidate-2 comparison; it is a plausible recommendation but is **not** decided here.)
2. Treat `recovery_substep_counts` as authoritative only for `heat_step.zig`'s own internal ladder walk, and treat `hourly_heat_water_solute.zig`'s three named constants as an intentionally separate, independently-reviewed stage-level policy -- in which case the array and the stage-level chain should be decoupled explicitly (e.g. the array should not silently accept a value beyond what the stage-level chain can request, via a `comptime` bound or a validated maximum), so a future array extension fails loudly at compile time or first use rather than silently working until a rare escalation path exposes the gap.
Either direction needs its own reviewed, regression-tested change; this issue's job is to record the confirmed defect, its current (dormant) reachability, and its relationship to the prior tagged incidents -- not to choose between them.

## Fix applied (2026-09-19, this pass)

Implements design option 1 from the "Disposition" section above (`boundedRecoveryFallback` reads `recovery_substep_counts` directly), per this pass's explicit instruction to close the recurring design gap structurally rather than re-synchronize hardcoded values by hand a third time. **Does not touch `recovery_substep_counts`'s production values** (still `[1, 2, 4, 8, 16, 20, 32, 64]`) -- extending the ceiling itself remains out of scope, reserved for a dedicated `issue-015` decision.

Source changes:
- `ecosys-ng/src/soil/water/heat_step.zig`: added `pub fn isRecoverySubstepCountMember(value: u8) bool` (linear-scans `recovery_substep_counts`) and a `comptime` block asserting `minimum_freeze_flow_coupling_substeps` is a member of the ladder -- a future edit that raises this floor above the ladder's true maximum (the other half of issue-024 round 7's reproduction, alongside extending the array) now fails to compile instead of crashing.
- `ecosys-ng/src/stages/hourly_heat_water_solute.zig`:
  - `maximum_bounded_recovery_substeps` is now computed from `recovery_substep_counts[recovery_substep_counts.len - 1]` instead of hardcoded as a literal `64`.
  - Removed `secondary_bounded_recovery_substeps` (the hardcoded `32` literal); no longer needed.
  - Added a `comptime` block asserting `stiff_heat_direct_recovery_substeps` (the rescue chain's floor, `20`) is a member of `recovery_substep_counts`, via the new shared `isRecoverySubstepCountMember`.
  - Added `fallbackWithinLadder(ladder: []const u8, floor: u8, attempted_substep_count: u8) ?u8`: returns the smallest `ladder` member that is both `>= floor` and `> attempted_substep_count`, or `null`. `boundedRecoveryFallback` is now a one-line delegation to `fallbackWithinLadder(&recovery_substep_counts, stiff_heat_direct_recovery_substeps, attempted_substep_count)`, replacing the old three-branch `if`/`else if` chain over hardcoded literals. This is the actual fix: extending `recovery_substep_counts` now extends this chain automatically and correctly.

Before/after equivalence evidence (zero behavior change at today's committed values): added test `"boundedRecoveryFallback matches the old hardcoded 20/32/64 chain across the full u8 domain (before/after equivalence, issue-058)"` (`hourly_heat_water_solute.zig`), which re-derives the exact pre-fix `if (a<20) 20 else if (a<32) 32 else if (a<64) 64 else null` formula as an independent literal (not calling any shared code) and checks it against the new implementation for every value `0..255`, not merely today's reachable array members. All existing pre-fix regression tests for this function and its callers (`"bounded recovery chooses only deliberate fallback schedules"`, the two `SOLUTE-HYDROGEN-ROW-RECURRING-NONCONVERGENCE-001` tests at hour-2,571/2,604 shape, `"adaptive fixed-hour recovery ..."` x4, `"fixed external hour recovery ..."` x2) also pass unchanged.

Extensibility evidence (proves the fix, not just preservation): added test `"fallbackWithinLadder escalates to a new tier beyond today's committed maximum (extensibility, issue-058)"`, which builds a local-only ladder `[1,2,4,8,16,20,32,64,128]` (production array untouched) and confirms `fallbackWithinLadder` escalates `64 -> 128` and returns `null` only at `128` -- the exact scenario that previously required editing three hardcoded literals in lockstep and, when done incorrectly (as issue-024 round 7 demonstrated), crashed with `STATUS_ACCESS_VIOLATION`.

Regression-guard evidence for the new comptime assertions: added test `"isRecoverySubstepCountMember distinguishes true ladder rungs from drifted values (guards issue-058 comptime assertions)"`, pinning the exact membership predicate both new `comptime` guards depend on against known members (`1,2,4,8,16,20,32,64`) and known non-members (`0,3,5,17,21,63,65,80,128,255`). A `@compileError` itself cannot be asserted at runtime, but a future weakening of this shared predicate (e.g. an accidental always-true implementation) would be caught here before it could silently disable both guards.
