## Fix implemented and committed (2026-09-19, same day, follow-up pass)

Follow-up to the "Iteration-budget confound closed" section immediately above, doing exactly what its recommendation asked for: a reviewed, regression-tested source change, plus a real (not two-hour-isolated) production replay to validate it, plus a decision on committing.

### Part 1 -- diagnosis and chosen fix

Read `reaction_solve.zig:905-990`'s full two-phase split (`solveCellWithWorkspaceAndTrace`, now `solveCellWithWorkspaceAndTraceUsing` after this pass's refactor) end to end. There is no comment or design rationale anywhere in the file for "phase 2 gets whatever phase 1 didn't use"; `git log --oneline -- ecosys-ng/src/soil/solute/reaction_solve.zig` shows exactly one commit for this repository (`514dd68`, the initial import), so there is no blame history to consult either -- this reads as an unexamined implementation default, not a deliberate, documented design choice.

Checked the Fortran oracle's equivalent ceiling: `f77src/solute.f:111`, `PARAMETER (MRXN=60)`. Read the full `DO 1000 M=1,MRXN` loop (`solute.f:822-2712`): Fortran runs **one** fixed-point loop, up to 60 times, that performs equilibrium reset (`:824-862`) and precipitation-dissolution kinetics (`:2454` "COMPLETE ITERATION WITH PRECIPITATION-DISSOLUTION REACTIONS") together in every single iteration. There is no analog of "solve equilibrium to convergence, then separately solve a post-kinetic equilibrium with whatever budget is left" -- that two-closure split is a Zig-native structural choice (arguably a better-conditioned one, sequencing a Newton/Anderson solve before and after the kinetic step rather than one coupled fixed-point sweep), but it means Fortran's `MRXN=60` was never calibrated for "one shared ceiling split unevenly across two sequential nonlinear solves." **60 was not an undersized translation of Fortran's own number for this specific shape; it was a faithful translation of a number that does not describe this shape at all.**

Chosen fix, in two complementary parts (both smaller than the diagnostic's ad hoc `200`/`300` and both justified from existing evidence/precedent rather than a fresh guess):

1. **(Option (b) from the task) Independent per-phase budgets.** `reaction_solve.zig`'s post-kinetic closure now receives `options.max_iterations` directly instead of `options.max_iterations - first.iterations`. This removes the "second phase pays for whatever the first phase happened to spend" shape unconditionally -- for any case where kinetics genuinely is the bottleneck (this session's earlier 128-substep observation: `newton_steps=3 picard_steps=1` for the second closure vs. `newton_steps=36 picard_steps=24` for the first), the second closure is no longer starved by construction. To keep this testable and reviewable, `solveCellWithWorkspaceAndTrace` was split into a thin public wrapper plus an injectable `solveCellWithWorkspaceAndTraceUsing(comptime equilibrium_solve: anytype, ...)`, mirroring the file's existing `solveEquilibriumWithAttempt`/`ScriptedRetryAttempt` pattern.
2. **(Option (a) from the task, and empirically the one that actually mattered here) Raise `solute_reaction_max_iterations`'s policy floor from a flat `60` to `100`** (`iteration_control.zig:38-70,131`), matching -- not inventing -- the floor-of-100 policy this project already applies to `organic_transport_max_iterations`, `water_heat_solute_max_iterations`, and `gas_max_iterations` in the same file, each with the same documented rationale ("if a real deck cannot converge within the floor, that is a residual-scaling defect to fix there, not a reason to raise the number again"). `100` was chosen over the diagnostic's `200` specifically because `100` is exactly the Ottawa deck's own committed `runtime` record ceiling (`max_nonlinear_iterations=100`, `runottawa:6`) -- every `Limits` field in this file is clamped via `@min(hard_max_iterations, X)`, so `100` is the largest value that has any effect for this specific deck without also changing a protected production input. `200` would silently no-op for this deck (clamped straight back to `100`) unless the deck's own runtime record were also edited, which this source-only pass treats as a config/scope decision outside its authority, not a translation defect to fix unilaterally.

Both changes are minimal, reuse existing project precedent for the exact number chosen, and do not touch the deck's own explicit ceiling or introduce an unbounded "grind" budget -- a genuinely non-convergent cell still fails deterministically within a bounded, evidence-based budget.
