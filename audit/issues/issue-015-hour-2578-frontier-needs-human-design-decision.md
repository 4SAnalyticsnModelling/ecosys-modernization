Status: **OPEN, REFRAMED.** This is the single blocker preventing "production run completes to the end" as of 2026-09-18. Per contract's diagnosis-budget rule ("three distinct hypothesis-driven experiments before a fresh reviewer/reframing"), this issue is being reframed now rather than continuing to spend the budget on further guesses, since the two completed experiments and one inconclusive check give no actionable lead.

## Summary

The Ottawa deck's first-ever production run in this `D:` checkout (`run-001`, see `audit/runs/run-001-ottawa-diagnostic-2026-09-18.md`) fails at **hour 2,578 of 262,920 (0.98%)** with `SoluteReactionSolverDidNotConverge` -- a stiff, simultaneous aluminum/iron/calcium-hydroxide-phosphate surface-site reaction-network disequilibrium, cell 0, layer 0, day 108. This is the same general failure class the mature reference project (read-only, OneDrive) documents extensively in its own `docs/GOAL.md`, reaching hour 2,604-2,704 across its own fix history before its maintainers concluded (after 6+ independently refuted hypotheses and an exhaustive audit of the reaction-network solver): "Hour 2,604 needs a human design decision... before further progress is possible."

## Experiments completed

1. **Named-fix presence check.** The two most obvious, specifically-named fixes from the mature project's fix history (`IRCHG` topographic downhill gate, `starts.f:274-303`; the Anderson-ladder full 8-tier retry escalation `[1,2,4,8,16,20,32,64]`) are both already correctly present and tested in this checkout. Independently confirmed by TWO different methods: (a) this session traced the actual test coverage in `hourly_process_driver.zig`/`heat_step.zig`; (b) peer session `ecosys-modernization-af` independently byte-hash-compared 5 named-fix files plus the solver core (`reaction_solve.zig`, `core/numerics.zig`, `reaction_solver_types.zig`, `heat_step.zig`, plus `litter_geometry.zig`, `runtime_adapter.zig`) between this `D:` checkout and the OneDrive reference -- all byte-identical. **Result: no missing fix found. The solver and named fixes are confirmed identical to the more mature checkout.**

2. **Geochemistry-kinetics rate-ceiling swap hypothesis.** A targeted trace found a real, independently-verified citation mismatch: `solute.f:112-113`'s two rate ceilings (`TPDH=2.5e-3`, `TPZH=2.5e-2`, a 10x difference) are assigned to species in the production parameter file backwards relative to their use in `solute.f:2474,2494,2517,2540` (gibbsite/Fe(OH)3/calcite should get the larger `TPZH`-derived ceiling; gypsum alone should get the smaller `TPDH`-derived one; the parameter file has this swapped). **Tested properly** (isolated copy only, after catching and reverting an accidental direct edit to the tracked production deck): the fix made the frontier **worse** (hour 2,568, run-002) with a **different** failure mode (`NegativePhosphateNetworkState` on dissolved H2PO4, not the original aqueous-hydroxide/aluminum signature). **Result: REFUTED.** The citation mismatch is real, but correcting it in isolation does not help -- something elsewhere either compensates for it or interacts with it in a way a single-field swap doesn't capture. No fix applied to the tracked deck.

3. **`soil.f` call-order check.** `soil.f` is pure call-order orchestration (`WTHR->HOUR1->WATSUB->NITRO->HFUNC->UPTAKE->GROSUB->EXTRACT->SOLUTE->TRNSFR->TRNSFRS->EROSION->REDIST`). A peer session's first attempt, tracing `ecosys_ng.zig` directly, was inconclusive (too large/unstructured). **A follow-up, more targeted check reached a definitive result**: by reading `stages/hourly_process_driver.zig`'s top-level orchestrating function and grepping for inline `soil.f:` line citations at each stage boundary, the Zig call order was reconstructed exactly: `WTHR -> HOUR1 -> WATSUB -> NITRO -> HFUNC -> UPTAKE -> GROSUB -> EXTRACT -> SOLUTE -> TRNSFR -> TRNSFRS -> EROSION/REDIST` (the last two merged into one `ProductionPhase.erosion_redist` call; one extra non-listed step, `produceCanopyStandingDeadFireBeforeSolute`, sits between EXTRACT and SOLUTE, not a discrepancy in the 11 named stages' relative order). **This exactly matches the Fortran oracle's order.** Better still, `hourly_heat_water_solute.zig:10331-10420` already contains a self-verifying regression test that asserts this exact ordering via `std.mem.indexOfPos` position comparisons on the actual production source text -- i.e., a swap would already fail CI, independent of any runtime signature. **Result: CONFIRMED, definitively ruled out** as the cause. Call order is not the explanation for the hour-2578 divergence.

4. **Phosphate-mineral TPDX/TPDA/TPDZ family (secondary lead from experiment 2's own fork report).** Checked before committing to a third live run: `ecosys-ng/src/soil/solute/phosphate_reaction_rates.zig:422-432` already correctly and explicitly documents and implements the exact same TPDX/TPDA/TPDZ distinction found in `solute.f`, including monocalcium phosphate's asymmetric dissolution-ceiling special case (its own separate `maximum_mineral_dissolution_mol_per_m3_step` field, distinct from the other four species' shared field). **Result: not a promising lead -- already correctly handled, no experiment run.**

## Reframe decision

Per contract's three-experiment discipline, and given experiment 4 above found no actionable lead without needing to spend a live run, **the diagnosis budget on this specific frontier is now considered spent.** Three clean, conclusive results (1 refuting a specific hypothesis with informative new failure-mode evidence; 2 and 3 confirming the solver/named-fixes AND the hourly call order are not the cause, the latter backed by an existing self-verifying regression test) plus one dead-end secondary lead, all independently cross-checked by two separate sessions, is a solid basis to stop guessing rather than continue an unstructured search.

**Working conclusion (not proven, but the best-supported explanation available)**: this is very likely the same fundamental stiff-convergence numerical wall the mature reference project's own maintainers already characterized and could not resolve through translation-defect-hunting, encountered somewhat earlier in this checkout (hour 2,578 vs. their 2,604-2,704) for a reason neither this session nor the peer session could pin down with a clean third experiment. It may be a genuinely undiscovered translation defect somewhere in the ~90%+ of `redist.f`/`trnsfr.f`/`trnsfrs.f`/`grosub.f` not yet depth-read, or it may be that the two checkouts have simply diverged enough elsewhere (in files neither session has compared) that a similar-magnitude starting disequilibrium behaves slightly differently. Given the solver itself and the two most-likely-relevant named fixes are proven identical, **this is not attributable to a known, fixable translation defect without new evidence.**
