## Cross-check against issue-058 (2026-09-19)

Read-only cross-check pass (no source changed, no run executed) investigating whether `issue-058`'s `recovery_substep_counts` two-consumer inconsistency (`heat_step.zig` array-driven ladder vs. `hourly_heat_water_solute.zig`'s `boundedRecoveryFallback` hardcoded chain, tag `SOLUTE-HYDROGEN-ROW-RECURRING-NONCONVERGENCE-001`, incidents at hours 2,571 and 2,604) is connected to this issue's hour-2,578 frontier.

**Verdict: CONNECTED at the mechanism level -- this is new evidence, but it does not identify a fix and does not, by itself, justify running a new experiment without first resolving `issue-058`'s design gap.** Specifically:

1. **The substep-recovery ladder does gate the SOLUTE reaction solver -- confirmed by direct code read, not inference.** `isFixedHourRecoveryFailure` (`hourly_heat_water_solute.zig:11292-11306`), the gate that decides whether `recoverFixedExternalHourAdaptively` escalates through `boundedRecoveryFallback`'s substep chain, delegates first to `ecosys.soil_water_heat_step.isFixedHourDtRecoveryFailure` (`heat_step.zig:1064-1126`), whose switch explicitly lists `error.SoluteReactionSolverDiverged/Stagnated/DidNotConverge/PhysicalBalanceFailure` (`heat_step.zig:1107-1110`) as recoverable. So a SOLUTE non-convergence is not a separate, unrelated failure to this ladder -- it is one of the exact error classes the ladder exists to retry at finer substep counts. This is independently confirmed by this checkout's own `run-001` terminal-error trace (`audit/runs/run-001-ottawa-diagnostic-2026-09-18.md:28`): the hour-2,579 failure shows `SOLUTE hourly reaction solver failed` (initial attempt) -> `exact_substep_count=32` -> escalated to `exact_substep_count=64` (the ladder's declared maximum) -> still `maximum_scaled_residual=1.16e3` (down from `2.33e5`, real but insufficient progress) -> hard failure. **Hour 2,578/2,579's failure runs through the exact same escalation machinery `issue-058` audits, and dies specifically at that ladder's current ceiling.**

2. **The hour-2,571/2,604 regression tests are genuinely about SOLUTE reaction-solver non-convergence, not a different symptom.** The fixture at `hourly_heat_water_solute.zig:9757-9811` uses the literal error `error.SoluteReactionSolverDidNotConverge` to demonstrate `isFixedHourRecoveryFailure`'s gating, and the hour-2,571/2,604 tests immediately following (`:9813-9851`, `:9853-9883`) pin the same escalation chain with comments crediting real production incidents ("32 substeps converges where 1 and 20 do not" for hour 2,571; hour 2,604 needing the true ladder maximum). Additionally, `ecosys-ng/src/soil/solute/reaction_solve.zig:1194-1215` carries a **third, still-open** regression under the same tag: `"SOLUTE-HYDROGEN-ROW-RECURRING-NONCONVERGENCE-001: hour 2561/day108-hour3 phosphate-site crawl (parent: fails)"`, captured from a real production snapshot, asserting `error.SoluteReactionSolverDidNotConverge` still occurs today when the reaction solver is invoked directly on that captured state (i.e. this is a currently-passing test only because the underlying solver-level non-convergence is *still reproduced*, not fixed). Its comment states this is "the same lime-driven pH~9.7 transient" as the tag's other incidents, and that two candidate mechanisms (rank deficiency, over-conservative damping) were tested and refuted for it elsewhere (in the mature reference project's `docs/discrepancy_register.md`, which does not exist in this `D:` checkout -- an external, read-only pointer, not resolvable here).

3. **Hour proximity is not coincidental -- it traces to the same day-108 lime event.** Using this deck's own hour numbering (`run-002`: hour 2,568 = day 107, hour 24; therefore day 108 hour *n* = hour 2568+n), the test's "day108-hour3" label is **hour 2,571** -- i.e. the *same* hour as one of the two ladder incidents already on record, not merely close to it. Hour 2,578/2,579 (this issue's frontier) is day 108, hour 10/11 -- 7-8 hours later, same day. `run-001`'s own experiment 2 (this file's "Experiments completed" section, item 2) independently traced a day-105 lime application (360 g Ca/m2 as CaCO3) as the trigger under investigation for this exact window, and `run-001`'s terminal failure signature (`limiting_name=phosphate_non_band.hydroxyl_site_mol_per_megagram`, `realized_endpoint_limiting_name=aqueous.hydroxide`/`aqueous.aluminum`) is the same aluminum/iron/calcium-hydroxide-phosphate surface-site chemistry family as `reaction_solve.zig:1194`'s "phosphate-site crawl" / "lime-driven pH~9.7 transient." Same day, same triggering event class, same chemistry family, hours apart -- this is a specific, evidenced shared-trigger match, not just adjacent hour numbers.

4. **What is NOT connected: `issue-058`'s own specific inconsistency bug is not the cause of hour 2,578 failing where it does.** `issue-058` establishes that under the presently committed source, `boundedRecoveryFallback`'s hardcoded ceiling (64) and `recovery_substep_counts`'s actual maximum (64) coincide, so the ladder behaved exactly as designed at hour 2,579 -- it escalated 20->32->64 and failed cleanly at exhaustion, not because of a mismatch bug. **Recommendation, not a decision made here**: this cross-check is the "new evidence" contemplated by this issue's closing line -- it does not overturn the three completed experiments' conclusions (named fixes present, geochemistry swap refuted, call order ruled out all stand), but it identifies a concrete, bounded fourth hypothesis that was not available before: *does convergence continue to improve past 64 substeps, once the ladder can actually reach a finer tier without crashing?* That requires, in order: (a) a reviewed fix for `issue-058` (small, regression-tested, per its own two design options), then (b) a bounded diagnostic replay of the retained hour-2,578/2,579 failure state (or a fresh capture analogous to `reaction_solve.zig`'s `testdata/ottawa_day108_hour3_layer0_20260916.b64` fixture) at one or two new tiers, measuring whether the residual keeps falling or plateaus. **Neither step is performed in this pass**, per this issue's explicit budget-exhaustion framing and this cross-check's read-only scope -- this is a candidate next experiment for whoever picks this issue up next, not a reopening of the budget by this pass.

## Substep-ladder extension experiment (2026-09-19, this pass) -- fourth hypothesis tested; inconclusive on convergence, but finds a second, distinct crash defect

Follow-up to the "Cross-check against issue-058" section above, now that `issue-058` is CLOSED/FIXED (commit `99176ab`, `boundedRecoveryFallback` genuinely array-driven). This pass ran the exact bounded diagnostic experiment that cross-check recommended: extend `recovery_substep_counts` past 64 and re-run the retained hour-2,578/2,579 frontier, to see whether the SOLUTE solver's real (non-stagnant) residual reduction at 64 substeps (`2.33e5 -> 1.16e3`, per `run-001`) continues to fall with more headroom, or plateaus.

**Setup**: uncommitted, local-only edit to `ecosys-ng/src/soil/water/heat_step.zig:483` (reverted before this pass finished; confirmed via `git status --short`/`git diff` showing zero changes at the end -- see "Disposition" below). Rebuilt with `zig build -Doptimize=ReleaseFast` (Zig 0.16.0) per this experiment's explicit instruction, not `run-001`'s `-Doptimize=ReleaseSafe` -- this is a deliberate deviation from exact reproduction, flagged here because it matters for what follows. Ran against a fresh isolated `robocopy /E` copy of the same `Cool Temperate Maize-Soybean ON` deck, same command shape as `run-001` (`ecosys_ng.exe --execution-evidence <path> runottawa`, cwd = isolated deck copy).

**Step 1 result -- the array-only extension claim holds, with one caveat and one incidental discovery**:
- First attempt used the task's own suggested example ladder, `[1,2,4,8,16,20,32,64,128,256]`. This **failed to compile**: `error: type 'u8' cannot represent integer value '256'` (`heat_step.zig:483:77`), surfaced through the new `comptime` membership guards `issue-058` added. `recovery_substep_counts` and every value derived from it (`maximum_bounded_recovery_substeps`, the two comptime-guarded floor constants) are typed `u8` throughout both files -- so **any tier at or above 256 requires widening the element type (e.g. to `u16`) everywhere it flows, which is a second, non-mechanical source change beyond the single array line, not covered by issue-058's "array is now the single source of truth" claim.** This is worth recording precisely: the claim is true for `u8`-representable tiers (up to 255) and false for tiers at or above 256 without an additional type change.
- Retried with `[1,2,4,8,16,20,32,64,128]` (one new tier, `u8`-safe). **This compiled and linked cleanly with the one-line array edit alone** -- no edit to `hourly_heat_water_solute.zig` was needed, confirming issue-058's core structural claim for `boundedRecoveryFallback`/`maximum_bounded_recovery_substeps`/`fallbackWithinLadder`, exactly as designed.
- Running the focused test filter (`zig test ... --test-filter "recovery"`) surfaced a **separate, test-only regression**, not a production one: two pre-existing tests (`"bounded recovery chooses only deliberate fallback schedules"` and `"adaptive fixed-hour recovery still terminates and reports failure when even the ladder maximum fails"`, `hourly_heat_water_solute.zig:9692`/`:9958-9979`) use a local mock fixture with a hardcoded `schedules: [4]u8` capture buffer, sized for the *old* maximum chain depth (one initial attempt plus three escalations: 20/32/64). With a fifth rung available, `recoverFixedExternalHourAdaptively` legitimately asks the mock to record a 5th attempt, and the mock itself panics: `index out of bounds: index 4, len 4` (`hourly_heat_water_solute.zig:9964`). **This is the mock fixture's own fixed-size buffer, not a production data structure** -- `recoverFixedExternalHourAdaptively`'s real escalation loop (`:11573-11614`) is a plain `while(true)` with no array-backed attempt history, confirmed by direct read. So the production code is unaffected, but **the existing test suite is not currently green against an extended ladder** and would need its mock fixtures' buffer sizes bumped (a small, mechanical, but real additional change) before this extension could be adopted with a clean `zig build test`. Did not make that test edit (out of scope for a revert-before-finishing diagnostic pass); flagged here for whoever picks this up next.

**Step 2 result -- the production run reached hour 2,579 and requested the new 128-substep tier, then the process crashed (`STATUS_ACCESS_VIOLATION`) before that attempt could resolve**:
- The run reproduced `run-001`'s frontier almost exactly: hour 2,568 accepted (last clean daily-conservation report), then SOLUTE non-convergences at day108-hour5/8/9 (hours 2,573/2,576/2,577) recovered via the same 20 -> 32 -> 64 substep escalation `run-001` showed. At hour 2,579 (day108-hour11, the **same hour** as `run-001`'s original terminal failure), the SOLUTE solver again failed to converge at 64 substeps with `maximum_scaled_residual=1.1634851086360193e3` -- **matching `run-001`'s `1.16e3` almost to the last reported digit**, strong evidence this is a faithful, deterministic reproduction of the same frontier, not a different code path.
- Unlike `run-001`, the escalation-on-failure chain did not give up at 64: `boundedRecoveryFallback(64)` now correctly returned `128` (issue-058's fix working exactly as designed), and the run entered a substep loop at `timestep_hours=7.8125e-3` (exactly 1/128 h). During that loop it emitted roughly 85+ consecutive `error: implausible surface conductive flux` diagnostic lines with slowly worsening (diverging, not stagnant) surface/subsurface temperature-difference values. This diagnostic is a pre-existing, already-tracked, non-fatal log line (`ecosys-ng/src/surface/temperature_solver.zig:764-767`, tag `DRY-LAYER-UNPHYSICAL-HEAT-SINK-HOUR-2726-001`, previously characterized in this project's own handoff as "a live, unresolved, in-progress diagnostic" seen around hours 2,705/2,726) -- its appearance here, newly, at hour 2,579 under a finer substep length it had not previously been exercised at, is itself a small new data point for whoever eventually resumes that separate investigation, but it is a `std.log.err` call, not a hard failure, and does not by itself explain what happened next.
- **The process then terminated with exit code `-1073741819` (`0xC0000005`, `STATUS_ACCESS_VIOLATION`)** -- no Zig panic message, no stack trace, no "hard failure"/"bounded fixed external hour recovery rejected" clean-failure line, and `evidence.jsonl`'s last flushed `accepted` event remained at hour 2,568 (the intervening hours 2,569-2,579's `attempted` events were never flushed to the journal either) -- the log and journal simply stop mid-substep, exactly the signature `issue-058` itself documented from `issue-024` round 7's original reproduction ("the log simply stops... no Zig panic message"). **Reproduced twice**: once in an initial background-monitored run (process disappeared, `Get-Process` returned nothing, no error in the redirected stderr/stdout files), and once in a second, fully synchronous foreground run from a freshly re-copied isolated deck, which directly captured the exit code above via `$LASTEXITCODE`. Both runs failed at the same hour with the same residual and the same crash signature.

**This is new, distinct evidence, not a repeat of issue-058's fixed defect.** `issue-058`'s own fix specifically closed the inconsistency between `heat_step.zig`'s array walk and `hourly_heat_water_solute.zig`'s `boundedRecoveryFallback`, and issue-024 round 7's original crash required *both* extending the array *and* raising `minimum_freeze_flow_coupling_substeps` past the old hardcoded ceiling to reach it. **This experiment left `minimum_freeze_flow_coupling_substeps` untouched at its committed value (`4`)** and still hit the identical crash signature from the array extension alone, once a real production run actually exercised a substep count above 64 through many consecutive sub-hour iterations of real physics (as opposed to issue-058's own extensibility test, which exercised `fallbackWithinLadder` structurally against a local-only ladder, never actually running a production hour at the new tier). **This means issue-058's fix, while a correct and verified solution to the specific two-consumer inconsistency it targeted, does not make extending the ladder generally safe** -- there is at least one more, still-unidentified assumption elsewhere in the production codebase that a maximum substep count of 64 will never be exceeded in practice, and it fails silently (no bounds-check panic) in `ReleaseFast`, where such a check would be compiled out, rather than the loud, diagnosable panic it would likely produce in `ReleaseSafe` (the mode `run-001` happened to use).

**Bounded root-cause search performed (not exhaustive)**: grepped the whole `ecosys-ng/src` tree for fixed-size arrays of length 64 that could plausibly be indexed by an in-hour substep counter. Found and individually inspected: `soil/water/solver_solve.zig:944` (`failure_norm_trace: [64]f64`) and `soil/solute/reaction_solve.zig:1496-1497` (`failure_norm_trace`/`failure_kind_trace: [64]...`) -- both are explicitly length-guarded (`if (failure_norm_trace_len < failure_norm_trace.len)` before every write) and indexed by inner Newton/Anderson *iteration* count (bounded separately by `max_iterations`, e.g. 60 for SOLUTE), not by the hour's substep count, so both are ruled out as the cause. The `MATRIC_TRACE024` diagnostic (the tag `issue-058`'s own original crash reproduction happened to be printing when it died) is gated to `executed_weather_hours < 1` and was therefore not even active at hour 2,579. **No production `[64]`-sized (or otherwise substep-count-shaped) unguarded buffer was found in this bounded search.** The actual cause of the access violation remains unidentified -- this pass did not have budget to bisect further (e.g., with a debugger, or a `ReleaseSafe` rebuild of the same extended ladder to get a clean panic message instead of a silent crash, which would be the obvious next diagnostic step for whoever continues this).

**What this does and does not answer**:
- It does **not** answer issue-015's central question. The SOLUTE solver's 128-substep attempt never ran to completion (accepted or rejected) -- the crash happened first. Whether more substep headroom would have let hour 2,579 converge is still genuinely unknown.
- It does **not** support the working conclusion that this is an unresolvable "genuine numerical wall" any more strongly than before -- the residual was still falling at the last valid data point (64 substeps, `1.16e3`, matching `run-001`), and that trend was never allowed to continue far enough to plateau-or-converge before the crash intervened. Confidence in the "genuine numerical wall" framing should if anything be **held flat, not increased**, by this result -- the experiment designed to test it was inconclusive on convergence.
- It **does** find a new, concrete, reproducible defect: extending `recovery_substep_counts` past its current committed maximum (`64`) crashes the production `ReleaseFast` binary via an unidentified memory-safety violation once the new tier is actually exercised in a real run, independently of `issue-058`'s already-fixed two-consumer inconsistency and independently of `minimum_freeze_flow_coupling_substeps`. This should be treated as its own tracked defect (a candidate `issue-059` or similar) by whoever picks this up next, since it blocks not just this specific experiment but any future attempt to extend the ladder at all.
