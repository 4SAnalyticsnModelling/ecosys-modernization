## Failure signature and first bad time/location/process

`f77src/redist.f`'s `DO 225 LX=NL(NY,NX),NU(NY,NX),-1` loop (`:7734-8133`, part of feature-010's Finding 15 range) computes, for each of four independent layer-boundary-depth-change mechanisms (`NN=1` pond, `NN=2` freeze-thaw, `NN=3` erosion, `NN=4` SOC), a per-layer cumulative depth change `DDLYX(LX,NN)`/`DDLYR(LX,NN)` accumulated from the bottom of the profile (`LX=NL`) upward to the top (`LX=NU`). Because the loop's own index range stops at `LX=NU`, each mechanism needs an explicit extra statement, guarded `IF(LX.EQ.NU(NY,NX))THEN`, to carry the cumulative value one slot further up to `DDLYX(LX-1,NN)`/`DDLYR(LX-1,NN)` -- this extra slot (`NU-1`) is read unconditionally later, in the nested `DO 200 NN=1,4` loop's soil-layer branch (`:8077-8080`): `CDPTH(LX-1,NY,NX)=CDPTH(LX-1,NY,NX)+DDLYR(LX-1,NN)` whenever `LX.EQ.NU(NY,NX)`. `CDPTH(NU-1,...)` is the cumulative depth to the bottom of the litter layer / top of the first active soil layer -- a load-bearing quantity read throughout the rest of the file.

Three of the four mechanisms have this top-of-profile carry statement, within the soil branch (`BKDS(LX)>ZERO`, `:7811` `ELSE`):
- Pond (`NN=1`): `:7820-7824` (`DDLYX(LX-1,1)=DDLYX(LX,1); DDLYR(LX-1,1)=DDLYX(LX,1); IFLGL(LX-1,1)=0`).
- Freeze-thaw (`NN=2`): present in *both* its active arm (`:7973-7978`, `ABS(DVOLI)>ZEROS`) and its negligible arm (`:7990-7994`).
- SOC (`NN=4`): present in its active arm (`:7913-7918`, `ABS(DORGC(LX,...))>ZEROS` and one of the horizon-reset conditions).

**Erosion (`NN=3`, `:7842-7864`) has no such carry statement in either of its two arms** (`:7857-7858` active -- `IERSNG.EQ.1.OR.3` and nonzero `TSEDER`/`TSEDSK`; `:7861-7862` negligible). Confirmed by direct read of the complete block, not by absence of a grep match alone. **SOC (`NN=4`) has a conditional version of the same gap**: its own negligible arm (`:7920-7930`, `ABS(DORGC(LX,...)).LE.ZEROS`) also lacks the carry -- so the SOC gap surfaces only when the top layer's own `DORGC` is negligible while a deeper layer's real SOC-driven depth change still needed to propagate up to `CDPTH(NU-1,...)`.

`DDLYX`/`DDLYR` are declared as plain local `DIMENSION(0:JZ,4)` scratch arrays at `redist.f:170` -- not `COMMON`, not per-`(NY,NX)`-grid-cell-dimensioned, reused across the whole `DO 9995 NX` / `DO 9990 NY` grid sweep for every cell in a single call. A full-file grep of every `DDLYX(`/`DDLYR(` occurrence in `redist.f` found no zero-initialization anywhere. Consequently, whenever the top soil layer is real soil (not pond) and erosion is active, `DDLYR(NU(NY,NX)-1,3)` is never freshly written during the current cell/hour's `DO 225` iteration -- it retains whatever value was last left in that memory slot, most likely a permanently-untouched zero (since index `NU-1` falls outside every cell's own `[NU,NL]` loop range and is therefore never touched directly by the main loop body for any cell), meaning the erosion-driven boundary shift is silently dropped from `CDPTH(NU-1,...)` specifically, while it correctly applies to every layer at and below `NU`.

Cross-check confirming this is specific to the soil branch, not the mechanism generally: the erosion leg's *pond* branch (`:7785-7792`, when `BKDS(LX)<=ZERO`) is a pure passthrough of the deeper layer's cumulative value and **does** carry to `LX-1` (`:7791-7792`). Only the soil branch's version of this same `NN=3` leg omits the carry -- an instance of the same "pond-branch-vs-soil-branch asymmetry" pattern class already tracked under `issue-017`, though this is a distinct mechanism (boundary-depth bookkeeping, not a pool-transfer defect) and is filed separately rather than folded into `issue-017`.

## Resolution

Cause: legacy Fortran per-mechanism, manually-unrolled boundary-carry logic -- three of four sibling mechanisms (pond, freeze-thaw, SOC-active-arm) each independently repeat a short `IF(LX.EQ.NU...)` carry block; the erosion mechanism's soil branch never had one written (and the SOC mechanism's negligible arm also never had one written). This is the same general defect *shape* already established in feature-010 (an incomplete manually-maintained parallel-block pattern), here manifesting as a missing boundary-index write rather than a missing species or a wrong-donor substitution.

No patch needed in Zig: production already avoids the gap because `geometry_change_assembly.zig`'s erosion and SOC assembly functions were written to explicitly construct every boundary value (including the top one) rather than to carry a value forward only when a per-mechanism conditional happened to trigger a write. This is a **positive, already-avoided** finding -- there is no divergence to fix in the Zig implementation as it stands today.

What remains open: the avoidance is **undocumented and not verified end-to-end at runtime**. Nothing in `geometry_change_assembly.zig`'s or `geometry_disturbance_transaction.zig`'s comments states that the "assign every boundary explicitly" design was chosen specifically because it also avoids this legacy carry-omission; it reads as an incidental consequence of a generally cleaner assembly style. A future refactor that changes either assembly function to a per-layer conditional-carry style (for performance or for some other reason) could silently reintroduce the exact legacy gap with no test flagging it as a regression against the *Fortran*, only against Zig's own prior behavior. Separately, this pass performed no dynamic/runtime check of what the legacy Fortran's stale `DDLYR(NU-1,3)` slot actually contains during a real grid sweep (static-analysis-only pass, per this pass's explicit constraint) -- the "most likely a permanently-untouched zero" characterization above is a structural inference from the array-declaration and loop-bounds evidence, not a confirmed runtime observation, and the actual legacy-side magnitude of this gap (if any) has not been evaluated.
