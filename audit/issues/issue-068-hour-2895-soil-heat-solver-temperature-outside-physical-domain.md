### Findings

- **The violation is on the upper bound, not the lower one.** All three observed values (401.75 K, 452.64 K, 455.14 K) exceed `maximum_physical_temperature_k=373.15` K (+100 C) by 28.6 K, 79.5 K, and 82.0 K respectively -- the layer is overheating, not overcooling. This is the opposite sign from the `REAL-DECK-HOUR-11-FATAL-STAGNATION-001` precedent (~125.5 K, overcooling), confirming this is a fresh manifestation of the same *class* of defect (finite-but-absurd committed state), not a re-run of that exact old bug.
- **Classification: genuine numerical instability, not a marginal overshoot.** 452-455 K is 79-82 K past the ceiling -- roughly 20% of the entire valid band's width past its edge, not a last-ULP rounding artifact. This clearly falls on the "something is fundamentally diverging" side of the distinction this task asked to resolve, not "needs a bit more headroom."
- **Escalating substeps made it worse, not better**: 401.75 K at `substep_count=20` -> 452.64 K at `substep_count=32` -> 455.14 K at `substep_count=64` (the ceiling). A normal stiff-but-resolvable problem should approach a bounded limit as `dt` shrinks; here finer time resolution is correlated with a *larger* overshoot. This is evidence against "just needs more substep headroom" and consistent with an ill-conditioned/near-singular update for this specific cell rather than an ordinary stiffness problem.
- **Same site, same session-long chain, and the mechanism is now more precisely located.** The run's existing `DRY_CARRIER_TRACE`/`TEMP_DIAGNOSTIC` instrumentation (still live from the issue-060..067 chain) shows, in the lines immediately preceding both violations, the familiar cell 0/layer 0 near-total desiccation (`old_water_m3`/`new_water_m3` repeatedly exactly `0`) *and* issue-060's own `negligible-capacity layer discarded heat per WATSUB 6907` warning firing repeatedly with `total_heat_capacity_megajoules_per_k` in the `2.0e-5`-`3.0e-5` range against `limit_megajoules_per_k=8.38e-5` -- i.e. this layer's heat capacity is chronically ~3-4x below issue-060's own already-fixed discard threshold, right before the blow-up. **This confirms issue-060's WATSUB-side energy-discard safeguard and this check are two different gates in the same pipeline, and the WATSUB-side one firing correctly does not prevent the dense heat solver's own Newton/Anderson commit from landing on a physically absurd temperature for this cell.** The two mechanisms do not talk to each other.
- **Connection to issue-024**: this is a fresh manifestation of the same still-open concern issue-024 rounds 6-7 flagged ("the substep-schedule/ICHKV-equivalent-tier gap... needs reviewer decision") for the same cell/layer, at a different hour (2,895 here vs. hour 1 there) and now materializing as a hard failure (solver rejects and the hour cannot commit) rather than a legacy-oracle divergence. Not the identical code path issue-024 examined, but the same underlying degenerate-layer class of problem the reviewer decision was deferred on.
- **Root cause located, mechanism confirmed, but not the exact numerical trigger inside the Newton/Anderson loop.** `solver_solve.zig`'s dense multi-layer Newton/Anderson solver has (at least) two "early accept" paths that commit `current` directly once a scaled residual `norm` metric is small (`:3189`, `norm<=1`; and `:4896-4912`, the `practical_accept` path with a `100x` relaxed multiplier) -- committing via `commitAcceptedState`, which is the only place `validateSoilTemperaturePhysicalDomain` is actually invoked on the *accepted* state (as opposed to the many `isPhysicalTemperatureK` line-search admissibility checks scattered through the same file, which just reject an individual trial step and keep searching, never raising this error themselves). For an ordinary layer, a small scaled residual implies a small absolute temperature departure. For this layer, heat capacity is near zero (`~2-3e-5` MJ/K, per the WATSUB trace above), so the same scaled-residual metric can be satisfied by a state whose *absolute* temperature is wildly off, because a small absolute energy residual divided by a near-zero capacity is a huge temperature swing. This is the specific mechanism by which the check catches something the residual-norm acceptance criterion missed -- exactly the scenario the check's own docstring predicts, just not yet observed with numbers before now.

### Why no fix was implemented this pass

Per this task's own instruction, a physically-justified stabilization is preferred over any change to the physical-domain bound itself (which is correctly not proposed here). The most defensible candidate fix identified is: require the two early-accept branches above (`:3189` and `:4896-4912`) to also pass `isPhysicalTemperatureK` for every component of `current` before treating the state as converged, falling through to the existing (already-tested) "did not converge" path otherwise rather than committing and failing the whole substep immediately. This is attractive because it reuses an already-tested fallback and does not touch tolerances, the recovery ladder, or the physical bound -- but it changes acceptance behavior inside the shared Newton/Anderson core used by every cell and every hour, not just this degenerate one, and interacts with `retrying_newton_after_anderson`/`best_state` bookkeeping this pass has read but not exhaustively traced. Given the contract's caution against touching an established solver architecture and this task's explicit "only implement if high confidence" instruction, this is handed off rather than attempted blind.
