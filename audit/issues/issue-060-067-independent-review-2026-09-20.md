### issue-062 -- shared `FloorDiscard` ledger (`heat_layer_remap.zig` / `relayering_activity.zig`)

This is the highest-blast-radius fix reviewed in most depth. Read `heat_layer_remap.zig`'s `calculate()` in full (not excerpted): `result.destination_discarded_megajoules`/`result.source_discarded_megajoules` are each `0` when that side's post-transfer capacity is above `parameters.minimum_heat_capacity_megajoules_per_k`, and otherwise `capacity_after * temperature_assigned - energy_after_exact` -- i.e. exactly the amount by which the legacy VHCPRX-floor fallback's assigned temperature departs from the exact conservative energy split, matching `redist.f:9660-9665`'s cited behavior.

**Independently re-derived the netting algebra** in `relayering_activity.zig`'s `stageBoundary` (did not just trust the issue's own claim): with `raw_loss = before_donor - after_donor` and `raw_gain = after_recipient - before_recipient`, and writing `after_x = exact_after_x + discard_x` for whichever side(s) took the fallback branch, `raw_loss - raw_gain = (loss_exact - gain_exact) - (discard_donor + discard_recipient)`. Since `heat_layer_remap.zig`'s exact split by construction satisfies `loss_exact == gain_exact == transferred_energy`, this reduces to `raw_loss - raw_gain = -(discard_donor + discard_recipient)`. `adjusted_delta = (raw_loss - raw_gain) + known_heat_floor_discard_megajoules` with `known_heat_floor_discard_megajoules = discard_donor + discard_recipient` (confirmed this is exactly what `relayering.zig:672-673` passes: `water_heat_floor_discard.source_megajoules + water_heat_floor_discard.destination_megajoules`, and confirmed `src_layer`/`dst_layer` passed to `stageBoundary` are the *same* `src_global`/`dst_global` passed to `transferLayerFractions`, so "source/destination" and "donor/recipient" are never swapped) therefore always evaluates to exactly `0` plus whatever genuine residual existed before any fallback fired. This is not merely "passes its own unit tests" -- the algebra is correct by construction, and a genuine unrelated heat-conservation violation of the same magnitude is still rejected (confirmed by the existing "still rejects a genuine mismatch" test, which supplies `0` discard against the identical 14.7 MJ gap and gets `RelayeringActivityConservationFailure`). Also confirmed the fix does not silently widen the *tolerance* (`allowed` is untouched; only the compared quantity is adjusted), so this cannot mask an unrelated defect of different magnitude/sign -- an unrelated donor/recipient mismatch would still have to coincidentally equal the *exact* floor-discard magnitude to slip through, which is not the failure mode this codebase's other defects exhibit (they are 10+ orders of magnitude off, not degenerate near-matches).

Finding 1's disposition (Finding 2 in the issue's own numbering: the tillage sidecar, confirmed NOT wired and confirmed NOT needed) was independently re-checked by reading `redistribution/tillage/physical_redistribution.zig:119-134`: temperature is computed by a plain unconditional division guarded only by `heat_capacity <= 0 -> error`, with no VHCPRX-style floor/fallback branch -- confirmed tillage cannot exercise `heat_layer_remap.zig`'s fallback at all, so no wiring gap exists there. **Holds up**, including the subtle sign/mapping details that a less careful review could get backwards.

## Cross-fix interaction check (the task's explicit ask)

Every one of the eight fixes uses the *same* shared floor (`core/legacy_water_negligible_floor.zig`'s `legacyNegligibleWaterVolumeM3`, `1.0e-6` m3/m2) and the *same* comparison operator (`>` for "stay live", not `>=`), confirmed by grepping every site above directly rather than trusting each issue's own claim of consistency. No two fixes use a different floor value, and no boundary-condition mismatch was found between any pair (e.g. one fix treating exactly-at-the-floor as "live" while a downstream consumer treats it as "dry" would double-count or leave a gap; this was checked and does not occur anywhere in the eight issues' own code).

**However, a genuine gap was found by extending this same cross-check beyond the eight issues' own files**, to every one of the 33 files in `ecosys-ng/src` that reference `dry_reference_water_m3`. Two of the issues' own sweeps (issue-061's keyword sweep for `*Carrier*`/`*WaterVolumes*`/`rebase`/`transfer`/`remap`/`relayer`, and issue-064's broader-but-still-keyword-driven sweep, and issue-066's dedicated pack/unpack sweep) all shared a blind spot: none of them reached `surface/pond_chemistry_transfer.zig` (a production surface-pond-to-soil mutator with the identical exact-zero-only guard shape, never mentioned by any of the eight issues) or the *asymmetry* between `redistribution/tillage/runtime_adapter.zig`'s correctly-fixed *write*-side call (`commitTillageSurfaceAmounts`) and its still-unfixed *read*-side call (`gatherTillageSurfaceAmounts`, in a different file, `surface/aqueous_runoff_transport.zig`). Filed as `issue-069` (new, distinct problem, not a reopening of issue-064 or any other issue in this chain).
