## Summary

All 7 failures visible in the first complete `zig test src/module_index.zig` run this session ever obtained share **one single mechanical root cause**, confirmed by direct byte-level inspection, not inferred:

1. **This checkout's tracked `.zig` files are 100% CRLF line-terminated** (`git config core.autocrlf` = `true` on this machine; verified by counting bytes in `ecosys-ng/src/ecosys_ng.zig`: 14,724 `LF` bytes, of which all 14,724 are immediately preceded by `CR` -- i.e. zero bare-LF lines in the whole file).
2. **7 tests hardcode a Unix-style (`\n`-only) multi-line string literal** and search for it verbatim inside either an `@embedFile`'d or `readFileAlloc`'d copy of a production `.zig` file (`ecosys_ng.zig` or `solver_solve.zig`), using `std.mem.indexOf`/`indexOfPos`/`count`.
3. On this CRLF checkout, the byte sequence actually present is `...(\r\n        ...`, not `...(\n        ...`. The literal `\n`-only needle is not a substring of the CRLF text (the `\r` sits between the two characters the needle expects to be adjacent), so every one of these 7 assertions fails to find its needle -- with **zero model execution and zero production-logic involvement** in any of the 7 tests. Every one of these tests is a pure source-text scan (`@embedFile`/`readFileAlloc` + `std.mem.indexOf`-family calls only); none instantiates a solver, state, or grid.

This is the same category of false alarm this project's own `numerics.zig` already carries a dated note about (per `audit/handoff.md`'s 2026-09-18 entry: "a prior false-alarm CRLF-related test-failure misattribution", 2026-09-03) -- this issue is the first time this session has pinned the mechanism down exhaustively across every currently-affected test, rather than one-off.

## Classification

**(c) Flaky/environment-dependent.** None of these 7 failures are:
- (a) genuine regressions from any of this session's ~75 prior fixes -- no production code path is exercised by any of the 7 tests, and every non-`\n`-embedding assertion in the same test files (including ones checking the exact call orders/counts these fixes touched) still passes.
- (b) pre-existing-but-unrelated defects predating this session -- they would fail identically on any checkout with `core.autocrlf=true`/CRLF-normalized `.zig` files, independent of when the source was last touched; this is a checkout/environment property, not a source-content-age property. (Not verified against an old commit specifically, since the mechanism is fully explained by byte-level evidence already gathered -- re-running against a stale commit would not add information and would spend diagnosis budget on a foregone conclusion.)

They are (c): the test's own hardcoded assumption (`\n`-only multi-line literals matching `@embedFile`/`readFileAlloc`'d *self-referential* production source) is only valid on a checkout where those same files are LF-terminated. This machine's `git config core.autocrlf=true` normalizes tracked text files to CRLF on checkout, which silently breaks any test that assumes byte-exact LF reproduction of its own repository's source.

## Fix (2026-09-21, adversarial Claude/Pi session) -- all affected assertions rewired to scan CR-insensitively; two findings this issue's original triage missed

**Approach taken, and the one deliberately not taken.** This issue offered two remediation paths: narrow CRLF-stripping at the `readFileAlloc` sites, or a repository-wide `.gitattributes` LF renormalization. Neither was used. The narrow path only covers 2 of the 4 affected files (the other two use compile-time `@embedFile`), and the repo-wide path rewrites every tracked file, which this issue itself argues against attempting solo. Instead the *assumption* was removed: a new shared, allocation-free, test-support scanner treats a `CR` in the haystack as invisible whenever the needle does not ask for one, so the same needle matches an LF and a CRLF checkout identically.

- New module: `ecosys-ng/src/core/source_scan.zig` -- `indexOfIgnoringCarriageReturns`, `indexOfPosIgnoringCarriageReturns`, `containsIgnoringCarriageReturns`, `countIgnoringCarriageReturns`, plus 5 of its own tests (including one proving the helper still works on a plain LF haystack, so this does not trade one checkout assumption for the opposite one). Returned offsets are offsets into the *original* haystack, so the ordering assertions these tests perform (`index_of_a < index_of_b`) remain valid. Registered at `src/module_index.zig:16` and `src/index/core_test_index.zig:59`, and carries a census banner in the same documented `CENSUS-ORPHAN-FP-001` class as the `src/index/*_test_index.zig` files.
- Rewired: `soil/heat/solver_tests.zig` (9 needles), `driver/outer_hour_transaction.zig` (the `inline for` binding count), `io/output/production_integration_test.zig` (its two shared helpers `requiredIndex`/`requiredIndexIn`, which covers every needle in that file), `canopy/symbiosis/plant_symbiotic_fixation.zig` (the `executeHourlyScience` needle). Needle text, error names, and comparison directions are all unchanged.

### Finding 1: this issue's own table understated the count, because a Zig test aborts at its first failed assertion

The table above lists one failing needle per test. That is the *first* failing needle, not the only one. `solver_tests.zig` actually carries **9** interior-`\n` needles across the affected tests, not the 4 the table implies; the extra 5 only surfaced after the first fix round still left `"transition-optimized endpoint discovery full-scans before recovery or ceiling"` failing. Anyone triaging a multi-assertion test from a single failure line should assume the same understatement.

### Finding 2: one of these assertions was passing for the wrong reason, and that is the more serious half of this issue

`solver_tests.zig:4200` asserts a needle is **absent** (`== null`) -- the guarantee that the rejected-mixed-endpoint branch does *not* reprice against `accelerated_residual`. On a CRLF checkout that needle could never match regardless of what the production text said, so the assertion proved nothing while reporting success. It is now meaningful for the first time. Note the asymmetry this implies for the whole class: a broken *positive* needle fails loudly and gets fixed, while a broken *negative* needle passes silently and can retire a production guarantee without anyone noticing.

### Classification rule worth keeping (it explains why exactly 7 tests failed and not more)

A needle whose only `\n` is **leading** is safe on a CRLF checkout: `"\npub fn solveSoilHeatWaterAndSoluteTransport("` still matches, because CRLF is `\r\n` and the `\n` the needle expects is genuinely present -- the extra `CR` sits *before* it, outside the match. Only an **interior** `\n` (one with needle content after it, e.g. `"...,\n        next_argument"`) breaks, because the text has `\r` where the needle expects `\n`. Trailing-`\n` needles against *generated* text (e.g. `conservation_survey.zig:382`'s `"never moved\n"`, searched in a `writeAll`-produced report rather than in source) are likewise safe. This is why a whole-tree sweep turns up many `\n` literals in files that also scan `.zig` source while only 7 assertions actually failed.

**Sweep performed after the fix** (two independent passes, one by each session, then reconciled): the peer reviewer swept every `@embedFile`/`readFileAlloc` consumer and reported no remaining affected assertion beyond `conservation_survey.zig:382` (correctly classified as safe generated text); an independent broader regex sweep here across all 44 `.zig`-source-scanning files initially flagged ~20 more sites, every one of which was then classified as a false positive on inspection -- `std.debug.print` format strings (`validation/mass_balance_audit.zig:1372` and similar), synthetic deck/option input text (`soil/profile/runtime_material_refresh.zig:396-403`, `core/options.zig`), or leading-`\n` needles covered by the rule above. A targeted multiline search for the dangerous combination specifically (a negative comparison within 160 characters of an interior-`\n` needle) returns only the `solver_tests.zig:4200` site already fixed.

## Why no fix was applied this pass

All 4 affected files (`plant_symbiotic_fixation.zig`, `outer_hour_transaction.zig`, `production_integration_test.zig`, `solver_tests.zig`) would need a CRLF-tolerant read/compare path to close this durably, and the natural fixes are asymmetric in risk:
- `outer_hour_transaction.zig` and `solver_tests.zig`'s `readSolverSolveSource()` already own a mutable, allocator-owned buffer (`readFileAlloc`) -- normalizing (stripping `\r`) in place there is narrow and low-risk.
- `plant_symbiotic_fixation.zig` and `production_integration_test.zig` use `@embedFile`, a compile-time immutable array; `production_integration_test.zig`'s `driver_source` in particular is a **module-level constant shared by 7+ other currently-*passing* tests** in the same file (including one that already does its own `\n`-based line-splitting, `splitScalar(u8, driver_source, '\n')`). Normalizing it safely means restructuring how every test in that file obtains its source, not a 1-line change, and risks a wider blast radius than this pass's "fix only if trivial/obviously-safe/1-2 items" budget allows for a single sitting.
- A repository-wide `.gitattributes` LF-normalization (the more durable fix) requires a full-tree `git add --renormalize`, which this contract's "do not rewrite unrelated files" caution and this session's own "no concurrent edits to shared... build files" discipline argue against attempting solo, especially with other sessions/peers concurrently active in this same working tree per this handoff's own history.

Recommended follow-up (not performed): either (a) add a small `stripCr`-style normalization helper used by the two `readFileAlloc`-based sites first (lowest risk, closes tests 2 and 4-7 = 5 of 7), then separately design the `@embedFile`-based sites' fix with its own dedicated review (tests 1 and 3); or (b) adopt a project-wide `.gitattributes` `*.zig text eol=lf` policy as a coordinator-level decision (closes all instances of this class at once, including any not yet discovered, but is a repo-wide change needing single-owner scheduling per the contract's "one coordinator owns... expensive/shared changes" rule).
