The comment reads as diagnosis, not yet resolution -- it is not stated here (in the part read) whether the eventual fix was "clamp at read like the oracle" (matching legacy exactly) or "keep the write-time reject but bound the tiny numerical overdraw" (a stricter, arguably more defensible policy, but a deliberate deviation needing its own approval per the contract's "legacy-defect-corrected" disposition). **Not yet confirmed** which resolution (if any) was actually applied -- `calculateNonstructuralStateUpdate` as read still calls `validateNonstructuralPool(next)` unconditionally, suggesting either (a) this is still an open/live failure mode for any input that reproduces hour 2678's tiny negative excursion, or (b) upstream callers now pre-clamp inputs so the excursion can't reach this function, which was not traced this session.
