Location: `ecosys-ng/src/soil/microbial/state.zig`, comment at line 98 above `calculateNonstructuralStateUpdate` (lines 78-96).
Finding: the legacy oracle (`nitro.f:3824`, `nitro.f:3832`) writes the nonstructural microbial pool `OMC/OMN/OMP(3,...)` **without** clamping, and deliberately allows it to go negative in storage; it clamps only at the two *read* sites (`nitro.f:2094`, `nitro.f:2532`: `OMC3=AMAX1(0.0,OMC(3,N,K,L,NY,NX))`). The comment reads as diagnosis, not yet resolution -- it is not stated here (in the part read) whether the eventual fix was "clamp at read like the oracle" (matching legacy exactly) or "keep the write-time reject but bound the tiny numerical overdraw" (a stricter, arguably more defensible policy, but a deliberate deviation needing its own approval per the contract's "legacy-defect-corrected" disposition). **Not yet confirmed** which resolution (if any) was actually applied -- `calculateNonstructuralStateUpdate` as read still calls `validateNonstructuralPool(next)` unconditionally, suggesting either (a) this is still an open/live failure mode for any input that reproduces hour 2678's tiny negative excursion, or (b) upstream callers now pre-clamp inputs so the excursion can't reach this function, which was not traced this session.
