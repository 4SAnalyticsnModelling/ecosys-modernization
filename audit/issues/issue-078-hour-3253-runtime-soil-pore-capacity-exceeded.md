## Sixth diagnostic pass (2026-09-21, source-reading only, no runtime rerun, no code changed) -- option (c) blocked at the Newton/Anderson boundary before any edit was made

**Goal**: test the refined form of option (c) -- a dedicated post-tillage relief step, invoked once immediately after `applyDeferredTillageSoil` completes, that reuses whatever EXISTING Zig mechanism already performs ORDINARY (non-tillage) excess-water redistribution between adjacent soil layers during a typical hour's WATSUB-equivalent solve, so tillage's excess water can reach deeper, non-tilled layers exactly as excess water from any other cause would. Explicitly scoped to stop, not guess, if that existing mechanism turned out to itself be Newton/Anderson acceptance logic.

**Search performed**: exhaustive `soil/water/` and `soil/profile/` inventory (all ~60 and ~19 files respectively) plus targeted keyword greps (`excess|redistribut|relief|overflow`) for any layer-to-layer water-movement mechanism that (a) is triggered by one layer exceeding its own pore capacity, (b) is not the Newton/Anderson solver core itself, and (c) is callable as a standalone step.

**Two candidates found, both ruled out:**

1. **`relayering.zig` -> `heat_layer_remap.zig`'s `transferLayerFractions`** (already characterized in this issue's second dynamic-diagnosis pass): moves a fixed fraction `fx` of a *source* layer's water/capacity into a *destination* layer, but `fx` is driven purely by layer-boundary/geometry-shift bookkeeping (`remapSoilLayerPair`, gated on `geometry_changes`), not by any capacity check. It has no notion of "excess" or "spare room" and was already shown (dynamic diagnosis, experiment 1) to move noise-level water (~1.4e-10 m3) at the actual frontier hour. Reusing it would not target spare capacity in deeper layers at all -- wrong tool, ruled out.

2. **`applyMechanicalFreezingDisplacement`** (`ecosys-ng/src/soil/water/solver_residual.zig:38-144`, backed by `mechanicalFreezingDisplacementM3` in `flux.zig:93-106`, doc-commented "WATSUB FLQL/FLWHL mechanical freezing term") -- this is the actual, and only, ordinary-case mechanism that moves water from a layer with a pore deficit into the adjacent layer above it when displacement is needed. It is exactly what `runtime_material_refresh.zig`'s own hour-boundary-check comment names as the intended relief path ("a source-ordered mechanical prepass"). **But it is not a standalone utility**: it is a private (non-`pub`) function called only from `residualAt` (`solver_residual.zig:212`), which is the residual function assembled and repeatedly evaluated by the Newton-Raphson/Anderson solve itself (`solver_solve.zig:30`'s `pub fn solve`). Its parameters are solver-internal types that do not exist in `postScienceManagementAndGasAccounting` (where `applyDeferredTillageSoil` runs): `group_types.Face` (per-hour face topology built for that hour's solve), `group_types.Properties` (the solver's own properties struct, distinct from `context.properties`), and `target: []f64` (the assembled continuous matrix+macropore state vector the nonlinear solve iterates on) -- not `context.grid`'s plain per-cell arrays, which is all that is available post-tillage. The same kernel (`mechanicalFreezingDisplacementM3`) is also inlined directly into `calculateMatrixFaceFlux` (`flux.zig:80`), the Darcy face-flux term at the heart of residual assembly -- confirming this term is Newton/Anderson machinery through and through, not a sibling module the solver merely happens to call.

**Why this blocks a safe implementation**: reusing this mechanism after tillage would require either (a) exposing the private function and hand-assembling solver-shaped `Face`/`Properties`/`target` inputs from `context.grid` outside of any real Newton/Anderson iteration -- fabricating a partial, ad hoc solve rather than reusing an existing independent mechanism -- or (b) invoking the real `solve()` an extra, hour-schedule-unspecified time immediately after tillage. `executeHourlyScience` (which runs the real per-hour WATSUB-equivalent solve, confirmed via `ecosys_ng.zig` call graph) already runs exactly once per hour, strictly BEFORE `postScienceManagementAndGasAccounting`/tillage; there is no lighter-weight "just redistribute once" entry point separate from the full nonlinear solve. Either option is precisely the class of change `PROJECT_CONTRACT.md`'s "Existing numerical architecture constraints" section warns against: "Internal iterations/substeps already belonging to an approved method must be documented and bounded... and must not change this policy silently" -- an extra, tillage-triggered solver invocation (or a hand-built fragment of one) is a nonlocal change to how many times per hour, and under what trigger, the Newton/Anderson solver runs, not a narrow reuse of a mechanism that lives outside it.

**Per the task's own explicit stop condition** ("If it requires touching something you're not confident is safe (e.g., if the existing mechanism turns out to itself be part of the Newton/Anderson acceptance logic after all), stop and report that boundary was reached rather than guessing"): that boundary was reached. **No edit was made.** `git status --short` and `git diff --stat` were checked before and after this pass and both are empty -- there was never anything to revert.

**Verdict**: option (c), as refined ("reuse an existing ordinary-redistribution mechanism"), cannot be implemented safely with the mechanism that actually exists, because that mechanism does not exist independently of the Newton/Anderson solver -- it IS part of it. This narrows, but does not close, the remaining design space: a genuine dedicated post-tillage relief step would need to be a NEW mechanism (not a reuse), built either as its own small capacity-aware transfer function operating on `context.grid` directly (structurally similar to, but a fresh implementation of, the capacity-aware idea already tested and found physically insufficient when scoped zone-internal-only -- this time explicitly scoped to reach deeper non-tilled layers too), or by extending `applyDeferredTillageSoil`'s dispatch to defer/queue unresolved excess across subsequent hours (mirroring legacy's actual repeated-small-dose architecture, previously named option (d) and already shown to require redesigning the tillage activity ledger's accumulation model). Neither is a "reuse an existing mechanism" fix; both are new-algorithm design decisions requiring their own dedicated, reviewed pass -- consistent with, and now further narrowing, the open handoff from the second- and third-candidate experiments above.

**Disposition**: no code changed, no build run, no production rerun executed (none was warranted once the boundary was hit in source-reading -- per the contract's "bindings/updates before physics" order and this task's own instruction not to guess past this boundary). Diagnosis remains OPEN. Options (a) (capacity-aware single dose) and the naive form of (d) (dose-splitting) are ruled out by direct evidence (prior passes); (b) (reorder tillage before WATSUB) was already found inconclusive/non-equivalent (third diagnosis pass); (c) as "reuse an existing mechanism" is now also ruled out by this pass. What remains viable, unexplored, and would need a fresh dedicated pass: a NEW capacity-aware relief mechanism explicitly scoped to reach beyond the tillage mixing zone into deeper layers (extending, not reusing, the already-tested-insufficient zone-internal design), or a redesigned deferred-discharge/ledger-accumulating form of (d).

## Second-candidate diagnostic experiment (2026-09-21, non-committed) -- capacity-aware single-dose mixing, physically insufficient

**Goal**: test the second of the three previously-named design options -- (a) make the single deferred tillage-mixing dose itself capacity-aware/self-limiting -- as a mass-conserving alternative to (d) dose-splitting (tested and blocked in the section below) and (c) a dedicated post-tillage relief step (untested). Explicitly required to be provably mass-conserving (reallocate, never discard) and to surface, not paper over, any genuine physical impossibility.

**Change made (uncommitted, reverted after the experiment)**: `ecosys-ng/src/redistribution/tillage/physical_redistribution.zig`'s `redistribute()` (the kernel bound by `TillageRuntime.apply()` at `runtime_adapter.zig:1005` and called via the `physical_redistribution.redistribute(...)` invocation at `runtime_adapter.zig:1850`) was restructured from one pass into three:
1. **Pass 1** -- the unmodified REDIST 12137--12203 three-way blend (`ti`/`tx`/`fi` weights, `mixing_fraction`), producing each mixing-zone layer's naive post-blend `water[layer]`/`vapor[layer]`/`ice[layer]`, unchanged from the existing translation. `mineral_energy`/`layer_energy` (previously local per-iteration variables) were hoisted into per-layer arrays since they don't depend on this layer's post-blend water and are needed unchanged by pass 3.
2. **Pass 2 (the new relief step)** -- for each layer actually touched by pass 1 (`is_mixed[layer]`, i.e. `overlap > 0` and not skipped as too-thin), compute `water_room_m3 = matrix_pore_capacity_m3[layer] - ice[layer]/ice_density` (the same quantity `runtime_material_refresh.zig`'s next-hour entry check validates against) and classify each layer as excess (`water[layer] > room`) or spare (`room - water[layer]`). If total excess across the zone is positive: if total spare is insufficient (`total_excess > total_spare + roundoff`), return a new error, `error.TillageMixingZoneCapacityInsufficient`, with full diagnostic detail (every mixed layer's naive water, capacity, ice, and room) logged via `std.log.err` first. Otherwise, cap each excess layer at its own room and add the removed excess back to spare layers proportional to their spare share -- by construction this is an exact reallocation (nothing added or removed from the zone total).
3. **Pass 3** -- finalize `heat_capacity[layer]`/`temperature_k[layer]`/`temperature_c[layer]` against the (possibly capacity-relieved) final `water[layer]`, exactly where the original single-pass translation computed them, just deferred until `water[layer]` is no longer subject to revision. `snapshot[layer] = water[layer]` moved here too, so it reflects the accepted-final, not naive, value.

A new `matrix_pore_capacity_m3: []const f64` field was added to `Inputs` (validated finite/nonnegative, correct length), and the one real call site (`runtime_adapter.zig:~1854`) was updated to pass `context.grid.matrix_pore_capacity_m3[global_first .. global_first + layers]` -- the exact capacity array the next hour's entry check reads, so relief inside `apply()` targets the check that would otherwise fire one hour later.

## Diagnostic experiment (2026-09-21, non-committed) -- dose-splitting hypothesis test, blocked before reaching hour 3253

**Explicit scope note on the 3-experiment budget**: the section immediately below (third diagnosis experiment) already marks this issue's diagnosis budget as 3 of 3 spent. This entry is a *fourth*, separately-authorized bounded pass, run fresh per direct task instruction as the "design decision" reviewer/reframing step the contract calls for after a budget is exhausted (`ecosys-audit/PROJECT_CONTRACT.md`: "three distinct hypothesis-driven experiments before a fresh reviewer/reframing"). It tests one specific, previously-unranked hypothesis (dose-splitting reduces peak overflow), not a repeat of any prior experiment, and it is fully bounded, non-committed, and reverted per its own instructions -- disclosed here explicitly rather than silently treated as within-budget.

**Goal**: test whether splitting the single full-strength `applyDeferredTillageSoil`/`TillageRuntime.apply` mixing dose into 4 equal sequential partial doses (matching the committed `NFH=4` baseline as the simplest well-precedented split) reduces or eliminates hour 3253's `RuntimeSoilPoreCapacityExceeded` violation, as a coarse test of the "many small doses reduces peak overflow" hypothesis attributed to legacy Fortran's actual architecture.

**Change made (uncommitted, reverted before finishing)**: `ecosys-ng/src/management/disturbance_management_dispatch.zig`'s `applyDeferredTillageSoil` (:306) was edited so each pending cell's single `TillageRuntime.apply(runtime, cell, request.depth_m, request.mixing_fraction)` call became 4 sequential calls to `TillageRuntime.apply(runtime, cell, request.depth_m, request.mixing_fraction / 4)`. `apply()` itself needed no change: it already reads/writes `context.grid`/`context.properties` directly via `@memcpy` at commit (`runtime_adapter.zig:1005` and surrounding lines), so each of the 4 calls automatically sees the previous call's committed result as its "fresh state" -- no separate refresh step was needed.

**Attempt A (one shared `local_activity` attempt around all 4 calls, matching the original `beginAttempt()`/`...`/`commitAttempt()` placement around the whole per-cell loop)**: failed immediately, before any hour ran, with `error.DuplicateTillageActivityCell`. Root cause read from `ecosys-ng/src/redistribution/tillage/activity.zig:139-140`: `Sidecar.stageCell` (called from inside `TillageRuntime.apply`) hard-rejects a second `stageCell` call for the same cell within one attempt (`if (cell >= self.cell_count or self.staged_cell[cell]) return error.DuplicateTillageActivityCell;`). The activity ledger's attempt model is architecturally "exactly one tillage application per cell per attempt" -- confirmed by reading the type, not inferred.

**Attempt B (one `beginAttempt()`/`commitAttempt()` pair per individual sub-dose, so `stageCell` never sees two calls in the same attempt)**: this satisfied the guard and the build ran, but reproduced a *different*, earlier failure: `error.HourlyLayerConservationFailure` at the very first tillage event, hour 2,532 (matching `stage_execution_census`'s `tillage_soil_application ... first_hour=2532` from the second diagnosis pass above) -- 721 hours before ever reaching the hour-3253 frontier this experiment was meant to test. The failure's own diagnostic output shows per-cell relative residuals up to ~85% across many simultaneously-tilled cells (e.g. `cell=17 quantity=water ... normalized_relative=8.457142872223501e-1`, `cell=4 quantity=nitrogen ... normalized_relative=6.190228831014774e-1`), i.e. roughly 3/4 of the moved mass/energy/nutrient appears to "vanish" from the reconciliation ledger's point of view. This is a bookkeeping artifact of the scaffolding, not a real physical loss: `activity.Sidecar.commitAttempt()` (`activity.zig:90-95`) does `@memcpy(self.accepted_soil, self.staged_soil)`, i.e. each commit *overwrites* (does not accumulate onto) the previous commit's ledger. With one attempt per sub-dose, only the 4th (last) sub-dose's transfer record survives in `accepted_soil`/`accepted_surface` by the time the outer, once-per-hour `ecosys.layer_local_conservation.accumulateTillageActivity` call (`ecosys_ng.zig:4027-4030`, called once after `applyDeferredTillageSoil` returns) reads it -- even though the actual physical state in `context.grid`/`context.properties` correctly reflects the cumulative effect of all 4 doses (each `apply()` commits directly to grid/properties state, independent of the activity ledger). The hourly conservation check then compares "true cumulative before/after storage" against "only 1/4 of the doses' worth of declared transfer" and fails hard, exactly as the check is designed to do when a real accounting gap exists.

**Verdict: the core hypothesis (does splitting the dose shrink or eliminate the hour-3253 pore-capacity overflow) was NOT tested -- the run never got close to hour 3253.** Both of the two most natural minimal ways to call `apply()` multiple times per cell per hour are blocked by the *existing* activity-ledger architecture, for two independent reasons at two different layers (the per-attempt duplicate-cell guard, and the once-per-hour non-accumulating ledger read), and a correct fix for either requires touching the activity/ledger accumulation itself (e.g. calling `accumulateTillageActivity` once per sub-dose immediately after each `commitAttempt`, which needs a cross-module signature change from `disturbance_management_dispatch.zig` into `ecosys_ng.zig`'s driver-level ledger, or redesigning `Sidecar` to accumulate across attempts). This is exactly the "substantial dispatch-design change, not a one-line reorder" the third diagnosis pass below already anticipated for design option (d) -- now with concrete, reproducible evidence of the specific mechanism (duplicate-cell guard, then non-accumulating per-attempt ledger overwrite) that makes it substantial, rather than a supposition.

**Disposition**: evidence for, not resolution of, the still-open design decision. This pass adds a fourth data point beyond the three options the third diagnosis pass already named: any interleaved/repeated-dose redesign (option (d)) must also redesign the tillage activity ledger's attempt/accumulation model, not just the water-mixing call site, or it will fail on a real (not spurious) hourly mass-conservation check hundreds of hours before the frontier it is meant to fix. The dose-splitting hypothesis itself remains untested and unranked relative to option (a) (capacity-aware self-limiting dose) and option (c) (dedicated post-tillage relief step); no evidence here favors or disfavors "many small doses reduces peak overflow" specifically.

`XCORP`/`CORP` (the mixing fraction) is set **once per calendar day** in `day.f:347-357` from that day's `ITILL(I,NY,NX)` disturbance-file entry (`CORP=ITILL/10` clamped to [0.05,1.0], `XCORP=1-CORP`) -- there is no per-hour reset anywhere in `day.f` or `redist.f`. `day.f` itself runs once per day, before the hourly loop (`soil.f:131`).

**Water-mixing formula, read in full (`redist.f:11900-12200`):** each layer's new `VOLW`/`VOLV`/`VOLI` is a three-way blend (`redist.f:12180-12185`, e.g. for water):
```
VOLW(L,..)=TI*VOLW(L,..)+CORP*(FI*TVOLW-TI*VOLW(L,..))+TX*VOLW(L,..)+FI*TVOLWR
```
where `TI`/`TX=1-TI` split the layer between inside/outside the tillage depth, `FI` is that layer's depth-fraction of the whole tilled zone, and `TVOLW` is the `TI`-weighted sum of water already accumulated across every layer in the tilled zone (`redist.f:11932`, `TVOLW=TVOLW+TI*VOLW(L,..)`). This is a **partial relaxation toward the mixing-zone-wide total**, scaled by the day's fixed `CORP` fraction -- confirmed by reading the full 300-line block (`redist.f:11900-12200`) that no term anywhere references `VOLX`, `POROS`, or any other pore-capacity/pore-space variable. Legacy's tillage mixing is therefore **exactly as capacity-unaware, algebraically, as Zig's** -- it does not check or cap any destination layer's result against its own pore capacity either. It structurally avoids the failure mode not through a capacity check but through two combined architectural properties: (1) each single application only moves a bounded `CORP`-weighted fraction of the imbalance, not the full imbalance in one shot, and (2) it is applied dozens of times per tillage day, and every single application is immediately followed (next substep, or the next hour) by another `CALL WATSUB` within the *same* day -- so WATSUB's own mechanical-displacement prepass gets many repeated chances across the day to relieve any transient per-layer overfill a given small mixing step creates, long before that day ends and long before any hour-boundary check downstream could see an uncorrected violation compound.

**Zig comparison:** `applyDeferredTillageSoil` (`ecosys-ng/src/ecosys_ng.zig:4021`, inside `postScienceManagementAndGasAccounting`) is confirmed by `stage_execution_census` (`tillage_soil_application entries=2 first_hour=2532 last_hour=3252`) to fire **exactly once per tillage event**, not once per substep/hour of a multi-hour event window. `redistribution/tillage/runtime_adapter.zig:apply()` (line 814) takes a single `mixing_fraction` parameter and writes the fully-mixed result for that fraction directly into `matrix_liquid_water_m3` in one `@memcpy` (`runtime_adapter.zig:1005`) -- i.e. Zig collapses legacy's "many small fractional applications spread across a whole day, each followed by a WATSUB relief opportunity" into "one single full-strength dose at one hour, followed by no further WATSUB call until the next hour's already-too-late hard entry check."

**Call-order verdict: inconclusive for a clean fix, per the task's step 5.** This is *not* simply "one function call sits on the wrong side of WATSUB" -- both `REDIST` (legacy) and `applyDeferredTillageSoil` (Zig) run strictly *after* that timestep's own WATSUB-equivalent solve, matching each other's intra-substep position. The actual, confirmed mismatch is architecture/frequency: legacy's safety net is repetition-and-interleaving (many small relaxation steps, each with its own WATSUB relief chance, spread across an entire calendar day), not an explicit per-layer capacity check. Zig's single deferred one-shot dose has no equivalent repeated-relief structure. Moving `applyDeferredTillageSoil` to run earlier within the *same* hour (e.g. before that hour's WATSUB substep loop) would at best buy **one** relief opportunity instead of legacy's dozens, and would still leave the dose itself at full (not `CORP`-fractional) strength -- an unproven, non-equivalent substitute for legacy's actual mechanism, not a narrow "restore call order to match legacy" fix. Per the task's own framing, this does not meet the bar for a high-confidence, narrowly-scoped implementation in this pass.
