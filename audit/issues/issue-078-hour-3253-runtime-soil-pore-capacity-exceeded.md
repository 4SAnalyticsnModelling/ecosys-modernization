## Third diagnosis experiment (2026-09-21, source-reading only, no runtime rerun -- 3rd/final reserved experiment)

**Goal**: find Fortran's actual tillage/soil-mixing implementation (the second pass's grep for `CALL TILLAGE`/`CALL TILL`/`SUBROUTINE TILL` had found nothing) and compare its capacity-handling and call order against Zig's `applyDeferredTillageSoil`.

**Found it.** A broader grep for `XCORP`/`ITILL`/`TILL` across all of `f77src/` (not just `CALL TILL*`) locates it: legacy has no separate named tillage subroutine at all -- the mixing action is embedded directly inside `SUBROUTINE REDIST` (`f77src/redist.f`), guarded by (`redist.f:11277-11278`):
```
IF(ITILL(I,NY,NX).GE.0.AND.ITILL(I,NY,NX).LE.20
2.AND.XCORP(NY,NX).LT.1.0-ZERO2)THEN
```
`XCORP`/`CORP` (the mixing fraction) is set **once per calendar day** in `day.f:347-357` from that day's `ITILL(I,NY,NX)` disturbance-file entry (`CORP=ITILL/10` clamped to [0.05,1.0], `XCORP=1-CORP`) -- there is no per-hour reset anywhere in `day.f` or `redist.f`. `day.f` itself runs once per day, before the hourly loop (`soil.f:131`).

**Call-order/frequency, read from `soil.f:135-223`:** the per-hour loop (`DO 9995 J=1,24`) contains a per-substep loop (`DO 9990 NFZ=1,NFH`) whose body is, in order: `CALL WATSUB` (157) ... `CALL EROSION` (213) ... `CALL REDIST` (221). Since `REDIST`'s tillage guard depends only on that day's `ITILL(I,...)`/`XCORP(NY,NX)` (constant for the whole day, not reset mid-day), **the tillage-mixing block inside `REDIST` re-executes at every single substep of every hour of the entire tillage day** -- up to `24*NFH` times (96 times at the committed `NFH=4` baseline), not once.

**Water-mixing formula, read in full (`redist.f:11900-12200`):** each layer's new `VOLW`/`VOLV`/`VOLI` is a three-way blend (`redist.f:12180-12185`, e.g. for water):
```
VOLW(L,..)=TI*VOLW(L,..)+CORP*(FI*TVOLW-TI*VOLW(L,..))+TX*VOLW(L,..)+FI*TVOLWR
```
where `TI`/`TX=1-TI` split the layer between inside/outside the tillage depth, `FI` is that layer's depth-fraction of the whole tilled zone, and `TVOLW` is the `TI`-weighted sum of water already accumulated across every layer in the tilled zone (`redist.f:11932`, `TVOLW=TVOLW+TI*VOLW(L,..)`). This is a **partial relaxation toward the mixing-zone-wide total**, scaled by the day's fixed `CORP` fraction -- confirmed by reading the full 300-line block (`redist.f:11900-12200`) that no term anywhere references `VOLX`, `POROS`, or any other pore-capacity/pore-space variable. Legacy's tillage mixing is therefore **exactly as capacity-unaware, algebraically, as Zig's** -- it does not check or cap any destination layer's result against its own pore capacity either. It structurally avoids the failure mode not through a capacity check but through two combined architectural properties: (1) each single application only moves a bounded `CORP`-weighted fraction of the imbalance, not the full imbalance in one shot, and (2) it is applied dozens of times per tillage day, and every single application is immediately followed (next substep, or the next hour) by another `CALL WATSUB` within the *same* day -- so WATSUB's own mechanical-displacement prepass gets many repeated chances across the day to relieve any transient per-layer overfill a given small mixing step creates, long before that day ends and long before any hour-boundary check downstream could see an uncorrected violation compound.

**Zig comparison:** `applyDeferredTillageSoil` (`ecosys-ng/src/ecosys_ng.zig:4021`, inside `postScienceManagementAndGasAccounting`) is confirmed by `stage_execution_census` (`tillage_soil_application entries=2 first_hour=2532 last_hour=3252`) to fire **exactly once per tillage event**, not once per substep/hour of a multi-hour event window. `redistribution/tillage/runtime_adapter.zig:apply()` (line 814) takes a single `mixing_fraction` parameter and writes the fully-mixed result for that fraction directly into `matrix_liquid_water_m3` in one `@memcpy` (`runtime_adapter.zig:1005`) -- i.e. Zig collapses legacy's "many small fractional applications spread across a whole day, each followed by a WATSUB relief opportunity" into "one single full-strength dose at one hour, followed by no further WATSUB call until the next hour's already-too-late hard entry check."

**Call-order verdict: inconclusive for a clean fix, per the task's step 5.** This is *not* simply "one function call sits on the wrong side of WATSUB" -- both `REDIST` (legacy) and `applyDeferredTillageSoil` (Zig) run strictly *after* that timestep's own WATSUB-equivalent solve, matching each other's intra-substep position. The actual, confirmed mismatch is architecture/frequency: legacy's safety net is repetition-and-interleaving (many small relaxation steps, each with its own WATSUB relief chance, spread across an entire calendar day), not an explicit per-layer capacity check. Zig's single deferred one-shot dose has no equivalent repeated-relief structure. Moving `applyDeferredTillageSoil` to run earlier within the *same* hour (e.g. before that hour's WATSUB substep loop) would at best buy **one** relief opportunity instead of legacy's dozens, and would still leave the dose itself at full (not `CORP`-fractional) strength -- an unproven, non-equivalent substitute for legacy's actual mechanism, not a narrow "restore call order to match legacy" fix. Per the task's own framing, this does not meet the bar for a high-confidence, narrowly-scoped implementation in this pass.

**Disposition:** genuinely does not map cleanly onto a call-order fix; reporting honestly per step 5 rather than forcing a fix. Two real options remain, both design decisions requiring a dedicated pass: (a) make the single deferred dose itself capacity-aware/self-limiting (a new algorithm), or (d, new) restructure Zig's deferred-tillage dispatch to interleave repeated smaller-fraction applications across the substep loop for the tillage event window, each followed by a WATSUB-equivalent call, mirroring legacy's actual architecture (a substantial dispatch-design change, not a one-line reorder). Neither was implemented. **No code changed in this pass; diagnosis budget 3 of 3 experiments spent (this pass: source-reading only, no runtime rerun).**

**Mechanism trace (static).** `ecosys-ng/src/soil/water/solver_flux.zig:117-127`, `acceptedEntryLiquidCeilingM3`, is documented as: "accepted entry overfill may persist transiently [through a hydraulic solve], but a nonlinear proposal may not manufacture any additional overfill." Concretely: `ceiling = max(capacity, entry_liquid + ice) - ice`, i.e. if a layer enters the hour already over its own capacity, the Newton/Anderson room-clamping in `solver_solve.zig` (`available_capacity`, `positive_room`/`negative_room`) treats the *entry* overfill itself as the ceiling and will not shrink it, only prevent it from growing further inside that hour's solve. `runtime_material_refresh.zig`'s own comment (lines 239-244) names the intended relief mechanism: a "source-ordered mechanical prepass" -- the WATSUB vertical-displacement path -- that is supposed to relocate any capacity-contraction-driven overfill to an adjacent layer before the hour ends, so the *next* hour's hard boundary check (above) passes.

Separately, `ecosys-ng/src/soil/profile/relayering.zig:423-443` -> `heat_layer_remap.zig:83-260` (`transferLayerFractions`) moves a fraction `fx` of a *source* layer's water and pore capacity into a *destination* layer: `dst_water' = dst_water + fx*src_water`, `dst_capacity' = dst_capacity + fx*src_capacity`. Algebraically this transfer is excess-preserving (cannot create a violation at the destination) **only if neither endpoint entered already violating its own capacity** -- if `src` carries "accepted entry overfill" (tolerated per the paragraph above), the transfer's own excess term is `fx * (src_capacity - src_water) < 0`, which can push a previously-valid `dst` (layer 1) over capacity too.

Cell=0/layer=1 is exactly one layer below cell=0/layer=0 -- the site of every prior round-1-through-7 "chronically elevated top-layer water content" finding in this issue's own history.
