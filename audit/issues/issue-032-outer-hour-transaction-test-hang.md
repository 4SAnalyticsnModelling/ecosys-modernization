## Diagnosis (2026-09-19)

**Method**: static analysis first (per contract), then bounded dynamic reproduction (PowerShell background jobs, hard-capped, no run exceeding ~100s, ~3 minutes total dynamic time spent, well under the 5-minute budget). No source file was modified; a `git status --short` at the end of the session confirms a clean tree (`D:\ecosys-modernization` is in fact a git repo -- `git rev-parse --is-inside-work-tree` returns `true` there and in `ecosys-ng/`, contrary to this session's environment banner).

**1. Static read of the named test** (`ecosys-ng/src/driver/outer_hour_transaction.zig:1489-1596`, `test "production outer hour explicitly owns soil gas and pending surface ledger"`): this test does **no model execution whatsoever**. It reads `src/ecosys_ng.zig` once via `std.Io.Dir.cwd().readFileAlloc` into memory, then performs a fixed sequence of `std.mem.indexOf`/`indexOfPos`/`count` substring searches over that in-memory buffer to assert call-order and binding-occurrence invariants on the driver source text. Every loop in this test file (`StableJournal.restore`'s reverse `while`, the binary search in `ExcludedRanges.overlaps`, etc.) is bounded by a decrementing index or a fixed slice length; none depends on floating-point equality, a resettable counter, or unbounded recursion. **This rules out the named test's own body as the site of an infinite loop.** It cannot reach `outer_hour_transaction.zig`'s runtime `Transaction`/`Workspace`/`StableJournal` machinery, the heat/water solver's bounded 8-tier retry ladder (`recovery_substep_counts = [1,2,4,8,16,20,32,64]` in `ecosys-ng/src/soil/water/heat_step.zig:483`), or the SOLUTE reaction solver's own retry escalation referenced by issue-015 -- it never calls into `soil/solute/reaction_solve.zig` or any solver code at all.

**2. Bounded dynamic rerun, routed through the actual `tests` build target's root** (`zig test src/module_index.zig --test-filter "production outer hour..."`, 100s cap): completed in well under the cap. 52 test groups ran (mostly single reference-forcing `test_0` stubs per index file, per the `_ = ecosys.outer_hour_transaction;` idiom in `driver_test_index.zig`), reaching the named test at position 49/52. **It did not hang.** It **failed** a `std.testing.expectEqual` at `outer_hour_transaction.zig:1530` -- one of seven expected single-occurrence source bindings (`".plant_water_state_update = &driver_context.plant_water_state_update_state.*"` or a sibling in that same `inline for` list) was found 0 times instead of 1 in the current `advance_phase` slice of `src/ecosys_ng.zig`. This reads as **source drift**: `ecosys_ng.zig`'s `advanceHour` phase has apparently changed (plausibly by other concurrent audit work between run-004's 2026-09-18 discovery and now) such that one of this test's hard-coded structural assertions no longer holds. This is a real, currently-failing assertion, but it is a fast, clean failure -- not a hang.

**3. Attempted rerun routed through `src/ecosys_ng.zig` directly** (75s cap): did not reproduce the module-tree route at all -- without build.zig's module-name wiring (`.imports = &.{.{ .name = "ecosys_ng", .module = module }}`), the bare `zig test src/ecosys_ng.zig` invocation cannot resolve the `@import("ecosys_ng")` package import, so it silently compiled only 3 unrelated file-local tests and never reached `outer_hour_transaction.zig` at all. This attempt is **inconclusive by construction**, not evidence of anything, and is recorded only so a future session does not repeat it expecting a faithful reproduction of the build's second (`executable_tests`) artifact. Faithfully reproducing that second artifact requires going through `zig build test` itself (or replicating its exact `-M`/module-import flags by hand), which this session's bounded time budget did not reach.

**Conclusion**: the hang is very likely **not** in the named test's own logic -- static reading rules that out conclusively, and the one faithful dynamic route available (module_index.zig root) completed in seconds. Two live possibilities remain open, undistinguished by this session's 3 experiments:
- (a) **Zig test-runner name misattribution under buffered output**: `zig build test` runs both artifacts; if stdout is buffered, the last *printed* test name at the moment of a hang is not guaranteed to be the *currently running* one. The true hang could be in a different, later-declared test anywhere in the whole module graph (a large one: 52+ entries were seen from module_index.zig alone, and the full graph is far larger per the project's own audit scope). This would make issue-032's test-name attribution itself unreliable, and the real hang could plausibly be in an actual solver-exercising test (e.g. something touching `soil.solute.reaction_solver`, `soil.solute.reaction_solver_tests`, or `soil.gas.coupled_gas_solver_tests`, all of which sit near this test in declaration order and, unlike this test, do execute real numerical code) -- which *would* connect to issue-015's stiff-solver retry ladder. This session did not check those tests' own termination bounds; that is the next concrete step.
- (b) **Environment/toolchain-specific stall specific to the two-artifact `zig build test` invocation** (e.g. Windows/MSYS2 antivirus scan or file-lock contention on the freshly linked `test.exe` when both artifacts build/link/run in the same `zig build` graph), independent of any model logic -- consistent with the issue's own original hypothesis (c) and not yet checked (would require actually running `zig build test` end-to-end with a hard external kill, which this session's remaining bounded time did not spend, to avoid risking another multi-hour runaway if the hang is real and this hypothesis is wrong).

**Connection to issue-015**: **not established, and now considered less likely for this specific named test** -- the named test provably cannot reach the SOLUTE reaction retry ladder or any solver code. If the hang is real and reproducible, it is more likely either (a) a name-misattribution pointing at a genuinely different, solver-exercising test elsewhere in the graph (which *could* then share issue-015's root cause), or (b) an unrelated build/OS-level stall. This issue and issue-015 should remain **separate** records until a future session pins the true hanging test's identity.

**What would be needed to actually resolve this**: (1) reproduce via the real `zig build test` command with a hard external process-tree kill (not just `Stop-Job`, since that may not kill a detached linked `test.exe`) and unbuffered/line-flushed progress output (or `--test-filter` narrowed incrementally) to get a trustworthy last-running test name; (2) if that name is a solver test, check its convergence loop against issue-015's bounded-ladder discipline for a resettable-counter or floating-point-equality exit condition; (3) if the hang truly does not reproduce at all under a fresh rebuild, downgrade this issue to "environment-specific, not yet reproduced this session" rather than "confirmed reproducible," since this session's three bounded attempts did not observe it.
