# Feature ID: FEAT-023-EXEC-DAILY-MASS-BALANCE-PROGRESS-AND-REINIT-GATE

Status: PARTIALLY_ASSESSED (first-pass source-audit; `exec.f` is small, 103 lines, full-file read; call-site and cross-file control-flow context read but not exhaustively traced)

## Scope and provenance

Legacy source: `f77src/exec.f` (sha256 `B588CAE65E01607DB18DD2DFED8751CFB23FB2D0D2AFC2EC1B88E9CA99BFF8B4`), header comment: "THIS SUBROUTINE TAKES MASS BALANCE VARIABLES CALCULATED IN 'REDIST' AND PERFORMS MASS BALANCE CHECKS AT THE END OF EACH DAY OF THE MODEL RUN, AND ERRORS OF > 1UG ARE FLAGGED." Single entry point `SUBROUTINE exec(I)`, `I`=current simulated day-of-year.

**Call-site correction versus the incidental description this dossier was commissioned from**: `exec.f` is not called from `main.f`'s scenario loop nor from `day.f`. It is called exactly once per simulated day from `f77src/soil.f:278` (`CALL EXEC(I)`), which is itself the true per-scene orchestrator ("THIS IS THE MAIN SUBROUTINE FROM WHICH ALL OTHERS ARE CALLED FOR ALL SCENES IN ALL SCENARIOS", `soil.f:4-5`, called once per scene from `main.f:117`). Within `soil.f`, `day.f` (`CALL DAY(I,...)`, `soil.f:131`) runs once at the *start* of each day to set up daily forcing/management; the hourly physics loop (`hour1`/`watsub`/`nitro`/`solute`/`trnsfr`/`trnsfrs`/`erosion`/`redist`, `soil.f:~140-222`) runs for that day; then output writers (`outsh`/`outph`/`visual`/`woutp`/`outsd`/`outpd`, `soil.f:225-272`) run; and only then, at `soil.f:278`, is `exec.f` called -- i.e. `exec.f` is the *last* thing that happens for a day, after all physics and all output for that day are complete. So relative to `feature-016` (`day.f`, per-day *setup* before the hour loop) and to `main.f` (per-scenario/scene dispatch), `exec.f` is the per-day *closeout*: mass-balance drift audit, operator progress echo, and a scene-continuity/checkpoint-reinitialization signal consumed immediately afterward at `soil.f:285-289`.

## 1. End-of-day whole-landscape mass-balance drift check and periodic baseline reset -- `replaced-by-approved-feature`

`exec.f:25-33` resets seven running reference totals (`TLW,TLH,TLO,TLC,TLN,TLP,TLI` -- water, heat, O2, C, N, P, ion/salt) only at `I.EQ.IBEGIN.OR.I.EQ.ISTART.OR.I.EQ.ILAST+1` (run start/scene-boundary/run-end). `exec.f:40-93`, gated on `(I/IOUT)*IOUT.EQ.I` (every `IOUT` days), computes `DIFFx=(current_total - TLx)/TAREA` for each of the seven pools, writes `WRITE(18,213)` (machine-readable, unit 18) with all seven deviations, and, per pool, if `ABS(DIFFx).GT.1.0E-06` writes a `"<POOL> BALANCE LOST ON DAY, YEAR"` diagnostic (`WRITE(18,19x)`) **and silently rebases `TLx` to the current total** -- i.e. legacy's discipline is *warn-and-rebase*, never *reject*: there is no code path in this file (or, per `feature-010` finding 3, in `redist.f`'s own now-dead balance-check block) that halts, rolls back, or refuses a step for a mass-balance violation. It is a post-hoc, once-per-`IOUT`-days, single-global-sum, one arbitrary absolute threshold (1e-6, same for all seven physically distinct units: g, MJ, mol-equivalent, etc.) audit.

Zig counterpart (architectural, not line-for-line): `ecosys-ng/src/validation/hourly_cell_conservation.zig` (sha256 `1133181B2A019FA99F1B9DE168398ACA4F8C6FAEA023744EEFB501DA021F1F87`) and siblings `layer_local_conservation.zig`, `landscape_boundary_balance.zig`, `mass_balance_audit.zig`, `landscape_mass_balance_runtime.zig`, `core/conservation_tolerance.zig` (sha256 `A9DF962B796F0E6C079CBFA6D7A5809EFA95D58899F615FD03065A12EF6A71EA`, `AbsolutePerArea` -- one independently configurable, physically-typed floor per conserved quantity: `water_m`, `heat_megajoules_m2`, `oxygen_g_m2`, `carbon_g_m2`, `nitrogen_g_m2`, `phosphorus_g_m2`, `ions_mol_m2`, plus sand/silt/clay/exchange-capacity, `:7-25`). This is the same architecture-level replacement already identified and dispositioned in `audit/features/feature-010-redist-state-acceptance-conservation.md` finding 3 (there, applied to `redist.f`'s own *dead* end-of-run diagnostic block) -- **folded in here, not re-derived**: `exec.f`'s check is a distinct, *live* (not dead-code) legacy routine performing the same *kind* of coarse, threshold-and-rebase, non-gating audit, once per day rather than never, and it is superseded by the same per-hour, per-process, unit-scoped, transactional accept/reject conservation system. Per the contract's explicit requirement ("Conservation tolerances have units and scale... never loosened solely to finish a run" and "Trial states must be transactional... Restore the complete pre-step state on failure"), the Zig design is the approved direction, not merely an incidental difference.

**Disposition: `replaced-by-approved-feature`.** Not independently re-verified this pass whether the Zig conservation gate's floors/relative criteria are demonstrably at least as tight as legacy's 1e-6/`TAREA` threshold for every one of the seven pools (cross-check against `audit/conservation/` evidence, per `feature-010`'s own caveat, before treating this as fully closed).

## 2. Operator-visible day-advance progress echo -- `preserved` (in spirit; format/cadence differ, not a scientific-parity concern)

`exec.f:49,52` (`WRITE(*,212)I,IYRC` / `FORMAT('NOW EXECUTING DAY',I6,'   OF YEAR',I6)`), gated on the same `(I/IOUT)*IOUT.EQ.I` cadence as finding 1 -- this is the exact source of the `NOW EXECUTING DAY N OF YEAR YYYY` line referenced incidentally elsewhere in this audit.

Zig: `ecosys-ng/src/ecosys_ng.zig:8055-8056`, `if (scene_weather_hours % 24 == 0) std.log.info("day advanced: scene_weather_hours={d} final_hour_elapsed_ms={d}", .{ scene_weather_hours, hour_elapsed_ms })`. Functionally equivalent operator-visible "a day just completed" signal, fired on a fixed 24-hour cadence rather than legacy's configurable `IOUT`-day cadence, and carrying an elapsed-hours/timing counter rather than the legacy calendar day-of-year/year pair. The comment at `:8051-8054` ("Keep default production progress visible at each accepted day boundary") shows this is a deliberate, current design choice, not an oversight. **Disposition: `preserved`** for the operator-progress-signal *intent*; the specific fields logged (day/year identifiers vs. hour-count/timing) are a cosmetic console-output difference with no output-file or scientific-parity consequence, since none of `exec.f`'s numeric deviations (`DIFFQ`...`DIFFI`) are reproduced in this log line -- those live in the separate conservation-survey/mass-balance-audit reporting path (finding 1), not here.

## 3. `IDAYR`/`IOLD` scene-continuity signal and mid-run checkpoint-reinitialization trigger -- `unresolved`, filed as `issue-030`

`exec.f:94-99` unconditionally sets, every day: `IDAYR = (IDAYR.LT.0) ? LYRX+IDAYR : I` and `IOLD = I` (plus `IMNG=0`, `NYR=0`). Immediately after the `CALL EXEC(I)` return, `soil.f:285-289` tests `IF(NYR.NE.1.AND.IDAYR.NE.IOLD)` to decide whether to re-read checkpoint files (`CALL ROUTS`/`CALL ROUTP`) before continuing. The same `IDAYR.NE.IOLD` comparison also gates full state re-initialization (`STARTS`/`STARTQ`/`STARTE`, `soil.f:39,78,106`) at the *start* of a new scene, immediately after `reads.f` (called once per scene, `soil.f:32`) sets `IDAYR` to a scene-boundary sentinel: `IDAYR=MIN(ISTART-1,ILAST)` with `NYR=0` for a mid-year scene end, or `IDAYR=LYRX` (year length) with `NYR=1` for a year-boundary scene end (`reads.f:760-767`). Because `exec.f` re-syncs `IDAYR=IOLD=I` every day *during* a scene's own day loop, the comparison only ever differs across a *scene boundary*, and only when the new scene's declared start is genuinely discontinuous with where the previous scene's `exec.f` calls left `IOLD` -- i.e. this is the mechanism that lets a multi-scene deck (e.g. several forcing years replayed in sequence with continuous state) skip full re-initialization when scenes are contiguous, and force it when they are not.

**Zig's own code explicitly flags that it has no equivalent gate.** `ecosys-ng/src/ecosys_ng.zig:312-316` (inside `recordHourStageExecution`, a stage-execution census instrument): "The day-of-year wrap. The deck is six forcing years repeated five times with continuous state, so this fires at each 365->1 boundary. Legacy handles that boundary with `reads.f:760-767` setting IDAYR=365 so `soil.f:39,78,106` do not re-initialize; ng has no such gate, so whether this ever fires is exactly what needs measuring." This is a self-declared, unverified-impact gap in the exact mechanism `exec.f` maintains the `IOLD` side of every day. It is directly in scope for this dossier because `exec.f` is the routine that both produces the `IOLD` state this comparison consumes and is the only place `IDAYR` is normalized back to a plain day-of-year (versus the negative-sentinel form referenced at `exec.f:94-95`, whose setter was not located in this pass -- see "Not covered this pass").

**Disposition: `unresolved`.** This is not dead code, not an incidental cosmetic difference, and not yet reviewed/approved as an intentional scope change -- it is a load-bearing legacy re-initialization-suppression/checkpoint-reinit trigger with no confirmed Zig counterpart, self-flagged by the Zig codebase's own commentary as unmeasured. Filed as `audit/issues/issue-030-idayr-iold-scene-continuity-gate-unmirrored.md`.

## 4. `IMNG` management-event flag clear -- not independently resolved this pass

`exec.f:100` clears `IMNG=0` every day. `f77src/reads.f:1209` sets `IMNG=1` (context: a per-scene management/event read path, not depth-read this pass). `f77src/routs.f:41`, `IF(IMNG.EQ.0)THEN` gates a block that re-zeroes tillage/irrigation/fertilizer schedule arrays (`ITILL`,`DCORP`,`RRIG`,`FERT`) when reading a checkpoint -- i.e. `IMNG` appears to suppress checkpoint-driven clobbering of the *current* scene's freshly-read management schedule when a management event has already been registered this scene. `exec.f`'s role is limited to clearing the flag once per day; the flag's producer (`reads.f:1209`) and consumer (`routs.f:41`) were not depth-read this pass. No Zig counterpart search was performed for `IMNG` specifically. **Not dispositioned this pass** -- see "Not covered this pass".
