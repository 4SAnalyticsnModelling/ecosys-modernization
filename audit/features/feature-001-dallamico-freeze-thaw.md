## Term-for-term equation correspondence (2026-09-19, this session)

Verified directly against the extracted paper text (page/eq. numbers as printed):

- **Paper Eq. 11** (generalized Clapeyron, ice pressure null): `rho_w * Lf * dT/T = dp_w`. Not implemented as a standalone line, but its integral is: see below.
- **Paper Eqs. 12-13**: Eq. 12 is the *exact* integral `Lf*ln(T/Tm) = p_w` (for saturated soil, `p_a=0`); Eq. 13 is the *linearized* approximation `Lf*ln(T/Tm) ~= Lf*(T-Tm)/Tm`, which the paper then uses to derive its Eqs. 15/17/19 closed forms.
- **Zig `melting_temperature_k`** (`phase_change.zig:153-164`): `clapeyron_exponent = g*psi_w0/Lf`; `melting_temperature_k = Tm * exp(clapeyron_exponent)`. Rearranging the *exact* Eq. 12 integral for the unsaturated case (paper Eq. 16, same structure, bounds `Tm..T*` and `0..psi_w0`) gives `Lf*ln(T*/Tm) = g*psi_w0` i.e. `T* = Tm*exp(g*psi_w0/Lf)` -- **this is exactly the un-linearized exact integral**, confirming the in-source claim ("we retain the exact integrated Clapeyron logarithm from Eqs. 11-12 rather than the linearized approximation in Eq. 13"). The paper's own printed Eq. 17, `T* = Tm + (g*Tm/Lf)*psi_w0`, is the first-order Taylor expansion of this same exact result (`exp(x) ~= 1+x`), matching the docstring's claim that the two are "first-order equivalent around the melting point." Term-for-term: `clapeyron_exponent` <-> `g*psi_w0/Lf`; constants `gravitational_water_potential_mpa_per_m` <-> `g` (in MPa/m, consistent with `latent_heat_of_fusion_megajoules_per_m3` <-> volumetric `Lf` since 1 MJ/m3 = 1 MPa, matching the paper's `rho_w*Lf(J/kg) = Lf_volumetric(J/m3)` substitution). The `minimum_exponent`/`floatMin` clamp is a pure numerical-underflow guard with no physical-equation counterpart -- it does not alter the formula, only prevents `exp()` underflowing to exactly `0` for pathologically dry/cold inputs.
- **Zig `liquid_pressure_head_m`** (`:165-174`): for `T < T*`, `psi(T) = psi_w0 + (Lf/g) * log1p((T-T*)/T*)` = `psi_w0 + (Lf/g)*ln(T/T*)`. This is the exact integral of Eq. 18 (`integral_{T*}^{T} Lf dT/T = integral_{psi_w0}^{psi} g dpsi'`), i.e. the un-linearized counterpart of the paper's printed Eq. 19 (`psi(T) = psi_w0 + Lf/(g*T*)*(T-T*)`), for the identical reason as above. For `T >= T*`, the code returns `psi_w0` unchanged -- matches the paper's Eq. 20's `T>=T*` branch exactly (Heaviside-gated in Eq. 21).
- **Paper Eqs. 22-23** (van Genuchten total/liquid content): `Theta_v = theta_r + (theta_s-theta_r)*{1+[-alpha*psi_w0]^n}^-m`; `theta_w = theta_r + (theta_s-theta_r)*{1+[-alpha*psi(T)]^n}^-m`. Zig's `MualemVanGenuchtenParameters.waterContentAtPressureHead` (`retention.zig:83-93`, calling `effectiveSaturationAtPressureHeadAssumeValid`) computes exactly `theta_r + Se*(theta_s-theta_r)` with `Se = (1+(alpha*|h|)^n)^-m`, `m=1-1/n` -- an exact algebraic match to both equations' shared functional form; the code evaluates it once at `liquid_pressure_head_m` (paper's `psi(T)`, giving `theta_w`, Eq. 23) and relies on the caller (see "Unchanged contracts" below) to have supplied `total_water_equivalent_m3` as the Eq.-22-consistent `Theta_v` at `psi_w0`, rather than recomputing Eq. 22 redundantly inside this function.
- **Paper Eq. 24** (`theta_i = Theta_v(psi_w0) - theta_w[psi(T)]`): Zig computes `ice_water_equivalent_m3 = total_water_equivalent_m3 - liquid_water_m3` where `liquid_water_m3 = min(total_water_equivalent_m3, retention_limited_liquid_m3)`. The `min()` is a defensive conservative-closure clamp, not a change to Eq. 24's algebra: under the paper's own construction `psi(T) <= psi_w0` whenever `T<T*` (since the `Lf/(g*T*)*(T-T*)` term is <=0), and the retention curve is monotone increasing in pressure head, so `theta_w[psi(T)] <= Theta_v(psi_w0)` should already hold and the clamp is a no-op in the ordinary physical regime -- it only becomes active for the below-residual/dry-evaporated edge case documented at `DALLAMICO-BELOW-RESIDUAL-WATER-HOUR-2726-001` (see below), where it is the mechanism that keeps ice non-negative. This is exactly the "conservative closure" the function's docstring claims, now traced to the specific algebraic reason it holds.
- **Unchanged contracts, now confirmed rather than assumed**: `unfrozenPressureHeadM` (`ecosys-ng/src/soil/heat/solver_enthalpy.zig:53-67`) is the sole production caller-side supplier of `unfrozen_pressure_head_m`/`total_water_equivalent_m3` pairing, and it computes `psi_w0` as *exactly* `parameters.pressureHeadAtWaterContent(clamp(Theta_v, theta_r, theta_s))` -- i.e., the retention-curve inverse of the total water content, on the *unmodified* Mualem-van Genuchten curve (its own doc comment explains why: pricing the caller's Theta_v rather than a partial/liquid content, and using the unmodified curve rather than an ice-shrunk one). This is precisely Eq. 22 used in reverse (`psi_w0 = f^-1(Theta_v)`), confirming the coupling invariant the paper's derivation requires is actually honored at the one call site that supplies it, not merely assumed.

## Addendum 2026-09-18 (second session, ecosys-modernization-88): a SECOND, distinct legacy freeze-thaw mechanism found, structurally matched to its Zig port (numerical test not yet run)

This dossier's scope above covers the `dallAmicoEquilibrium` Clapeyron-form treatment. There is a **separate** legacy freeze-thaw mechanism this dossier had not yet traced: the **latent-heat/matric-depressed-freezing-point partition**, `f77src/watsub.f:6386-6446` (surface-litter/snowpack variants at `:1938-1960`, `:2064-2083`, `:2355-2381`, `:2788-2808`, `:3131-3151`):
```
TFREEZ = -9.0959E+04 / (PSISV1 - 333.0)                 [6399]  micropore: matric-depressed freezing point
macropore threshold = 273.15                            [6430]  plain 0C, no depression
HFLFM1 = VHCP1*(TFREEZ-TK1)/(1.0+6.2913E-03*TFREEZ)      [6404-6405]
HFLFM  = donor-bounded, scaled by XNPXX                  [6406-6410]
WFLFL  = -HFLFM/333.0                                    [6411]
```
Explicit physical asymmetry: micropore water is capillary-bound (freezing-point-depressed), macropore water behaves as free water (plain 0C, no depression).

**Zig port, structurally/textually matched**: `phase_change.zig`'s `freezeParameters()` (`:328-330`) carries the identical constants (`9.0959e4`, `333`, `6.2913e-3`, `273.15`). `freezeThaw` (`:286-302`) reproduces the formula AND the micropore/macropore asymmetry in one line (`:291`): `threshold_temperature = if (macropore) parameters.pure_water_freezing_temperature_k else freezing_temperature;`, dispatched via public wrappers `matrixFreezeThaw` (`:276-278`, micropore) / `macroporeFreezeThaw` (`:280-284`, macropore). Donor-bounded heat clamp (`:294-297`) and `liquid_change = -heat/latent_heat`, `ice_change = -liquid_change/ice_density` (`:298-299`) match `watsub.f:6406-6411`'s shape. This half of the freeze-thaw feature is a strong textual/structural match, **complementary to and distinct from** the `dallAmicoEquilibrium` new-physics half already documented above — the codebase appears to run both: the legacy-faithful `freezeThaw` primitive for legacy-equivalent consumers, and `dallAmicoEquilibrium` (paired with the new Mualem-van Genuchten curve) for the hydraulic-conductivity solver.

**Independent review (2026-09-18, fresh agent, no shared context with the author): every citation above re-verified exact against direct file reads, including the non-obvious detail that both Fortran and Zig correctly preserve the macropore *entry gate* using flat 273.15 while the *driving heat term* still uses the depressed freezing temperature.** However, the review found the disposition language overreached: calling this "verified faithful"/`preserved` is not yet earned — no matched-state numerical test has been run (the same bar this dossier's own Dall'Amico section insists on before closing), and which callers route to which of the two mechanisms — and whether that routing is correct — remains untraced (flagged as a follow-up above, but one sentence had already asserted routing correctness with more confidence than that follow-up supports). **Corrected disposition: textually/structurally matched, NOT `preserved` — pending a matched-state test and caller-routing verification before upgrading.**
