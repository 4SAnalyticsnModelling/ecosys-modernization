## 1. Independent verification: `visual.f` is genuinely fully inert in the legacy codebase -- confirmed, `preserved`

Read the entire file (all 286 lines) line by line rather than trusting the prior-session citation (`audit/issues/issue-002-fortran-toolchain-substitution.md`'s Follow-up section, itself citing an external OneDrive reference project's `DISC-OUTPUT-VISUAL-NOT-EMITTED` tag). Independent findings:

- **All output statements are commented (`C`-prefixed) and confirmed by direct count**: every `WRITE` in the file -- `WRITE(19,90)` (`:52`), `WRITE(19,90)` units (`:67`), `WRITE(20,95)` (`:83`), `WRITE(20,95)` units (`:96`), `WRITE(19,91)` (`:254`), `WRITE(20,96)` (`:256`), `WRITE(19,2025)` (`:268`), `WRITE(20,2026)` (`:277`) -- is `C`-commented. That is 8 distinct `WRITE` statements at 8 distinct source locations (two of the nine the prior citation counted, `:52` and `:67`, are the header-label and header-units writes to the same unit 19 inside the same `IF(ICHECK.EQ.0)` one-time block, i.e. the "9 WRITE statements" figure a prior session cited is consistent with this independent count once the one-time header block's two writes are counted separately from the per-step writes). **No live `WRITE`, `PRINT`, or other I/O statement exists anywhere in this file.** The prior finding is confirmed correct.
- **No other live side effect beyond the dead writes was found.** The only live I/O in the file is a **read**: `OPEN(16,FILE='years',STATUS='OLD')` / `READ(16,*)IYR1,IYR2` / `CLOSE(16)` (`:44-47`), executed once (guarded by `SAVE...ICHECK` / `DATA ICHECK/0/`, `:41-43`) to load a year-selection window from an external file named `years`. This has no observable side effect (it does not write, does not mutate any COMMON state consumed elsewhere -- `IYR1`/`IYR2` are local `SAVE`d variables used only to gate this same subroutine's `IF(IYRC.GE.IYR1.AND.IYRC.LE.IYR2)` block at `:116`) beyond potentially **erroring the whole run if the file `years` does not exist** (`STATUS='OLD'` on a missing file is a runtime I/O error in standard Fortran) -- this is a latent, silent operational dependency: if `visual.f` is ever reached (i.e. `DATA(18).EQ.'YES'` in the options file) but no `years` file is staged in the run directory, the model would abort, even though the subroutine, once entered, does nothing observable. This was not tested (out of scope for a read-only pass and would require a run); it is a **static-analysis-only finding**, recorded for completeness, not confirmed against an actual run.
- All other computation inside the routine -- the entire `OUT(1)` through `OUT(68)` array (carbon/energy/water/soil-layer aggregation, `:200-250`), the landscape totals `TTRN/TTLE/TTSH/TTGH/TTCO/TTCH` (`:117-130`), and the soil-water-content `SWC` array (`:131-141`) -- is computed into local arrays/variables that are **never read by any other subroutine** (all are locals or `SAVE`d within this file; none appear in a COMMON block per the file's own `include` list, which pulls only read-only forcing/state blocks, not a dedicated VISUAL-output common). The computed values are pure dead-end arithmetic: real CPU cycles spent every time the (rarely-reached, `DATA(18)='YES'`-gated) subroutine runs, producing values consumed by nothing.

**Disposition: `preserved`.** The independent verification confirms the prior citation: `visual.f`, even when reached, produces no observable output and no side effect other than the described latent file-existence dependency. Zig correctly has no obligation to reproduce dead arithmetic; the question is whether Zig's own comparable capability (finding 2) is scoped and disclosed correctly, which it is.

## 2. What `visual.f` was meant to produce

Recovered from the commented-out `FORMAT`/`WRITE` pairs (`:52-107`, `:254-283`) and variable derivations:

- **Per-timestep, per-cell "hourly" stream** (`WRITE(19,91)`, intended file unit 19): model name, year, day, hour, then 38 values -- cumulative GPP for 3 plant functional types (spruce/shrub/moss) and their total, cumulative Ra (autotrophic respiration) per type and total, total NPP, total Rh (heterotrophic respiration), total NEP, CO2 flux, CH4 flux, net radiation (`Rn`), latent heat (`LE`), sensible heat (`H`), 11 layers of soil water content (`SWC 0..10`), and 11 layers of soil temperature (`Temp 0..10`). Units documented in the commented header: `kg C m-2 s-1`, `W m-2`, `m3 m-3`, `K`.
- **Per-day, per-cell "daily" stream** (`WRITE(20,96)`, intended file unit 20): transpiration by type, evapotranspiration, soil evaporation, runoff, discharge/recharge, water-table depth, snowpack depth, total LAI, leaf/wood/root carbon by type, and an 11-layer SOC profile. Units: `mm`, `m`, `m2 m-2`, `kg C m-2`.
- **Landscape-aggregate variants** of both (`WRITE(19,2025)`/`WRITE(20,2026)`, format labels `'FLUXES'`/`'SWC'`), summed/looped across the `NHW..NHE`/`NVN..NVS` grid-cell window rather than per-cell.

The preceding comment "WRITE OUTPUT FOR SPECIAL PROJECTS (EG MIPS)" identifies this as a bespoke reporting extension for a specific external research consumer (a MIPS -- Model Intercomparison Project Study -- style deliverable), not part of the model's core science or its regular `OUTSH`/`OUTPH`/`OUTSD`/`OUTPD` output-editor-driven files.

## 3. Zig has a live, gated, actually-emitting counterpart -- Zig does MORE than the legacy oracle ever emitted -- notable finding, not a defect

`ecosys-ng/src/io/output/visualization_output.zig` (sha256 `17B7AF894AB746EE7A71463AA315F5E44865A73108CC2E313929B57ECAD787A1`) is a direct, functioning reimplementation of exactly the dead `OUT(1..68)` arithmetic above, and it is wired to **actually write files**:

- `hourlyInto` (`:541-618`) reproduces `visual.f`'s `OUT(1)`-`OUT(38)` term-for-term: e.g. the carbon-rate scale factor `carbon_rate = 0.001 / (inputs.cell_area_m2 * 3600.0)` is `visual.f:200`'s `0.001*CARBN(1,NY,NX)/(AREA(3,NU(NY,NX),NY,NX)*3600)` generalized to arbitrary species/layer counts (the doc comment at `:527-529` states this explicitly: "VISUAL hourly order generalized as: species GPP, species respiration, seven ecosystem carbon fluxes, three energy fluxes, water profile, and temperature profile" -- matching `visual.f`'s `OUT(1)`-`OUT(16)` then two per-layer loops at `:216-226`). The `277.8` radiation/heat unit-conversion constant (`visual.f:213-215`, W m-2 from MJ) is reproduced exactly at `:603` (`net_radiation_megajoules_h * 277.8 / inputs.cell_area_m2`).
- `dailyInto` (`:648-719`) reproduces `visual.f`'s `OUT(39)`-`OUT(68)` term-for-term (doc comment `:636-638`: "VISUAL daily order generalized as: transpiration by runtime species, evapotranspiration, residual soil evaporation, runoff, outflow, water-table depth, snow depth, LAI, species leaf/stalk/root C, and SOC profile" -- an exact match to `visual.f:227-250`'s derivation and `:84-94`'s commented daily-header field list).
- The `Streams` type (`:206-495`) **actually calls the file-writing stream bank** (`bank.streams[cell].write(file_name, ...)`, `:480-493`) whenever `scene_enabled` and the configured year window and per-variable enable flags permit -- this is a live write path, not dead code. Output file names are built with the literal tokens `"visual_hourly"`/`"visual_daily"` (`:471`), and a code comment at `:459-462` explicitly narrates the naming convention's history relative to this exact legacy feature ("the earlier `visual_hourly_c<column>_r<row>_<year>.txt` form used grid indices... for a single-cell run were always `c1_r1`" -- i.e. this Zig output has already been through at least one naming revision in production use, confirming it is a real, exercised feature, not a stub).
- The enable/gate condition maps one-for-one onto `visual.f`'s legacy gate: `SceneOptions.visualization_enabled` (`ecosys-ng/src/core/options.zig`, sha256 `F6F3EEFA7C2A2A0460964B2189310D40D36D07C1984410F1BF6912315AAAE81C`, `:47,97`) is parsed as the 4th scene-option record, immediately after the three scene dates -- the identical field position and `YES`/`NO` semantics as legacy `DATA(18)` (`reads.f:104`, the first of the three post-date option flags; `checkpoint_output_enabled`/`resume_from_checkpoint` at `options.zig:48-49,98-99` correspondingly map to legacy `DATA(19)`/`DATA(20)`, confirmed against their respective legacy consumers at `soil.f:239-261` and `reads.f:53,189,226`). `visualizationIncludesYear` (`options.zig:81-88`) additionally gates on a start/end year window read from the scene-options record (test fixture literal `"ViSuAlIzAtIoN_YeAr_WiNdOw|1998|1998"`, `options.zig:207`) -- a Zig-side refinement (year-windowed rather than always-on-when-enabled) with no direct legacy analog in `visual.f` itself (legacy's own year gate, `IYR1`/`IYR2` read from an external `years` file at `visual.f:44-47`, serves the same *purpose* by a different *mechanism* -- an external file dependency versus an inline option-file record).
- Call sites confirmed live in the production driver: `ecosys_ng.zig:1333,1369` (hourly, inside the accepted-hour output path) and `:2609-2615,2707` (`writeAcceptedDailyVisualizationOutput`, inside the accepted-day output path), both gated on `active_options.*.visualizationIncludesYear(current_year)`, and `:7752-7755` (`configureScene(visualization_enabled, visualization_start_year, visualization_end_year)`, wiring the per-scene option into the stream).

**This is exactly the case the audit brief anticipated: Zig has built a genuinely live, correctly-gated, unit-consistent, tested (`visualization_output.zig:731-1015`, seven `test` blocks covering dimension mismatches, non-finite rejection, negative-value rejection, catalog alignment, and file output) capability that reproduces the *arithmetic* of a legacy feature the legacy codebase itself never actually emits, because every one of its `WRITE` statements is dead.** It is not a defect (nothing in the contract requires Zig to *withhold* a working feature merely because the reference implementation left its own version commented out), and it is not silently invented (the Zig code's own comments and file-naming history explicitly acknowledge and trace back to the `VISUAL` name and structure). It is, however, directly relevant to output-comparison work: **any comparison harness expecting bit-for-bit or even structural legacy `visual_hourly`/`visual_daily` reference files will find none exist** (the legacy run produces zero bytes of this output under any configuration, per finding 1), so Zig's `visual_hourly*.txt`/`visual_daily*.txt` outputs have **no legacy oracle counterpart to validate against** -- they can only be validated by first-principles unit/kernel tests (which exist, see above) and by independent re-derivation from the same state Zig's core science outputs already expose elsewhere (e.g. `OUTSH`/`OUTPH`/`OUTSD`/`OUTPD` equivalents), not by legacy-vs-Zig file comparison.

**Disposition: `replaced-by-approved-feature`-shaped, recorded as a notable finding rather than a strict disposition assignment**, per the task brief's framing -- this is Zig doing *more* than the oracle, not Zig deviating from an oracle behavior, so none of the five contract dispositions (`preserved`/`replaced-by-approved-feature`/`legacy-defect-corrected`/`retired-with-explicit-scope-approval`/`unresolved`) cleanly fits a "the legacy behavior was X, Zig does Y" comparison when X is "nothing, ever." Closest formal fit is `replaced-by-approved-feature` (an approved output-capability feature superseding an inert legacy stub), but this has **not been through an explicit scope-approval review** confirming that reviving this exact legacy-named-but-dead capability was an intentional, reviewed decision versus an emergent byproduct of generalizing another output path. Recommend a reviewer either (a) explicitly approve this as an intentional feature (then it converts cleanly to `replaced-by-approved-feature`), or (b) note it purely as documentation with no disposition required, since there is no legacy behavior to be unresolved *about*.
